## 1. 定位与原则

### 1.1 用户得到什么

视频的权威状态在 `video.db`（SQLite，[架构设计 §5.1](../../architecture/architecture-design.md#51-存储分层)）。它适合编辑，但看不出改了什么，也不能按「版本」回到过去：撤销历史是一笔一笔的，回到一小时前要撤销几十步。

本方案不改存储、不依赖 git。VideoEngine 在每个视频目录里多写两样文本：

- **最新快照**：视频当前状态的确定性文本，打开期间最多落后几秒。
- **最近版本**：最近 10 个版本，每个版本是一份相对上一个版本的 diff，开头列出这一版做了哪些操作。

用户因此得到：

| 收益 | 怎么得到 |
| --- | --- |
| **按版本回滚** | 选一个版本「回到这个版本」，作为一笔可撤销的编辑应用（§3.5）；没有 git 也能用 |
| **看得见每一版改了什么** | 版本文件是标准 unified diff，开头是这一版的操作清单（§3.2）；人、智能体与 `patch` 工具都能读 |
| **视频坏了能重建** | `video.db` 丢了或没带过来，从快照重建（§4.2） |
| **有 git 随时可以提交** | 快照按行稳定排版，适合 git；用户什么时候 `git commit` 都得到一份完整、可重建的状态（§5） |

### 1.2 三层历史

| 层 | 粒度 | 在哪 | 范围 | 用途 |
| --- | --- | --- | --- | --- |
| **撤销历史** | 每一笔编辑事务 | `video.db` 的 `transactions` 与 `undo_records`（[命令与协议规范 §3](../../spec/command-protocol-spec.md#3-事务与严格的版本校验)） | 一部视频，打开以来的全部 | 撤销、重做 |
| **版本记录** | 一个版本：一段工作里的多笔编辑合在一起 | 视频目录的 `.bcut-snapshot/` | 一部视频，最近 10 个版本加上保存的版本 | 看改了什么、按版本回滚、重建 |
| **git**（可选） | 用户或 BaoCut 的一次提交 | 用户的仓库 | 整个项目，不限时长 | 长期历史、同步、备份、协作 |

前两层由 BaoCut 维护，不需要任何外部程序。git 只是锦上添花，它让整个项目可以长期回滚，但版本记录不依赖它。

### 1.3 原则〔G〕

- **`video.db` 仍是唯一的权威。** 快照与版本文件由 VideoEngine 从已提交的状态生成，是派生物（视频格式规范 §3.1「不是第二个写入端」的同一条规则）。外部对快照的改动只能经 VideoEngine 的一笔事务进入视频（§4.3）。
- **只有 VideoEngine 写 `.bcut-snapshot/`**，而且只在它持有这部视频的写锁时写。Runtime 和其他进程只读。
- **回滚是向前的。** 回到某个版本是一笔新的、可撤销的事务，产生一个新版本；不删除、不改写已有版本。
- **不依赖外部程序。** 没有 git，版本记录照样完整工作。BaoCut 运行 git 时不执行仓库带来的命令，也不碰用户的改动（§5）。
- **宁可报错，不给错的时间线。** 版本链上任何一步对不上摘要，那一步以及更早的版本都标为不可用，不拼出一个看似合理的错误状态（§3.5）。

### 1.4 不做什么

- 不把 `video.db` 换成 JSON 与 JSONL。多实体原子提交、幂等与回执、撤销记录与 outbox 同一事务落盘（[架构设计 §5.2](../../architecture/architecture-design.md#52-写入发布与崩溃一致性)）都靠数据库。
- 不做项目级的版本。版本是一部视频的；整个项目一起回到某个时刻是 git 的事。
- 不做「只撤回第 k 版、保留其后各版」。那是三方合并，可能得到语义上错误的时间线。
- 不做视频级的合并。两边都改了同一部视频时，按整部视频选一边（§4.3）。
- 不属于任何项目的会话（会话自己的文件夹）里的视频不写快照、不记版本。
- 幻灯片、文档、设计稿暂不纳入，见待评审事项。

## 2. 工作区快照

### 2.1 位置与布局

```text
<video-dir>/
  video.db, video.lock, blobs/      # 不变
  .bcut-snapshot/
    video.json                      # 最新快照：VideoSnapshot 的投影（§2.2）
    documents/<documentId>.json     # 每个文档当前版本的正文，一个文档一个文件
    history/
      000001.patch …                # 最近的版本，一版一个文件（§3.2）
```

- 放在点目录里：Space 的扫描、`projects.files.list` 与文件监视都跳过点开头的名字（`isIgnoredName`），快照与版本不会作为用户内容出现。代价是现有的递归监视看不到它的变化，外部改动另行检测（§4.1）。
- 文档文件名不带版本号。改一句话是同一个文件里改一行，diff 才有意义。这一点与便携包的 `documents/<id>/<revision>.json` 不同（[视频格式规范 §8](../../spec/video-format-spec.md#8-便携包)）。
- 每个文件先写临时文件再改名替换。写入顺序是先文档、再 `video.json`、最后版本文件；`video.json` 记着每个文档文件的摘要，读的一方发现不符就当作快照不完整，报告而不导入。
- 整个视频目录（含 `.bcut-snapshot/`）随项目一起移动、复制。

### 2.2 内容：当前状态的投影

`video.json` 由 VideoEngine 的 `VideoState::snapshot`（[视频格式规范 §3.1](../../spec/video-format-spec.md#31-videosnapshot)）投影而来，只在下面几处不同：

- **文件头**：`format: 'baocut.workspace-snapshot'`、`schemaVersion: 1`、`videoSchemaVersion`、`videoId`、`name`，以及每个文档文件的摘要（§2.1）。不写 `projectId`：它是机器本地的标识，副本检测会改写它（[架构设计 §5.1](../../architecture/architecture-design.md#51-存储分层)）。
- **去掉每次提交都变的计数**：顶层 `revision`、序列的 `revision`、`eventSeq`、`ownerGeneration`。否则每一版都在头部改一行。写入时的修订号记在 `video.db` 的元数据里（§4.1）。
- **只留当前**：
  - 文档头只保留当前版本，素材版本只保留当前实体引用到的。
  - 检查点不写进快照，保存的版本在版本记录里（§3.6）。
  - 文档正文只写当前版本。
- **不写每次保存都会变的时间**，如 `updatedAt`。只在创建时写一次、之后不变的时间保留，包括 `createdAt`、`importedAt` 和链接时的 `modifiedAt`。

快照里没有撤销历史、回执与 outbox。

### 2.3 行稳定的序列化

快照与版本文件都由 VideoEngine 用 Rust 生成。Runtime 只读、不重新序列化，因为 Node 的 `JSON.parse` 再 `JSON.stringify` 会把整数样子的键提到前面，改变顺序。规则：

- UTF-8，换行 LF，文件以换行结尾。
- 对象的键按字典序：引擎的映射是 `BTreeMap`，`serde_json` 不开 `preserve_order`。数组保持模型规定的顺序：
  - 轨道按顺序再按 ID；
  - 片段按轨道、开始位置、ID；
  - 标记按帧再按 ID。
- **前两层展开，第三层起每个值写成一行**：
  - 根对象的每个成员一行，缩进两个空格；
  - 第三层及更深的值压成一行紧凑 JSON；
  - 结果：`video.json` 里一个片段、一个标记、一个素材版本各占一行；转录文档里一个句段连同它的词时间占一行。
- 同一状态必须得到逐字节相同的文本。这是序列化器的单元测试。
- **往返不变**：从快照重建（§4.2）或导入（§4.3）之后立即写出的快照，必须与读入的快照逐字节相同。投影与导入都不能补默认值、丢可选字段或改顺序，否则版本链最新一版的摘要对不上，全部保留的版本都会被判为不可用（§3.5）。

改一个片段的入点，diff 是一行；给一句字幕改一个字，也是一行。

### 2.4 何时写

视频打开期间：

- 最后一笔编辑之后 10 秒写一次（去抖）。
- 关闭视频时，在放下写锁之前写，与 blob GC 同一时机（[架构设计 §5.2](../../architecture/architecture-design.md#52-写入发布与崩溃一致性)）。
- 保存版本、回到某个版本、BaoCut 代为提交 git 之前，立即写。

所以视频打开期间，磁盘上的快照最多落后 10 秒；没有人打开时，快照等于库里的状态。

- 每次写只重写内容变了的文件：按摘要比较，相同的不碰，保留修改时间。
- 每次写都同时更新当前版本的 diff（§3.1）。
- 不属于项目的视频不写。

### 2.5 链接素材的路径

- **项目内的链接素材**：本来就按相对视频目录的路径记录（[视频格式规范 §4.2](../../spec/video-format-spec.md#42-存储位置)），复制或克隆后照常有效。
- **项目外、用户主目录下的**：写成 `~/` 开头的路径。
- **其余**（外接盘、网络共享）：保留绝对路径。
- 都同时保留文件名、内容摘要与大小，供另一台机器上 `relinkAsset` 找回。
- 推送到远端的快照会带上项目外素材的路径，设置里说明这一点。完全不想带路径时用便携包分享：它把路径换成占位，见[视频格式规范 §8.2](../../spec/video-format-spec.md#82-规则)。

## 3. 版本

### 3.1 版本的边界

每部视频有一个**当前版本**，它是打开的。每次写快照（§2.4）时，VideoEngine 判断这次的改动是并入当前版本，还是开一个新版本。判定在写的那一刻完成，不需要定时器去「封口」一个已经关闭的视频。

满足任一条件就开新版本，当前版本自此封存：

| 条件 | 说明 |
| --- | --- |
| **安静满 5 分钟** | 当前版本最后一次更新距现在超过 5 分钟 |
| **当前版本满 30 分钟** | 一直在改时，30 分钟切一版，一个版本不无限变长 |
| **当前版本是终结的** | 当前版本是保存的版本、一次「回到版本」或一次外部导入，它们各自单独成版 |
| **按回合切分时的新回合** | 频率设为 `turn` 时，智能体新回合的第一次写，由 Runtime 传入标记 |

否则这次改动并入当前版本，重写它的 diff。由此：

- 关闭视频不封存版本。5 分钟内重新打开继续改，改动并入同一个版本。在两三部视频之间来回切换不会切出一串零碎的版本。
- 没有改动不写、不产生版本。
- 回到某个版本、外部导入、保存版本是在当前改动之外单独成版，前面的改动先作为一版封存。

频率设置 `versions.cadence`：`segment`（默认，上表的前三条）或 `turn`（另加第四条）。5 分钟与 30 分钟是可调的产品参数（[文档约定](../../README.md#规范用语)），不是保证。

### 3.2 版本文件

`history/<序号>.patch`，序号是这部视频里递增的 6 位十进制数，不复用。内容是一段头部加一份标准 unified diff：diff 从上一个版本的快照到这个版本结束时的快照，覆盖 `video.json` 与 `documents/` 下的文件，路径相对 `.bcut-snapshot/`。

```text
BaoCut-Version: 12
Kind: segment
Started-At: 2026-10-17T09:41:07Z
Updated-At: 2026-10-17T10:02:55Z
Revisions: 40..57
Summary: 发布会：剪掉 3 处停顿等 14 项
Action: agent:claude | Cut pauses | 3
Action: user_local | Trim clip | 11
Conversation: conv_8f2 | 发布会粗剪
File: video.json sha256:3f1a… sha256:9c0d…
File: documents/doc_5b1.json sha256:7e22… sha256:41b8…

--- a/video.json
+++ b/video.json
@@ -12 +12 @@
-    "itm_…": {"start":…}
+    "itm_…": {"start":…}
```

- **头部的键固定为英文**，每行 `键: 值`，供程序解析。
- **`Kind`** 取值：`segment`（普通一段工作）、`save`（保存的版本）、`restore`（回到版本）、`external`（外部导入）、`rebuild`（重建后的第一版）。
- **`Summary`** 是给人看的一句话，用写入时的界面语言，模板在多语言目录里（[仓库约定 §5](../../repo-conventions.md#5-文案与多语言)）。它由模板拼出，不调用模型。
- **`Action`** 每行一个操作，取自这个修订号范围内的事务：
  - 格式是「执行者 | 标签 | 次数」，同名合并计数，超过 50 行折叠为一行「另有 N 项」。
  - 有 `labelRef` 的写原文标签，界面按当前语言显示；智能体传入的自由文本原样保留。
- **`Conversation`** 列出这一版里改过视频的会话。
- **`File`** 是每个改动文件在这一版之前与之后的 sha256；新建的文件，之前写 `-`；删掉的文件，之后写 `-`。
- 保存的版本还有 `Name` 与可选的 `Note`，以及对应的检查点 ID `Checkpoint`（§3.6）。
- diff 的上下文是 3 行。头部与 diff 之间空一行；`patch` 与 `git apply` 都会跳过 diff 之前的文字，所以在 BaoCut 之外也能用 `patch -R` 逐版退回快照文本。
- 当前版本打开期间，它的文件随每次写快照重写。VideoEngine 在视频打开期间把当前版本开始时的快照文本留在内存里，用来算 diff。

### 3.3 回滚靠 diff，动作用来读

每个版本既有 diff，也有动作清单，但回滚只用 diff：

- **动作不能可靠地反向执行。** 删除操作只凭命令还原不了被删的内容；带涟漪的裁剪、移动依赖当时相邻片段的位置；编辑操作的格式会随引擎版本变化。`video.db` 的撤销记录本来就存的是状态变化（`undo_records.changes`），而不是反向命令，原因相同。
- **diff 自足、可验证。** 有最新快照和一串 diff 就能还原任何保留的版本，每一步都能用摘要核对，不依赖当时的引擎、库或撤销历史。
- **动作清单留给人和智能体读。** 它回答「这一版做了什么、谁做的」，在版本列表里显示，也是智能体理解近期改动的入口。
- 一笔一笔的回滚仍是撤销历史的事（§1.2）。

### 3.4 保留与清理

- **保留数量**：每部视频保留最近 `versions.keep`（默认 10）个未命名的版本，加上全部保存的版本。
- **保留大小**：一部视频的 `history/` 总大小超过 64 MiB 时，从最旧的未命名版本删起，直到降到上限的 90%。整篇转录重新生成的那一版，diff 大约是文档的两倍；只限数量，挡不住这种情况。
- **删掉中间的版本要合并 diff**：删除版本 j 时，在它之后的版本 j+1 的 diff 改为从 j−1 直接到 j+1。做法是还原出两端的文本重新计算。最旧的版本直接删掉文件。这样保存的版本两侧的链始终连续。
- **素材的引用**：保留的版本引用的素材版本与 blob 不被 GC。每个版本写入时，VideoEngine 记下它的快照引用的 blob 摘要，存进库的元数据；`gcBlobs` 的引用集合加上这些摘要（[架构设计 §5.5](../../architecture/architecture-design.md#55-引用图与资源清理)）。这也让「被检查点引用的版本不被 GC」（[视频格式规范 §3.11](../../spec/video-format-spec.md#311-检查点本规范补全)）在版本记录里落实。
- **清理时机**：只在 VideoEngine 写快照时进行，不另起后台任务。

### 3.5 回到某个版本

1. 先按 §2.4 立即写一次快照，手上的改动作为一版封存（§3.1）。
2. VideoEngine 从最新快照开始，按序号从新到旧逐版反向应用 diff，直到目标版本：
   - 每一步要求精确匹配，不做模糊匹配；
   - 每一步按 `File` 行核对摘要。
3. 任何一步对不上，就停下：这一步及更早的版本标为不可用，状态写明从哪一版开始断了。不导入半成品。
4. 还原出的快照按 §4.3 的同一个求差流程，作为**一笔**可撤销的事务应用：
   - 标签「回到版本 <序号>」；
   - 产生一个 `Kind: restore` 的新版本。
5. 目标版本引用的素材如果已经不在：按 §3.4 本不该发生；万一发生，标为缺失。

还可以回到「最旧的保留版本之前」：再反向应用最旧那一版的 diff 即可。

### 3.6 保存版本

用户或智能体可以把当前状态存成一个具名版本。

- 它在库里建一个检查点（[视频格式规范 §3.11](../../spec/video-format-spec.md#311-检查点本规范补全)），在版本记录里是一个钉住的 `Kind: save` 版本，头部写检查点 ID。
- 用户只看到「版本」一个概念：检查点是它在库里的记录，版本文件是它在磁盘上的样子。
- 保存的版本不计入 `versions.keep`，也不被大小上限清理，只能由用户删除。删除时按 §3.4 合并两侧的 diff，并删掉检查点。

## 4. 从快照回到视频

### 4.1 判定

`video.db` 的元数据记两样，它们不属于修订内容，写它们不产生新版本：

- `snapshotRevision`：最后一次写快照时的修订号；
- `snapshotDigest`：那一组快照文件（不含 `history/`）的摘要。摘要按规范化后的文本计算，换行统一成 LF，文件名排序后逐个摘要再整体摘要。

需要判定的时机：

- 打开视频时；
- 打开中的视频的快照有变化时。每部打开的视频单独监视自己的 `video.json` 与 `documents/`，不依赖跳过点目录的递归监视。

判定规则：

| 库领先（当前修订 > `snapshotRevision`） | 快照被改（磁盘摘要 ≠ `snapshotDigest`） | 处理 |
| --- | --- | --- |
| 否 | 否 | 一致，什么也不做 |
| 是 | 否 | 正常：快照还没写，几秒内写 |
| 否 | 是 | **外部改动**：导入（§4.3） |
| 是 | 是 | **冲突**：不自动合并（§4.3） |
| 没有 `video.db` | 有快照 | **重建**（§4.2） |

- VideoEngine 自己写快照也会触发监视。摘要与元数据相同，不做处理。
- 快照解析不了（被手改坏了、有冲突标记）或 `schemaVersion` 高于已知时，不导入、不覆盖。视频按库里的状态照常打开，状态说明快照不可用；下一次写快照之前，先让用户选择保留哪边，不静默覆盖用户的文件。

### 4.2 只有快照：重建

在另一台机器克隆、或者 `video.db` 被删掉时，视频目录里只有 `.bcut-snapshot/`：

- Space 扫描把「有 `.bcut-snapshot/video.json`、没有 `video.db`」的目录列为视频，状态是「待重建」。
- 打开项目时，后台逐个重建，与认领视频同一个预处理流程（[架构设计 §5.1](../../architecture/architecture-design.md#51-存储分层)「打开项目时预处理它的视频」）；用户打开视频时也会触发。
- 重建是 VideoEngine 的新操作 `videos.rebuildFromSnapshot`：
  - 就地创建 `video.db`，**保留快照里的 `videoId`**，之后照常按所属项目认领。同一项目里已有同一个 `videoId` 的目录时按副本处理，分配新标识。这与便携包导入不同：导入要求目标目录不存在，总给新标识。
  - 文档按当前版本导入。
  - 收进来的素材在 `blobs/` 里有就引用，没有就标为缺失。链接素材照常解析，找不到也标为缺失，由用户或智能体 `relinkAsset`。
  - 修订号从 1 开始，撤销历史从重建开始。
- 目录里还有 `history/` 时（例如整个文件夹被拷过来而 `video.db` 丢了），版本记录照常可用：
  - 重建后的第一版是 `Kind: rebuild`，diff 为空；
  - 更早的版本仍可回到。
- 没有 `history/` 时（例如 git 克隆，§5.2），版本记录从重建开始。

### 4.3 快照被外部改了：导入

用户 `git pull`、切换分支、`git checkout -- <path>`，同步盘覆盖了文件，或者手改了快照：

- **只有快照被改**：VideoEngine 的 `videos.applySnapshot` 比较库的当前状态与磁盘上的快照，按实体与文档求差，作为**一笔**事务提交。
  - 事务的标签是「外部变更」，`actor` 是 `system:history`，可撤销。
  - 同时产生一个 `Kind: external` 的版本。它的 diff 从库的导入前状态（即上一份快照）算到磁盘上的新快照，所以本地的版本链不断。
  - 撤销这笔事务后库领先，几秒后快照被写回撤销后的状态，相当于拒绝了这次外部改动。
- **两边都改了**：不导入、不覆盖。视频以库里的状态照常可编辑，状态提示这部视频有冲突，给两个选择：
  - **保留 BaoCut 里的**：下一次写快照覆盖磁盘上的。
  - **用磁盘上的**：按上一条导入。BaoCut 里的改动仍在撤销历史与版本记录里，可以回来。
- 用户没有选择之前，这部视频的快照不被重写。
- 导入后素材缺失的处理同 §4.2。

## 5. git（可选）

BaoCut 不要求 git、不自动 `git init`，也不在后台跑 git，除非用户打开了 §5.3 的自动提交。

### 5.1 随时可以提交

快照的设计让用户什么时候提交都安全：

- **完整**：每个文件原子替换，`video.json` 记着各文档文件的摘要（§2.1）。一个提交里的快照总能重建出一部完整的视频（§4.2）。
- **及时**：视频打开期间快照最多落后 10 秒（§2.4）。要包含刚刚的改动，先保存版本，或者用 BaoCut 的「提交到 git」（§5.3），两者都会先写快照。
- **可读**：行稳定的排版（§2.3）让 `git diff` 与代码托管网站上的对比有意义。
- `video.db` 及其附属文件不能提交：二进制、打开时有一部分最新提交只在 `-wal` 里，而且克隆后由快照重建即可（§4.2）。

### 5.2 忽略与属性规则

项目在一个 git 仓库里时（项目目录是仓库根，或在仓库的子目录里），BaoCut 在打开项目时往仓库的 `info/exclude` 与 `info/attributes` 写入自己的块：

- 块的边界是 `# >>> BaoCut` 与 `# <<< BaoCut`，块外的内容不动。
- 它们是机器本地的，不改用户提交进仓库的 `.gitignore` 与 `.gitattributes`。
- 普通的 `.git` 目录直接写；`.git` 是文件的情况（worktree、子模块）在有 git 时用 `git rev-parse --git-path` 找到位置，没有 git 时跳过。

`info/exclude` 块（注释用英文，与代码字符串的规则一致）：

```gitignore
# BaoCut: machine-local state and rebuildable output
.bcut/
.bcut-trash/
**/video.db
**/video.db-*
**/video.lock
**/movie.db
**/movie.lock
**/blobs/.staging/
**/.bcut-snapshot/history/
.baocut-out/
**/.baocut-out/
**/.baocut-export-*/
.baocut-import-*/
**/.*.partial
**/exports/
```

- **`.bcut/` 不进 git**：项目标识是机器本地的，提交它会在克隆之间来回改。
- **`video.db` 及其 `-wal`、`-shm`、`-journal` 与 `video.lock` 不进 git**。
- **版本文件（`history/`）不进 git**：git 本身就是长期历史。版本文件进了 git，窗口满之后每个提交都在增删补丁文件；两台机器各自产生的同一序号的补丁还会互相覆盖，打断两边的链。版本记录跟着文件夹走（复制、同步盘），git 克隆的新位置从重建开始（§4.2）。
- **导出的成片不进 git**：可以重新导出。

`info/attributes` 块：

```gitattributes
**/.bcut-snapshot/** text eol=lf merge=binary linguist-generated=true
```

- **`eol=lf`**：Windows 上 `core.autocrlf` 不能把快照改成 CRLF。摘要按规范化文本计算（§4.1），即使被改了也不会误判，但 diff 会乱。
- **`merge=binary`**：两边都改了同一部视频的快照时，git 报冲突而不逐行拼接。逐行拼出来的时间线可能是合法 JSON，却是错的剪辑；冲突之后按 §4.3 选一边。
- **`linguist-generated`**：代码托管网站的 diff 默认折叠快照。

用户自己的规则优先：用户忽略了的路径（比如 `blobs/`），BaoCut 提交时不加 `-f`。

### 5.3 BaoCut 代为提交

项目在仓库里、本机有 git 时，BaoCut 提供两种提交：

- **「提交到 git」**：在版本记录面板、CLI 与智能体工具里都有。
- **自动提交**：设置 `versions.git.autoCommit`，默认关。打开后，项目安静满 5 分钟、关闭项目或退出 BaoCut 时提交一次。它只运行 git、只读磁盘上的文件，不需要打开视频。

两种的规则相同：

- **先写快照**：仍在打开中的视频先按 §2.4 立即写一次。
- **提交范围**：只提交 BaoCut 的路径。
  - 有改动的视频的 `.bcut-snapshot/`（不含 `history/`）；
  - 这些视频的 `blobs/` 里小于 `versions.git.maxFileMiB`（默认 50 MiB）、且没被用户规则忽略的条目；
  - 仓库已用 Git LFS 跟踪的路径不受这个大小限制。
- **不碰用户的改动**：项目里的其他文件（脚本、智能体写的代码）由用户自己提交。提交用 `--only`，用户已经暂存的其他改动原样留在暂存区：

  ```text
  git add -- <paths>
  git commit --only -F <message-file> -- <paths>
  ```

- **提交说明**：标题取这段时间里各视频版本的 `Summary`，正文列出各视频的版本序号与动作，尾注的键固定为英文：

  ```text
  BaoCut-Video: <videoId> v<from>..v<to>
  ```

- **作者**：仓库或全局配置了 `user.name` 与 `user.email` 时用用户自己的身份；没配置时用 `BaoCut <baocut@localhost>`，不从系统用户名或主机名拼邮箱。
- **锁**：`index.lock` 存在说明有人在用 git。等 2 秒重试，最多 5 次，仍不行就推迟到下一次，状态里显示「仓库正被占用」。**任何时候都不删锁文件。**
- **仓库的特殊状态**：仓库在合并、变基、拣选、还原或二分中，或 HEAD 处于分离状态时，提交暂停，状态说明原因。用户完成操作后恢复。
- **BaoCut 不做的事**：不 `push`、`fetch`、`pull`、`merge`、`rebase`、`reset`、`checkout`，不 `--amend`，不删分支与标签。
- **初始化**：项目不在仓库里时，项目设置提供「初始化 git」，由用户显式执行，不自动执行。用户主目录、系统的标准用户文件夹（桌面、文稿、下载、影片、音乐、图片，以及 Windows 上对应的已知文件夹）和卷或盘符的根不提供这个动作：在那里建 `.git` 会让下面所有文件夹在其他工具看来都处在一个仓库里。
- **失败不影响编辑**：提交失败只记日志并在状态里显示，从不让编辑、智能体回合或任务失败。

### 5.4 安全

用户可以把任何已有文件夹打开为项目，包括从别处下载的仓库，而 git 会执行仓库本地配置里的命令。产品设计规定打开项目不弹信任确认（[产品设计 §3.2.1](../../product/product-design.md#321-起始状态ux-01)），所以 BaoCut 每次运行 git 都不执行仓库带来的命令：

- **钩子一律不跑**：每次调用都带 `-c core.hooksPath=<BaoCut 的空目录>`，提交再加 `--no-verify`。
- **其余参数**：
  - `-c core.fsmonitor=false`、`-c commit.gpgSign=false`、`-c maintenance.auto=false`、`-c gc.auto=0`；
  - 环境变量 `GIT_TERMINAL_PROMPT=0`；只读查询加 `GIT_OPTIONAL_LOCKS=0`；
  - 提交说明用 `-F` 从文件读，不启动编辑器、不用分页器。
- **执行方式**：参数是数组、不经 shell，在自己的进程组里运行，超时整组终止，与受管外部工具的规则相同（[架构设计 §12.9](../../architecture/architecture-design.md#129-受管外部工具与安装动作)）。
- **本地过滤器**：仓库本地配置里定义了 `filter.<name>.clean|smudge|process`、`include.path` 或 `includeIf` 时，BaoCut 的 git 写操作暂停，状态说明原因，用户显式启用后才继续。
  - 这些过滤器不能一律置空：git-crypt 一类工具靠本地过滤器加密，置空会把明文提交进去。
  - **暂停的范围**：git 在 `status`、`add`、`diff` 与 `commit` 时都可能对有改动的文件运行 clean 过滤器。暂停期间 BaoCut 只运行不读工作区文件内容的命令（`rev-parse`、`config`、`check-ignore`、`check-attr`、`ls-files`），自动提交与「提交到 git」都等待。打开项目、编辑、版本记录与智能体都不受影响。
  - **Git LFS 不算**：本地配置里的 `filter.lfs.*` 与 `git lfs install --local` 写入的值逐字相同时（`clean = git-lfs clean -- %f`；`smudge = git-lfs smudge -- %f` 与 `process = git-lfs filter-process`，或带 `--skip-smudge` 时的 `smudge = git-lfs smudge --skip -- %f` 与 `process = git-lfs filter-process --skip`；`required = true`）不暂停：执行的是用户 PATH 里的 `git-lfs`，不是仓库带来的程序。只认这几个逐字的值，不按模式匹配。
  - **启用**：状态与项目设置列出每一个条目和它要执行的命令，用户点「允许」后继续。启用记在这台电脑的 Runtime Home 里，不写进项目，克隆与复制项目都不带走；记的是这些条目解析后的值与 `include.path`、`includeIf` 指向的文件内容的摘要。每次运行 git 前，本地配置或被包含文件的修改时间变了就重算摘要，摘要变了重新暂停；只改了别的配置（例如 `user.name`）不重新暂停。
  - **谁能启用**：只有桌面界面的项目设置与 CLI。Web 与智能体都不能：启用等于允许在 Runtime 所在的机器上执行仓库配置里写的程序，与安装动作同一类（[架构设计 §12.9](../../architecture/architecture-design.md#129-受管外部工具与安装动作)）。智能体的 `project_git_commit` 遇到暂停时返回原因，下一步是请用户在项目设置里查看并启用。
  - 这不是对文件夹的信任确认：[产品设计 §3.2.1](../../product/product-design.md#321-起始状态ux-01) 规定加入已有文件夹不问是否信任，这里也不弹窗、不拦打开，只在 BaoCut 自己要运行仓库指定的程序之前请用户确认一次。
  - 全局与系统配置里的过滤器照常生效，例如用户全局安装的 Git LFS。
- **不碰网络**：不读取、不传递凭据，不访问网络。

## 6. 界面、多端与智能体

用户可见的部分（实施前先做原型）：

- **版本记录面板**：在编辑器里按视频列出版本，每一项显示序号、时间、摘要、动作清单和改了哪些部分（时间线、哪份文稿）。
  - 选中一个版本可以看它的 diff，或者「回到这个版本」（§3.5）。
  - 不可用的版本标出原因。
- **保存版本**：编辑器与会话里都能把当前状态存成具名版本（§3.6）。
- **冲突与外部变更**：
  - 有冲突时编辑器顶部给出 §4.3 的两个选择；
  - 外部导入在撤销历史与版本记录里各显示为一项「外部变更」。
- **项目设置**：
  - 版本频率（§3.1）；
  - 项目在仓库里时：git 状态（正常、暂停及原因、没有 git）、「提交到 git」、自动提交开关；因本地过滤器暂停时列出条目与命令，给出「允许」（§5.4）；
  - 不在仓库里时：「初始化 git」；
  - 项目外素材路径会进入快照的说明（§2.5）。

多端（[开发流程 §4.1](../../development-workflow.md#41-跨平台系统集成)）：

| | macOS | Windows | Web |
| --- | --- | --- | --- |
| 版本记录 | 全部 | 全部 | 全部：列表、diff、回到版本、保存版本都经 Runtime |
| 需要 git 吗 | 不需要 | 不需要 | 不需要 |
| BaoCut 运行 git 时去哪找 | 登录 shell 的 PATH；`/usr/bin/git` 只在 `xcode-select -p` 成功时用，否则它是会弹出安装开发者工具的占位程序 | PATH 里的 `git.exe`（Git for Windows 的 `cmd\git.exe`）；按 PATHEXT 查找，拒绝 `.cmd`、`.bat` | 不在浏览器里，提交发生在 Runtime 所在的机器上 |
| 路径 | POSIX | 盘符、UNC、`\\?\` 扩展路径交给 git 前按既有转换入口处理；快照与版本文件里的路径一律 `/` 分隔 | 不显示本机路径 |
| 换行 | LF | 快照与版本文件固定 LF；摘要按规范化文本计算 | — |

Web 可以看 git 状态、触发「提交到 git」：提交只运行 git 本身，参数固定（§5.4），只提交 BaoCut 的路径，不跑钩子与本地过滤器，不碰网络，不执行任何仓库带来的程序，所以不按受管外部工具的口径对 Web 关闭（[架构设计 §12.9](../../architecture/architecture-design.md#129-受管外部工具与安装动作)）。Web 不能做的：

- 开关自动提交：`versions.git.autoCommit` 是 Runtime 的偏好设置，Web 不能改设置；
- 「初始化 git」：在本机文件夹里建仓库，与 Web 不能选本机文件夹一致，只在桌面界面与 CLI；
- 启用本地过滤器（§5.4）；
- 「在文件夹中显示」这类本机动作。

智能体：

- **工具**（经 CLI 与 MCP 对外部智能体同样提供，[Agent 能力面设计](../agent-surface/agent-surface-design.md)）：
  - `video_versions`：列出版本与动作清单；
  - `video_version_diff`：读一个版本的 diff；
  - `video_restore_version`：回到版本；
  - `video_save_version`：保存版本；
  - `project_git_commit`：提交到 git，只在用户要求时用。
- **内置 skill 的说明**：
  - 要了解一部视频最近改了什么，读版本记录，不必翻撤销历史；
  - 用户要「回到之前那版」时用回到版本的工具；
  - 不要手改 `.bcut-snapshot/`，也不要在视频打开时 `git checkout` 或 `git reset` 它。

## 7. 实现

### 7.1 VideoEngine

- **快照投影与序列化**：在 `VideoState::snapshot` 之上加投影（§2.2）与行稳定序列化器（§2.3），放在 `crates/video-engine`。便携包仍用原来的快照，两者共用投影前的部分。
- **diff**：
  - 行级 Myers diff，输出标准 unified diff；
  - 反向应用要求精确匹配；
  - 用 Rust 实现或选一个维护中的 crate，依赖进 `Cargo.lock`。
- **`videos.writeSnapshot { path, boundary?, meta }`**：持有写锁时调用。
  - 写 §2.1 的文件，按 §3.1 判定并入当前版本还是开新版本，按 §3.4 清理；
  - 更新元数据里的 `snapshotRevision`、`snapshotDigest` 与各版本引用的 blob 摘要；
  - `boundary` 是 `save | turn | restore | external`；`meta` 是 Runtime 组织的 `Summary` 与会话列表，动作清单由引擎从自己的事务表取。
- **`videos.restoreVersion { path, version }`**：按 §3.5 还原并应用，一笔事务。
- **`videos.applySnapshot { path, snapshotDir }`**：
  - 按实体与文档求差，作为一笔带撤销记录的事务提交，用于外部导入（§4.3）；
  - `snapshotDir` 可以是临时目录。
- **`videos.rebuildFromSnapshot { path }`**：就地建库（§4.2）。`snapshotDigest` 取自读入的文件，不取自重新生成的文本，往返不变（§2.3）由测试保证。
- **`videos.snapshotStatus { path }`**：返回 §4.1 判定需要的修订号与摘要，只读，不取锁。
- **GC**：`gcBlobs` 的引用集合加上保留版本引用的 blob（§3.4）。

### 7.2 Runtime

- **调度**：
  - 每部打开的视频有一个去抖计时器（§2.4），到时调用 `videos.writeSnapshot`；
  - 保存版本、回到版本与提交到 git 之前立即调用；
  - 频率为 `turn` 时，在 Harness 回合开始后的第一次写传 `boundary: 'turn'`。
  - 输入来自 `VideoService.onChange`，它的语义是「修订变了」，用来重置计时器。
- **监视**：打开中的视频监视各自的 `video.json` 与 `documents/`，按 §4.1 判定。
- **Space**：扫描识别「待重建」的视频目录（§4.2），交给项目打开时的预处理。
- **git 桥**（可选）：
  - 查找 git：只检测、不下载，加进受管外部工具的登记表，与 ffmpeg 相同（[架构设计 §12.9](../../architecture/architecture-design.md#129-受管外部工具与安装动作)）。顺序是环境变量 `BAOCUT_GIT`、用户指定的路径、系统 PATH，版本 ≥ 2.30。
  - 写 `info/*` 块（§5.2）；
  - 「提交到 git」与自动提交（§5.3），带 §5.4 的参数；
  - 用系统的 git 命令行，不内嵌 git 库：忽略规则、属性、LFS、`safe.directory` 与锁的行为都与用户自己的 git 一致。
- **摘要文案**：`Summary` 的模板与动作标签的显示走多语言目录。

### 7.3 协议与设置

- **方法**：
  - `videos.versions.list { videoId, limit? }`
  - `videos.versions.get { videoId, version }`：头部与 diff 文本
  - `videos.versions.save { videoId, name, note? }`
  - `videos.versions.restore { videoId, version }`
  - `videos.versions.delete { videoId, version }`：只删保存的版本
  - `videos.versions.resolve { videoId, keep: 'video' | 'snapshot' }`
  - `projects.git.status { projectId }`
  - `projects.git.init { projectId }`
  - `projects.git.commit { projectId, message? }`
  - 视频主题推送版本列表的变化，`projects.git` 状态随项目主题推送。
- **设置**（[架构设计 §5.10](../../architecture/architecture-design.md#510-偏好设置)）：
  - `versions.keep`（默认 10）
  - `versions.cadence`（`segment` | `turn`，默认 `segment`）
  - `versions.git.autoCommit`（默认 `false`）
  - `versions.git.maxFileMiB`（默认 50）
  - 项目级的覆盖值记在项目登记里。
- **错误码**：
  - `VERSION_NOT_FOUND`
  - `VERSION_CHAIN_BROKEN`（带断开的序号）
  - `SNAPSHOT_CONFLICT`
  - `SNAPSHOT_INVALID`
  - `GIT_UNAVAILABLE`
  - `GIT_PAUSED`（带原因：`locked`、`repo-state`、`local-config`）
  - `GIT_INIT_REFUSED`（主目录等位置）

### 7.4 体量

按本机现有视频的实测：

- 一部 6 MB 的 `video.db` 里，`document_versions` 占 5.69 MB（9 个版本），其中一份转录有 5 个版本，每个约 950 KB；实体只有约 10 KB。
- 这部视频的最新快照只有各文档的当前版本，约 1–2 MB 文本。
- 一个只改了几处的版本，diff 只有改动的行加上下文，通常几 KB 到几十 KB。10 个这样的版本远小于 1 MB。
- 整篇转录重新生成的版本约 2 MB。64 MiB 的上限（§3.4）能容下几十个这样的版本。
- 现有视频最多的有 37 笔事务。按 §3.1 合并后，这样一次编辑大约是 2–4 个版本。

## 8. 例子：已有仓库 baoyu-video

`baoyu-video` 是用户自己的仓库：

- 代码合成的源码在 `scenes/` 下，用 `compositions import <videoId> --path scenes/out/<seg>` 导入视频；
- 视频在一块外接盘上；
- 仓库已经忽略了 `.bcut/`、`video.db*`、`video.lock`、`blobs/` 和 `**/export/**`。

BaoCut 在这里的行为：

- **版本记录**：每部视频照常有最新快照与最近版本，跟 git 无关。
- **git**：
  - BaoCut 往 `.git/info/exclude` 补自己的块，其中 `**/exports/` 覆盖了用户规则没覆盖的复数形式，`**/.bcut-snapshot/history/` 让版本文件不进 git。
  - 各视频的 `.bcut-snapshot/` 在 `git status` 里显示为新文件，用户想什么时候提交都行，或者用「提交到 git」只提交它们。
  - `scenes/` 的代码照旧由用户自己提交。
- **素材**：`blobs/` 被用户忽略，BaoCut 不强行提交，克隆后收进来的素材缺失。外接盘上的链接素材在快照里是绝对路径（§2.5），另一台机器上标为缺失，挂上同名盘或重新链接后恢复。
- **大文件**：这个仓库的 `.git` 有 413 MB、19 个提交，大头是同一套约 12 MB 的字体被反复提交了六次。它们是用户自己提交的，BaoCut 不碰；BaoCut 代为提交时有大小门槛（§5.3）。

## 9. 分期与验收要点

| 期 | 内容 |
| --- | --- |
| 一期 | 快照的投影、序列化与写入（§2）；版本的边界、版本文件、保留与清理、GC 引用（§3.1–§3.4）；回到版本与保存版本（§3.5、§3.6）；从快照重建（§4.2）；协议、设置与智能体工具 |
| 二期 | 外部改动的导入与冲突（§4.3）；版本记录面板（已做，§12.4）、冲突提示等界面（先做原型）；git 桥：`info/*` 块、「提交到 git」、初始化、自动提交、安全参数（§5） |
| 三期 | 待评审事项里通过的扩展，例如幻灯片、文档、设计稿纳入版本记录 |

验收要点（实施时写进[验收与测试](../../acceptance/acceptance-spec.md)）：

- 同一状态两次写快照逐字节相同；改一个片段只改一行。
- 随机编辑序列下，回到第 k 版得到的快照与当时写出的快照逐字节相同。
- 篡改一个中间版本文件后，回到它之前的版本被拒绝并报告断点，视频不变。
- 3 个回合和 20 笔手工编辑之间没有超过 5 分钟的停顿，只产生 1 个版本，动作清单列全；在两部视频之间来回切换不产生额外版本。
- 版本数超过 10 时删最旧的未命名版本，保存的版本保留，链保持连续。
- 被保留版本引用的 blob 在关闭视频的 GC 之后仍在，回到该版本时素材完整。
- 删除 `video.db` 后重新打开项目，视频按快照重建，`videoId` 不变，版本记录仍可用。
- 对各种视频（含代码包、多语言文稿、链接与收进来的素材），重建或导入之后立即写出的快照与读入的逐字节相同。
- 关着的视频的快照被 `git pull` 改了，打开时导入为一笔「外部变更」和一个 `external` 版本；撤销后回到原状态。
- 没有 git 时版本记录的全部功能可用。
- 有 git 时，「提交到 git」不带走用户已暂存的无关文件，`index.lock` 存在时不提交、不删锁；本地过滤器存在时提交暂停，查状态与提交都没有执行过滤器；`git lfs install --local` 写入的标准条目不暂停；启用后只改 `user.name` 不重新暂停，改了过滤器的命令重新暂停。
- Windows 上 `core.autocrlf=true` 时检出快照不被误判为外部改动。

### 12.1 一期

实现与本文不同的地方：

- **投影**（§2.2）：`video.json` 是实体的扁平投影，按种类、按 ID 排开，不是 `VideoSnapshot` 的嵌套形式。
  - 实体原样写：实体里本来就没有每次提交都变的计数，不另去掉时间字段。
  - 素材记录整条保留，含全部素材版本。
  - 检查点与保护都不写。
  - 文件头多了 `timeContractVersion`，没有 `name`：名字在 `video` 实体里。
- **读快照**要求三个格式版本都等于读的一方支持的版本，更旧的也拒绝。旧快照怎么迁移待定。
- **第一次写只写基线**：打开视频时立即写一次，之后的第一笔修改成为版本 1。重建时没有版本文件也只写基线。
- **头部的文字**：
  - `Summary` 写英文缺省文字，另加 `Summary-Ref`（多语言引用），界面按当前语言显示，不按写入时的界面语言写。
  - 动作标签同样写英文缺省文字，另加 `Action-Ref`。
  - 超过 50 行的动作写成 `Actions-Omitted: N`，不写成一行「另有 N 项」。
- **打开着的版本旁边有 `<序号>.base`**，是这一版开始时的快照，代替「留在内存里」（§3.2）：崩溃后也能重算 diff。
- **簿记**多了三项：`snapshotFiles` 是逐个文件的摘要，外部改动按它判断；`snapshotPending` 用于两段式写入；`versionsNext` 是下一个序号。
- **GC 引用**不存进库的元数据：GC 时扫描快照、版本文件与起点文件里出现的摘要。
- **保留**：`keep` 计入最新一版，最新一版总是留着。删除中间的版本时，版本链对不上就不删。
- **回到版本**：
  - 多了 `before`，回到这一版开始之前，代替单独的「最旧版本之前」。标签是「回到版本 N」「回到版本 N 之前」。
  - 结果与当前状态相同时不提交，也不产生版本。
  - 智能体调用时检查任务的保护范围。
  - 检查点与保护保持现状。
- **删除保存的版本**：它是最新一版时，变回普通的一段。
- **写入方法带 `commandId`**（保存、回到、删除），重试返回第一次的结果。
- **方法**：多了 `videos.versions.status`；`videos.versions.resolve` 随外部导入放到二期。视频主题不推送版本的变化。
- **引擎命令**（§7.1）：
  - 命令是 `videos.writeSnapshot { videoId, boundary?, conversations?, keep? }`、`listVersions`、`readVersion`、`snapshotStatus { path }`、`restoreVersion`、`saveVersion`、`deleteVersion` 与 `rebuildFromSnapshot { path, keep? }`。
  - `boundary` 只有 `turn`；保存与回到版本由引擎自己单独成版。
  - 摘要与动作清单都由引擎生成，Runtime 只交会话列表。
- **回合**由 Harness 的任务主题推断：出现新的运行中任务就是新回合。
- **不属于项目的视频**：除了不写（§2.4），保存、回到与删除版本都以 `VERSIONS_NEED_PROJECT` 拒绝。
- **智能体工具**用 `videos_` 前缀：`videos_versions`、`videos_version_diff`（长 diff 用 `offset` 分页）、`videos_save_version`、`videos_restore_version`。没有删除版本的工具。
- **重建**：同一项目里两个目录重建出同一个 `videoId` 时，不单独换标识，按打开时的既有规则保留先打开的那一个。
- **监视**（§4.1）一期没有做，外部改动只报告、不覆盖；二期补上，见 §12.2。

### 12.2 二期：外部改动的导入

规则在[视频格式规范 §9.8](../../spec/video-format-spec.md#98-外部改动)。冲突提示与选择的界面见 §12.4。实现与本文不同的地方：

- **状态**：`videos.versions.status` 多了 `external`（只有快照被改，Runtime 会导入）；`conflict` 带原因 `conflict`，是 `both-changed` 或 `invalid`。磁盘上的快照恰好等于库里的状态时（中断的写或导入之后）不算外部改动，状态是 `pending`。
- **「库领先」按内容判断**（§4.1 的表）：当前状态的投影与上次写下的快照文件不同才算，不比修订号。只建检查点这类不进快照的修改不算两边都改了。
- **快照读不出**（§4.1 末条）归为 `conflict`（`invalid`），只能保留 BaoCut 里的；选用磁盘上的以 `SNAPSHOT_INVALID` 拒绝。
- **`videos.versions.resolve` 带 `commandId`**，返回 `{ receipt, replayed, version, status }`，同一个 `commandId` 重试返回第一次的结果。Web 与其他写入方法一样按写入归类。
- **保留 BaoCut 里的**是立即写快照、覆盖磁盘上的，不等「下一次写快照」（§4.3）；按效果幂等。
- **用磁盘上的**：BaoCut 里还没写进快照的改动先封存成一版（只写版本文件，不动磁盘上的快照），`external` 版本从它结束时算起，回到 `external` 版本之前就能找回它们。这是 §4.3「仍在版本记录里」的做法。还没有任何版本时不另封存，`external` 版本直接从库里的状态算起。
- **撤销导入**：撤销按操作者分开，调用者的「撤销」撤不到 `system:history` 的这笔，要用 `edits.undo` 的 `target: { transaction }` 指定它。撤销后写回的快照是普通的一段。
- **只差排版**、内容没变时不提交、不产生版本，只写回规范的文本。
- **引擎命令**：`videos.applySnapshot { videoId, commandId, actor, force?, keep? }` 只读视频目录里的快照，没有 `snapshotDir`（§7.1）；`force` 对应「用磁盘上的」。`videos.writeSnapshot` 多了 `overwrite`。`boundary` 不加 `external`：导入由引擎自己单独成版。
- **监视**（§4.1、§7.2）：每部打开的视频用一个递归的 `fs.watch` 监视自己的 `.bcut-snapshot/`，跳过 `history/` 与点开头的临时文件，去抖 300 毫秒后调 `videos.applySnapshot`。打开时立即的那次写报 `SNAPSHOT_CONFLICT` 时同样调它，所以关着时的 `git pull` 在打开时导入。
- **智能体没有选择去留的工具**（§6 没有列，这里明确）：选哪边都会丢掉一边的工作，由用户决定。`videos_versions` 报告 `external`、`conflict` 与原因，`SNAPSHOT_CONFLICT` 的下一步提示让智能体转告用户；内置 skill 同样这样说明。

### 12.3 二期：git 桥

后端、协议、CLI 与智能体工具已实现，规则在[架构设计 §5.12](../../architecture/architecture-design.md#512-视频的版本记录)的「git 桥」。界面（项目设置里的 git 一节、「提交到 git」按钮）没有做，先做原型。实现与本文不同的地方：

- **方法**：多了 `projects.git.allowLocalConfig { projectId, digest }`，就是 §5.4 的「允许」；`digest` 是用户看过的那组条目的摘要，与此刻的不同时以 `GIT_PAUSED`（`local-config`）拒绝，免得允许了没看过的条目。`projects.git` 的状态不随项目主题推送，界面按需查。新增错误码 `GIT_FAILED`（git 自己运行失败，`internal`）；`GIT_UNAVAILABLE` 的 `details.reason` 分 `missing`（没有能用的 git）与 `not-repo`（项目不在仓库里）。
- **CLI 与智能体**：工具叫 `projects_git_commit`（不是 `project_git_commit`），沿用 `<名词>_<动词>` 的命名，CLI 是 `baocut projects git-commit`。它在 BaoCut 自己的会话与 CLI 里，MCP 上没有：对外服务的访问范围可以只是几部视频，提交却作用于整个项目与用户的仓库，与 `projects_create` 同样处理。查看状态、初始化与允许过滤器是 CLI 的管理命令 `baocut projects git-status|git-init|git-allow`，不进工具目录。
- **补救的指向**：界面没做之前，「初始化 git」与「允许」的补救文字与智能体的下一步都指向 CLI（`baocut projects git-init`、`baocut projects git-allow`），不指向项目设置。智能体遇到没有仓库时同样不替用户初始化，结果里是 `unavailable`（与 `paused` 并列）。
- **「关闭项目」**按项目最后一部打开的视频关闭算：Runtime 没有单独的关闭项目。自动提交由打开中的视频的修改触发；关着的视频不会有新改动，提交时仍按 `git ls-files` 把项目里所有视频的快照算进来。
- **提交说明的标题**：版本的名字优先于摘要，多个用分号连接，至多 72 个字；都没有时是「BaoCut：更新 <视频名>」，按 Runtime 的语言。正文按视频列出版本序号与名字或摘要，不列动作。版本范围从上一次提交的尾注 `BaoCut-Video` 接着算；找不到尾注时按上一次提交的时间。
- **提交范围**：删掉或移走的视频，它在仓库里的旧快照不由 BaoCut 删除，留给用户自己提交。`blobs/` 里有改动、且超过大小上限又没被 LFS 跟踪的条目跳过，不报错。
- **安全参数**比 §5.4 多：`tag.gpgSign=false`、`submodule.recurse=false`、`diff.ignoreSubmodules=all`、`log.showSignature=false`、`core.editor=:`、`core.pager=cat`，`core.askPass` 与 `credential.helper` 置空，`protocol.allow=never`；环境去掉会把命令指到别处的 `GIT_*` 与 `EMAIL`，另设 `GCM_INTERACTIVE=never` 与 `LC_ALL=C`；路径一律带 `--literal-pathspecs`。
- **暂停期间运行的命令**比 §5.4 列的更少：只有 `rev-parse`、`config` 与 `symbolic-ref`（读分支名），不运行 `check-ignore`、`check-attr` 与 `ls-files`。
- **摘要每次重算**，不看修改时间（§5.4）：本地配置与被包含的文件都小，按修改时间判断反而会漏掉同一秒里的改动。
- **`info/*` 的块**除了打开项目时，也在这次运行里项目第一次有改动时与每次提交之前写，没变时不重写；找不到 git 时只认 `.git` 目录，遇到 worktree 与子模块的 `.git` 文件跳过。
- **初始化的拒绝名单**：Windows 上按用户主目录下的标准文件夹名判断，被重定向到别处的已知文件夹（例如 OneDrive 里的「文稿」）没有解析。
- **找 git**：环境变量是 `BAOCUT_GIT`；macOS 上判断 `/usr/bin/git` 能不能用时运行 `xcode-select -p`，失败就跳过它、接着在 PATH 里往后找（例如 Homebrew 的 git）。
- **换行**：快照 `eol=lf` 的效果由真实的 git 测试核对（`core.autocrlf=true` 时进仓库的仍是 LF）；读快照时把 CRLF 当作 LF 是外部改动的导入那部分做的（§12.2）。
- **项目级的设置**（§7.3 的覆盖值）没有做：两个设置都是 Runtime 级的。

### 12.4 二期：版本记录面板

版本记录面板已实现，桌面端与 Web 共用一套界面，规则见[产品设计 §5.1](../../product/product-design.md#51-一套编辑器两个入口)。与 §6 不同或还没做的地方：

- **按钮**：视频栏原来的撤销历史按钮改叫「修订 N」、换成撤销图标，与「版本 N」分开；版本记录是旁边一个只有图标的按钮。
- **刷新**：视频主题不推送版本的变化（§12.1）。按钮在修订停下约 11 秒后读一次状态，窗口回到前台、Runtime 导入了外部改动时也读一次；对话框打开时读一次，修订变了再读，状态是「正在写入」或「正在导入外部改动」时每 3 秒读一次，直到结束。所以 BaoCut 里没有新修改时，快照被改坏、或在 BaoCut 写快照之前就被外部改了这类只在磁盘上发生的冲突，要等窗口回到前台或下一次修改才出现。
- **冲突**：对话框头上写原因（两边都改了、快照读不出）与被改过的文件，给 §4.3 的两个选择（`videos.versions.resolve`），快照读不出时只有「保留 BaoCut 里的」；停用保存与回到版本，按钮上加一个圆点。编辑器顶部另有一条，只在冲突时出现，「查看」打开版本记录，另外两个按钮直接选。
  - 两个选择都先确认，写明各自丢掉什么。「保留 BaoCut 里的」是危险的确认，按钮是「覆盖磁盘上的」，立即写快照（§12.2）。「用磁盘上的」的确认不写本地有几项修改、并进哪一版：界面没有这两个数，只说本地改动先记进版本记录；结果给撤销（按事务撤销那笔「外部变更」）。
  - 对话框里的结果写成对话框里的提示；编辑器顶部那一条的结果是 toast，只有标题。
  - 圆点是 S2 的强调色，原型是红色。
- **外部改动**：状态 `external`（只有快照被改、Runtime 正在导入）写「正在导入外部改动」与被改过的文件，期间停用保存与回到版本；还开着的最新一版另说明它会先收口。Runtime 自己导入后，对话框开着时在对话框里说，关着时弹 toast，都给撤销；自己选的「用磁盘上的」不再说一遍。「外部变更」版本的详情说明它来自 BaoCut 之外、回到它之前就是导入前的内容。
- **会话**：在这台电脑上的会话点开后关掉对话框、切到这条会话，Web 也可以；不在的写明「不在这台电脑上」。
- **diff** 一次最多显示 1500 行，其余复制后看；没有改动文件的版本（保存）不读 diff。
- **Space 不显示「待重建」**：Space 的条目没有这一项，而打开项目或视频时 Runtime 就从快照重建了（架构设计 §5.7）。
- **项目设置**（版本频率、git）没有做；git 桥的界面见 §12.3。
