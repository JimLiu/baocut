## 1. 定位与原则

### 1.1 用户得到什么

EmbeddingGemma 2 不写一个字、不剪一刀。它做的只有一件事：**决定文本模型、编辑器和用户看到哪一部分素材**。所以用户能感知到的收益不是"多了一个 AI 功能"，而是现有功能变得：

| 收益 | 现在的痛点 | 有了本地语义索引之后 |
| --- | --- | --- |
| **找得到** | 记不住原话就搜不到；没字幕的画面与声音完全搜不到 | 用自己的话描述就能找到；画面与声音也可以找（v0.1） |
| **写得准、能追溯** | 写博客、写总结把整篇文稿塞给模型，长视频被截断或漏掉；写出来的话查不到出处 | 按主题选材；每一段都带出处，点一下回到视频那一句 |
| **改得快** | 改一段要重跑整篇，等待久、费用高 | 只取相关证据重写一段，其余不动 |
| **本地、便宜** | 每次都把全文发给云端模型 | 选材在本机完成，发给云端的只有相关部分；云端用量账本里看得见省了多少 |
| **跨视频复用** | 术语、译法、品牌素材每个视频重来一遍 | 译过的句子、纠过的术语、用过的素材在新视频里被主动找出来 |

### 1.2 原则〔G〕

- **候选不是决定**。语义相似度只产出候选与排序；写进视频的每一笔仍走编辑事务、保留撤销，删除类操作永不自动执行（v0.1 §12.3、§15.3）。
- **出处是硬约束**。凡是由检索选材后生成的文字，必须能回到原句；没有锚点的内容在界面上标为"模型推断"，不与转录原话混在一起（v0.1 §15.2）。
- **不装模型照常工作**。每个接入语义能力的功能都必须有不依赖索引的路径，且结果形状相同；界面说明走的是哪条路，不把"没有索引"伪装成"没有相关内容"。
- **派生、可删、可重建**。向量与索引是派生缓存，不是真源；不随成片导出，不同步云端（v0.1 §1.2、§17）。
- **外发沿用既有授权**。本机检索不是数据外发；把命中片段发给云端文本模型才是，走现有的外发授权与用量账本（产品设计 §7.2、§7.3），不因为"只发了一部分"而跳过。
- **不假定语言**。查询、文稿、译文可以是任何语言；跨语言是语义索引的常规用法，不是特例。

### 1.3 不做什么

本文不做：训练或微调、"爆款预测"、人脸与说话人身份识别、自动删除、全自动发布。也不把 embedding 当问答模型：所有生成仍由已配置的文本模型完成。

## 2. 产品设计：按用户的时刻

每一节按同一结构写：用户在做什么、界面上多了什么、没装模型时是什么样、明确不做什么。入口放置遵循产品设计 §5.10：工具定义一次，从 AI 工具 Tab、对话、所在面板与智能体四处用到。

### 2.1 找片段

**P0。** 沿用 v0.1 §13：Space 搜索加"综合 / 精确文字"模式、"讲话内容 / 画面 / 声音"通道与范围；结果卡带原文、锚点、命中通道与索引状态；点击预览，选中后转为可编辑候选或子视频。编辑器里的"查找片段"与"给这句话找配套画面"是同一服务的两个入口。

本文只补一条：**搜索结果可以直接"喂"给写作与对话**。结果卡上的"交给 Agent"把选中的若干命中作为引用带进会话（产品设计 §4.7），"用于写作"则把它们作为预选材料打开写作工具（§2.2）。用户先找、再写，是最自然的创作顺序。

命中原因与那一刻（2026-10-13，原型与两端已实现）：每条命中左边放命中那一刻的画面，下面一句写为什么命中——字面对上的写出原句里对上的词（「说到了「确定性」，意思也对得上」，最多三个、去重），只按意思找到的写「意思接近，原句里没有这些字」，弱命中写只是勉强相关；不编概念名（向量说不出因为什么才近），不写分数；章节命中的是标题、不是讲出来的话，不挂「讲话内容」、不写「说到了」，只写字面或意思对上。点命中打开预览，放命中那一句前后各 2 秒（命中的部分在播放条上标出），「在时间线打开」才去打开视频（沿用原来的跳转与重新解析）。原型见 `model-space-search.js` 的 `why`、`moment` 与 `space-search.jsx` 的 `Moment`。实现：Runtime 的 `space.hitMoments { entryId, spans }`（只读，Web 白名单内）按视频当前的工作稿读一次内容（不打开视频、不取写锁），时间线秒的命中取那一秒看得见的视频片段（叠在上面的可见轨道优先，同封面与预览的取法），源时间的命中取文稿对应的素材（译文看它译自的文稿），每处给一张 320 px 的小图与要播的素材区间；播放走 `media.resolve { entryId, assetId, revision }`（视频条目里的素材版本，同样不打开视频）再经 `media.playback`。与原型的出入：Electron 与 Web 的命中是按视频分组的列表，小图放在行首，不是卡片网格；预览播的是素材原片，没有时间线上的剪辑、字幕与叠加，前后 2 秒不跨出命中所在的片段（靠近剪口时会短一些）；预览里只有命中这一句，没有原型的前后各一句（命中里不带上下文，要再读文稿）；定格片段与没有画面的素材（纯音频）只给画面或什么都不给，写「这一刻没有可播放的画面」；视频在建索引之后改过时写位置可能有偏差。

### 2.2 写总结、写博客、起标题、写简介

**P0（选材与出处）、P1（局部改写与系列文章）。**

**用户在做什么。** 一小时的访谈要写成一篇博客；一个系列的五期要写一篇综述；写完之后想把第三节展开。

**现在的问题。** 写作工具（产品设计 §5.10）把所选范围的文稿整段发给模型：长视频超出上下文被截断，模型"自己挑"重点时漏掉用户在意的部分；写出来的段落无法回到视频里核对。

**有了语义索引之后：**

1. **按主题选材，不按时间切。** 参数页的「范围」行在"整篇 / 某一章 / 带来的段落"之外多一项**「按主题」**：用户在提示词里写的意图句（例如"写一篇讲我们怎么做模型选型的博客"）本身就是查询；Runtime 先在这部视频（或所选的几部）里找出相关句群，按时间顺序排好，再连同它们的章节标题发给模型。参数页里"发给模型的"一行照样写清：「提示词 + 文稿 12 段（按主题挑选，覆盖 3 章）· 章节 N · Skill …」，并给「查看挑选的段落」，用户可以勾掉或加回。
2. **每一段带出处。** 生成结果里的每个段落（或要点）附带它依据的原句锚点。结果页里出处显示为可点的时间码；点一下，预览跳到那一句、文稿面板高亮该句。拷走 Markdown 时出处按用户选择保留为时间码或去掉。没有锚点支撑的句子标成「模型推断」。
3. **这段不对。** 结果页的段落菜单：「看出处」「重写这一段」「换材料重写」。重写这一段只重新检索这一段对应的主题、只重生成这一段，其余段落不动；换材料重写打开"挑选的段落"让用户改勾。这是用户改稿时最省时间的一步。
4. **系列文章。** 范围可以选同一项目里的多部视频（Space 选择器，只列有文稿的）：选材跨视频进行，出处带视频名。结果仍是一个文档条目。
5. **起标题与写简介**用同一套选材：简介生成时附带视频的章节与高相关句群，而不是前三分钟；标题候选可以标注"来自第 12:30 的说法"，用户一眼知道标题有没有根据。

**没装模型时。**「按主题」一项置灰，并写明"需要本机语义模型"，给设置入口；其余范围照常。出处功能不依赖语义模型：只要发给模型的是带编号的句子，模型就能回引编号（§3.4），所以 P0 的出处在无模型时也应可用，只是选材退回整篇或章节。

**不做什么。** 不替用户决定观点，不改用户在提示词里写的意图句；选材只决定"模型看到什么"，不删改原文。

### 2.3 关键帧插图

**P1。**

**现在的问题。** 写博客的「添加关键帧插图」只在交给智能体时可用；直接调模型"拿不到画面"而置灰（产品设计 §5.10）。

**有了视觉索引之后。** 这项在两条路径下都可用：Runtime 用段落文字在这部视频的视觉索引里找最贴近的关键帧（限定在该段出处所在的时间附近，优先；其次全片），插进正文对应位置。每张插图带源时间；用户在结果页可以「换一张」（列出同一时间附近的其他候选帧）或「去掉」。

**没装多模态模型时。** 退回"按出处时间取帧"：每段的第一处锚点取一帧，不做语义匹配；页面写明"按时间取帧，未按内容挑选"。

**不做什么。** 不用模型识别画面里的小字（v0.1 §6.2）；不为了插图改写正文。

### 2.4 生成章节

**P1。**

**现在。** 生成章节整篇发给文本模型，由模型同时决定边界与标题；长视频切分不稳，重跑一次结果可能完全不同。

**之后。** 本机先按相邻句群的语义距离找出话题转折的候选边界（§3.6），文本模型只在候选基础上合并、命名并写一句简介。用户看到的变化：章节边界更稳定、与讲话内容的转折一致；重跑只换标题不换边界；长视频不再被截断。参数页多一行「边界：按话题自动检测 / 由模型决定」。

**没装模型时。** 退回现在的做法。

### 2.5 润色与术语表

**P1。**

**用户在做什么。** 转录把产品名、人名听错了，一篇里错了七处，还各不相同；用户库里的术语表（架构设计 §5.9）只在转写提示里起作用。

**之后。**

- **术语候选。** 润色参数页多一个勾选项「按术语表找疑似误听」：对术语表里的每个条目，在文稿里找语义或发音相近但写法不同的片段，列成候选表（原文、建议、出现位置、出现次数），用户勾选后一次替换；全部可撤销。不自动应用。
- **反向：从文稿发现术语。** 文稿里反复出现、写法不一致的专有名词，提示「加入术语表」。这是让术语表自己长出来的入口，之后的每部视频都受益。

**没装模型时。** 术语候选只按精确与常见误听写法匹配（现有术语表的 `misheard` 列表）；页面写明只做了精确匹配。

### 2.6 翻译与配音：翻译记忆

**P1。**

**用户在做什么。** 系列视频每期开头结尾相同，口头禅与术语相同；每期翻译都重新译一遍，译法还不一致。

**之后。**

- **翻译记忆。** 翻译字幕时，Runtime 在用户已有的译文（同一语言方向、所有已索引视频）里找与当前句语义几乎相同的句子，把它们的既有译法作为参考附给翻译模型；参数页写明「参考了 N 句已有译文」。完全相同或只差标点的句子可以直接复用（标为「沿用」），用户在字幕面板能看出哪些是沿用的，可以逐句改为重译。
- **术语一致。** 译文里同一术语前后不一致时，字幕面板的统计条多一项「N 处术语不一致」，点开列出位置，可以一键统一到术语表里的译法。
- **配音不变。** 翻译记忆只改译文来源，配音流程不变；沿用的译文与重译的译文在配音里没有区别。

**没装模型时。** 翻译记忆只做精确匹配（相同原文），其余照常。

**不做什么。** 不跨用户共享翻译记忆；不把其他语言方向的译文混入。

### 2.7 剪口播：重录与重复

**P1。**

**用户在做什么。**「找可剪的口」已能找口头禅与长停顿；但"同一句话录了三遍，哪一遍该留"仍要手动听。

**之后。**「找可剪的口」多一类候选：**重录**。本机找出相邻且语义几乎相同的句群（§3.8），成组列出：每组显示各遍的原文、时长、是否完整，默认建议保留最后一遍或最完整的一遍；用户逐组确认；确认后像其他可剪的口一样提交为一笔编辑、可撤销。**特别检查**：数字、否定词、专有名词不同的两遍不算重复，列在「相似但有差异」里让用户看差异。

**没装模型时。** 重录候选只按完全相同的文字找。

**不做什么。** 永不自动删除；不判断"哪一遍讲得好"，只判断"是不是同一句"。

### 2.8 短视频与补充画面

**P1 / P2。** 按 v0.1 §14 与 §15.1：剪成短视频用语义检索加速选题，补充画面（B-roll）用视觉检索给候选提案。本文只定两条产品规则：

- 剪成短视频的参数页允许写一句**主题**（"讲模型选型的部分"），由检索圈定候选段落再交智能体判断；不写主题时仍走全片分析。
- 补充画面的提案 Artifact 在编辑器里以候选卡出现（预览、画幅警告、来源），用户选择后再插入，默认不覆盖原声。

### 2.9 智能体：按需取材与跨视频问答

**P0（按需取材）、P1（跨视频问答）。**

**现在。** 智能体按范围读取文稿（架构设计 §3.7）；要找"讲到定价的那段"只能全文翻或靠 `speech.search` 的子串匹配。视频记忆（产品设计 §6.4）是整份附上。

**之后。**

- **按意图取材。** 智能体多一个工具（§3.9）：给一句意图，返回这部视频（或项目）里相关的句群与锚点。它取代"先读全文再找"，上下文更小、更准、更便宜；任务卡片上的"读取了什么"写出"按主题读取 12 段"。
- **记忆按需召回。** 视频记忆按条目索引；任务开始时只附与本次任务相关的记忆条目，其余按需召回。用户仍可查看与删除全部记忆。
- **跨视频问答。**（v0.1 §15.2）在无项目会话或 Space 里问"我哪一期讲过 X"，回答附来源视频与时间；覆盖不完整时说明。回答的每一句引用都是可点的。会话里的智能体平时只看本会话来源目录里的视频（架构设计 §3.5），所以从 Space 发起的问答由用户给会话一个只读检索范围（全部视频，或不属于项目的视频），只放宽检索，输入框上写明并能去掉（架构设计 §5.7「权限」）。

**没装模型时。** 取材工具退回 `speech.search` 的字面匹配并在结果里标明 `effectiveMode`；记忆整份附上。

### 2.10 Space 与素材库

**P1 / P2。**

- **按描述找自己的素材**（P1）：品牌库与项目素材可以用"那张蓝色背景的 Logo 动画"找；在编辑器取用面板与 Space 共用同一检索。
- **相关视频**（P2）：Space 条目的查看框里列出"讲相近内容的视频"，用于系列创作与避免重复选题。只列用户自己的视频，只在用户打开时计算。
- **导入去重提示**（P2）：导入素材时发现与已有素材内容几乎一致，提示"已有相同素材，链接到它？"；不自动合并。

### 2.11 模型、索引状态与降级

**P0。**

- **设置 › 语义索引**（偏好设置一组）：模型（「文字搜索」「多模态搜索」两个包，v0.1 §4.2）、已索引的项目与通道、缓存大小、暂停/恢复/清理、实际后端（CPU/GPU）。完整性按通道分别写（"文字已就绪；画面 18/30 个素材完成"）。
- **安装不等于扫描。** 装完模型默认只对已有文稿建轻量文字索引；画面与声音按项目开启，开启时写明范围与开销（v0.1 §9.1）。
- **每个入口自己说明状态。** 写作参数页的「按主题」、润色的术语候选、翻译记忆、重录候选、插图匹配：各自在置灰或退回时写一句原因与去设置的入口；不弹全局警告卡。
- **索引过期**：视频刚改过、索引还没跟上时，用到语义能力的入口显示「索引更新中，结果可能不含最近的修改」，不阻塞操作。

### 2.12 多端差异

- Electron 与 Web 共用连接的 Runtime，索引只在 Runtime 所在主机建立；Web 显示 Runtime 的能力状态，不在浏览器里建索引（v0.1 §4.3）。
- AI 工具 Tab 目前只在 Electron（Web 端没有结果页与参数页）；写作选材、术语候选、重录候选等随它一起只在 Electron 出现。Space 搜索、字幕面板的翻译记忆标记与术语不一致统计两端都有。
- CLI 与 MCP：`space search` 与取材工具进入 Agent 面；写作类直接流程的 `--scope topic` 参数进入 CLI；库相关（术语、翻译记忆）按架构设计 §5.9 不对外部程序开放。

### 3.2 Runtime 内部能力：SemanticContext

写作、章节、术语、翻译记忆、重录、插图与智能体工具都不直接碰 `SearchService` 的用户检索接口，而是用一层 Runtime 内部能力 **SemanticContext**（`packages/runtime-core/src/space/semantic/context.ts`，拟议）。它不是网关方法，不进 `methods.ts`；稳定之后再决定哪些子集暴露为 RPC。

```ts
interface SemanticContext {
  // 用 query profile 编码一批文字；无模型时抛 MODEL_NOT_INSTALLED
  embedTexts(texts: string[], opts: { role: 'query' | 'document'; profileId: string }): Promise<Float32Array[]>;

  // 在授权范围内找与一句意图最相关的句群，按时间排序或按相关度排序
  findRelevantChunks(req: {
    intent: string;                      // 用户的意图句或段落文字
    scope: ChunkScope;                   // 视频 / 项目 / 已授权素材；view: source | sequence
    channel: 'text';                     // 本层 P0 只接文字；视觉见 matchFrames
    limit: number;
    order: 'time' | 'relevance';
    neighbors?: number;                  // 每个命中向前后各扩几句，保证上下文完整
    minScore?: number;                   // 只要不低于它的语义命中；不给时不筛，低于弱命中阈值的标 weak（阈值由标注集校准，不是置信度）
  }): Promise<RelevantChunkSet>;

  // 段落 → 画面候选；无视觉索引时抛 INDEX_NOT_READY，由调用方决定退路
  matchFrames(req: {
    text: string; videoId: string;
    near?: { anchor: SentenceAnchor; windowSec: number };  // 优先在出处附近找
    limit: number;
  }): Promise<FrameCandidate[]>;

  // 对称相似：两组句子谁与谁几乎相同（重录、翻译记忆、术语）
  pairSimilar(req: {
    left: ChunkRef[] | string[]; right: ChunkRef[] | string[];
    profileId: string;                   // 对称 profile，不是检索 profile（v0.1 §15.3）
    threshold: number;
  }): Promise<SimilarPair[]>;

  // 调用方要在界面上写"走了哪条路"
  status(scope: ChunkScope): Promise<SemanticStatus>;   // ready | partial | stale | unavailable + 原因
}

interface RelevantChunkSet {
  chunks: Array<{
    chunkId: string; videoId: string; documentId: string;
    sentenceIds: string[];                 // 稳定句子身份，供回引与定位
    text: string;                          // 原文，不清洗
    anchor: { clock: 'source' | 'sequence'; start: MediaTime; end: MediaTime };
    chapter?: { id: string; title: string };
    score: number;                         // 仅用于排序与阈值
    weak?: boolean;                        // 低于弱命中阈值：只标出，不藏起来（G0：阈值分不开有答案与无答案）
  }>;
  coverage: { chapters: string[]; indexed: boolean; stale: boolean };
  effectiveMode: 'semantic' | 'lexical' | 'none';
}
```

规则：

- **范围先于计算**〔G〕。`scope` 由调用方的主体与授权解析为可见对象集合，再进入向量扫描（v0.1 §8.3）。智能体调用时 `scope` 不得超过它的会话范围。
- **原文不清洗**。返回给文本模型的文字是文稿原文；NFKC/小写只在 lexical 分支内部。
- **冷启动可控**。`embedTexts` 走 v0.1 §11.4 的临时资源租约，不为每次调用建持久 Job；连续调用共享已加载的模型，空闲后按 §16.1 卸载。
- **不缓存意图向量**。查询向量不持久化；文档向量全部来自语义索引的当前 `activeGeneration`。

### 3.4 写作流水线：选材、引用与局部改写

**数据流（直接调模型路径）：**

```text
意图句 + 范围
  → scope = topic ? findRelevantChunks(intent, scope, order:'time', neighbors:1) : 现有范围投影
  → 组装：每句一行 "[s17] 原文"（sentenceId 的短编号映射表随任务冻结）
         + 章节标题行 + 时间码与说话人（现有做法）
  → 文本模型（Markdown 正文；每段或每个列表项末尾回引 "[s17, s18]"）
  → 按段落拿出编号并校验：只接受本次发出的编号；无效编号丢弃；正文段没有有效编号时标 inferred
  → 结果文档：去掉编号的 Markdown 正文 + citations 旁文件
```

- **正文内回引而不是结构化输出（实现时的取舍）**。模型在段落末尾写方括号编号，Runtime 按 Markdown 段落（空行分隔的块、每个标题、每个顶格列表项各算一段）拿出编号、校验后从正文里去掉。这样任何文本模型都能照做（写作工具不要求结构化输出），智能体路径的写作 skill 也用同一种写法、同一个校验（`runtime-core/src/ai-tools/ai-tool-citations.ts`）。标题段不需要出处。
- **句子编号而不是时间码回引**。要求模型回引句子编号比回引时间更可靠，也与出处锚点一一对应；时间码仍随文稿发出供模型理解顺序。
- **结果成为文档条目（有意的行为变化）**。现在直接调模型的写作结果"给你读、拷走，不写进视频、没有收据"（产品设计 §5.10）；本文把它改为保存成 Space 的文档条目（与工具页的文本生成一致），否则出处无处存放、「重写这一段」也无从接续。不写进视频这一点不变。
- **引用表的持久化**。结果文档条目带一份 `citations` 旁文件（`baocut.citations/1`，类型 `CitationsFile`，见 `@baocut/protocol` 的 `semantic.ts`）：每段 `{ index, role, markdown, inferred, cites[] }`，每处出处 `{ videoId, documentId, sentenceIds, clock: 'sequence', startSec, endSec, text }`（相邻句并成一处），另记 `effectiveMode` 与丢弃的编号数。稳定句子身份是 `s-<首词 ID>`（同编辑器的句子规则），时间是任务时的时间线时间。条目上的 `citations: { artifactId }` 指向它，`space.citations` 读取。拷走 Markdown 时按用户选择内联为时间码链接或去掉。
- **局部改写**。「重写这一段」提交同一流程的 `section` 模式：输入是该段原文、它的 cites 对应的句群（再做一次 `findRelevantChunks` 以该段文字为 intent，允许用户改勾）与全文大纲（各段首句），输出替换该段并更新 citations；其余段落不变。
- **智能体路径**。交给智能体时不改提示词的拼法，而是把"按句编号的文稿"（`speech_sentences`）与"按主题选材"（`speech_relevant`）作为工具提供（§3.9），两者给的句子都带短编号，编号按会话登记、同一会话里不重复；写作 skill 要求在段落末尾回引 `[sN]`。收尾是交付：`downloads_save` 交出 `.md` 时按这个会话登记过的编号做同样的 cites 校验，交出去掉编号的正文，出处随 Space 条目保存（架构设计 §3.5）。
- **跨视频**。`scope` 含多部视频时编号带视频前缀（`v2:s17`），citations 带 `videoId`；文档条目来源记为这些视频。

**无模型时**：`effectiveMode: 'lexical'` 或 `'none'`，选材退回现有范围投影；编号与 citations 照常，所以出处能力不依赖语义模型（§2.2）。

### 3.5 段落与画面的匹配

- 候选来源是 v0.1 §6.2 的视觉索引（`representation=keyframe|clip`）；匹配用文字 → 视觉的检索 profile。
- 优先级：先在该段 citations 的锚点附近（默认 ±20 秒）找，再全片；两者都给候选，界面「换一张」按这个顺序列出。
- 取帧按源 PTS，经现有媒体通道产出图片素材并收进视频（`managed`），Provenance 记 `matchedBy: encoderProfileId`。
- 退路：无视觉索引时按每段第一处锚点取帧，Provenance 记 `matchedBy: anchor-time`，页面写明。

### 3.6 章节边界候选

- 对时间线投影后的句群（v0.1 §6.1 的文字 chunk，重叠去掉）取文档向量：这一版转写已建好语义索引时直接读索引里的向量（`SemanticContext.topicUnits`，不重新编码；句群起点取第一句不与上一个句群重叠的句子），索引不是这一版（终点与文稿相差超过 1 秒也算）时把时间线上的段落现算向量。
- 按 TextTiling 的做法打分：每个间隔取前后各 `window` 个句群（默认 2）的平均向量，两边的余弦相似度是连贯度；连贯度向两侧爬到各自的高点，落差之和是深度。比较一段窗口而不只比相邻两个，一句插话或很短的离题不会单独成为转折（只比相邻两个时插话两侧的距离与真正的转折差不多）。
- 边界候选 = 深度的局部极大值且超过自适应阈值（全部间隔深度的中位数 + k·MAD，k 为待校准默认 1.5）；再按最短章节长度（默认 60 秒）与最大章节数（默认 24）合并。用索引句群时，候选吸到 15 秒内最近的段落开头，吸不到时留在句子开头，吸附后再按最短章节长度收一遍。
- 共用：AI 工具「生成章节」（`boundaries: 'topic'`）与智能体、CLI 的 `speech_topic_boundaries`（§3.9）是同一份实现（`ai-tools/topic-boundaries.ts`）。
- 画面佐证（2026-10-13）：这部视频这一版建了画面索引时，每个候选另给 `visualShift`：转折前后各 24 秒里时间线上关键帧的平均向量之间的余弦距离（`SemanticContext.timelineFrames`，读索引、不取帧不编码）。只作佐证，不参与打分、不改候选：智能体与 skill「分章节」在深度相近、拿不准合并哪处时参考；直接调模型的「生成章节」暂不用它。未校准：作者章节处与非章节处的分布要等有画面索引的真实库再测。
- 校准：`tools/embedding-eval/chapter-boundaries-eval.ts` 把作者自己分的章节（从链接导入的素材的 `assets[].source.chapters`）当标准答案，在 k、窗口、最短章节长度的网格上算候选落在作者章节点 ±15 秒内的精确率、召回率与 F1。数据集只含时间与向量，放在仓库外；作者章节存在每部视频自己的库里，要用户同意后才读，所以阈值仍标 UNCALIBRATED。
- 把候选边界（时间与前后各两句）连同全文大纲发给文本模型，要求它只在候选处分章、可以合并不可新增，并命名与写简介；结构化输出校验后写入章节标记，与现在的收据与撤销一致。
- 重跑：边界候选来自确定性的向量计算，同一索引世代下结果稳定；只有命名随模型变化。
- 章节自检（原型提议，2026-10-13；实现未做）：写入章节后本机再查两件事，只提示、不改章节。标题与这一章句群质心的相似度，在同一部视频的几章里低于中位数 0.12 以上且低于 0.45 的，提示「标题可能没概括这一章」；相邻两章质心相似度 ≥ 0.9 的，提示「可以考虑合并」（没有合并按钮，挪边界在文稿里做）。每条提示带「跳到这一章」。没装模型或索引不是这一版时不查，并写明没查，不说「没问题」。阈值未经校准；原型见 `model-tool-semantic.js` 的 `chapterHints` 与「生成章节」结果卡。

### 3.7 术语候选与翻译记忆

- **对称 profile**。重录、翻译记忆、术语对比是"两边谁与谁相同"的对称判断，不用检索的 query/document 前缀配对；用 v0.1 §5.2 流程里另立的 `symmetric` profile，并单独校准阈值（v0.1 §15.3）。
- **术语候选**。对术语表条目的规范写法（及其 `misheard` 列表）编码；在文稿句群里找相似度高于阈值、且字面不同的片段；再用字符级相似（编辑距离或拼音/音素近似，按语言可用）复核，避免把语义相近但不是误听的词列进来。输出候选表，用户确认后作为一笔 `polish` 事务提交。
- **术语发现**。文稿里出现 ≥3 次、写法有 ≥2 种且两两相似的名词短语，提示加入术语表；加入是库写入（`library.put`），不是视频编辑。
- **翻译记忆**。索引对象是用户所有视频里的译文单元（`baocut.translation/2`，原句 ↔ 译句），按语言方向分空间；翻译时对每个待译句找相似原句，相似度 ≥ 沿用阈值且非过期的直接沿用并标 `reuse: { fromVideoId, unitId }`，其余作为参考附在提示里（每句最多 3 条）。沿用的译文仍是这个视频里的普通译文单元，可逐句改为重译。
- **术语一致**。同一译文文档内，对术语表里有译法的术语，列出译句里未按译法翻译的位置；统一是一笔普通编辑。

### 3.8 重录候选

- 在时间线投影后的文稿里，对每个句群与其后窗口（默认 90 秒）内的句群做 `pairSimilar`；相似度 ≥ 阈值的连成一组（并查集），组内按时间排序。
- **差异检查**：组内两两做字面差异，提取数字、否定词（按语言的词表，有兜底）、专有名词；任一不同则该对降级为「相似但有差异」，单独列出并高亮差异。
- 默认建议：保留最后一遍；若最后一遍不完整（句末无终止标点且时长明显短于其他遍），建议最完整的一遍。只建议，不预勾。
- 确认后的删除走现有口播剪辑的编辑事务，与其他可剪的口同一张收据、同一次撤销。

### 3.9 智能体工具与上下文投影

- **新工具**（进入工具目录的 Agent 与 CLI 面；首版不开放给对外服务〔MCP〕，要另外登记协议常量与界面文案）：
  - `speech_sentences { video, documentId?, range? }`：一段时间线上的讲话按句编号（与直接调模型的写作发给模型的文稿同一个写法），写作出处用（§3.4）；不依赖语义模型。
  - `speech_relevant { intent, scope?, limit?, neighbors? }`（命名沿用名词组 + 一个动词的模式，如 `speech_activity`、`videos_shots`）：返回 `RelevantChunkSet` 的只读投影（原文、sentenceId、锚点、章节、effectiveMode）。不写视频；范围不超过会话范围。
  - `space_search_v2`、`space_resolve_search_hit`：按 v0.1 §11.4。
  - `space_index_status { videoIds?, projectId?, waitSec? }`：按视频给语义索引的状况（`indexed`、`stale`、`pending`、`failed`、`missingInput`、`excluded`），`waitSec`（≤ 50 秒）时等到范围里没有排队与落后的视频；只读。`space_index_build { videoIds?, projectId?, rebuild?, waitSec? }`：把给出的视频排到队首、重试失败的、`rebuild` 时全部重算；只按会话自己的范围（不用 §2.9 的只读检索范围），没装模型、暂停、项目没纳入时什么也不做；风险 `command`（占本机算力）。建索引本来就在后台自动进行（最近动过的视频在前），这两个只是看与催。
  - `space_related_videos { videoId, limit? }`：与 Space 查看框的 `space.relatedVideos` 同一个实现（§2.10），段落在当前时间线上时带 `href`；只读。
  - `speech_topic_boundaries { video, documentId?, minChapterSec?, maxChapters? }`：话题转折的候选（§3.6），`mode` 为 `topic` 时给 `first` 与按时间排的 `candidates`（`at`、`href`、`depth`、前后原文），`calibrated: false`；为 `model` 时没有候选、给原因。内置 skill「分章节」先取它，章节只落在候选处、按目标章数合并；只读。
  - `speech_retakes { video, documentId? }`、`speech_glossary_candidates { video, documentId? }`：与编辑器 AI 工具页的重录候选、术语候选同一份实现（§3.7、§3.8），只给候选；剪掉哪一遍、改哪个写法由智能体再用 `edits_apply` 提交；只读。
- **skill 怎么用**。说明书 §4 写一条通则：要在视频里找内容时先检索（`space_search_v2`、`speech_relevant`、`space_related_videos`），不先通读；用户给了要挑内容的素材时先转写，再用 `space_index_status` 等索引建好再取材，没有可用的索引或素材没纳入时不等。内置 skill 各自写明在哪一步用：写博客与总结的只写一个主题或几部合写时按意图取材，标题简介与封面看系列里的相关视频，切短视频按点名的话题先检索、不重复切已经切过的段，成片与旁白按每段稿子的意思从用户素材里取原声或画面，口播粗剪先列重录，润色先列术语候选，跨视频问答处理弱命中、退回字面时改用关键词、合并两种说法的结果与翻页。
- **记忆按需召回**。视频记忆条目（产品设计 §6.4）逐条编码进语义索引（对象类型 `memory`，只在该视频范围内可见）。任务开始时 Runtime 用任务合同的意图句召回相关条目附入上下文，其余由智能体用 `memory_search { intent }` 取；记忆的查看与删除界面不变。
- **提示注入**〔G〕。检索回来的文稿与画面是不可信材料（产品设计 §7.5）：工具结果以数据块返回，不含任何可被当作指令的包装；RAG 不授予编辑权限（v0.1 §15.2）。
- **跨视频问答**是一个内置 skill 的流程：`space_search_v2` → 按来源去重 → `space_resolve_search_hit` → 文本模型 → 带引用的回答；回答格式要求每条论断附 `videoId + anchor`，Runtime 校验引用存在后再渲染为可点链接。

### 3.10 配置与 profile

- 新能力在 v0.1 §4.2 的基础上增加 profile 用途：`retrieval`（query/document 配对）、`symmetric`（对称相似）、`text-to-visual`。三者的 `embeddingSpaceId` 可能相同也可能不同，由 G0 评测决定，不假定。
- 设置分组 `semantic`：模型包、启用的通道、索引的项目、翻译记忆是否启用（默认开）、术语候选是否启用（默认开）、缓存大小与清理。
- 每个消费者的阈值（弱命中、沿用、重录、术语、相关视频）集中在一份 `semantic-thresholds.json`（随应用，带 `rankingVersion`），由标注集校准（v0.1 §18.1），不在界面上暴露为滑块。

### 3.12 资源、成本与隐私

- **调度**：交互式调用（写作选材、术语候选、取材工具）走临时租约，优先级高于后台索引、低于预览与导出（v0.1 §16.1）；翻译记忆与重录候选在各自流程的准备步骤内完成，不另起 Job。
- **不触发全库索引**〔G〕：任何写作或编辑入口都不得因为"需要更多候选"而扩大索引范围；只提示用户去设置里开启。
- **成本可见**：按主题选材后发给云端模型的 token 数记入用量账本（架构设计 §6.10）；参数页的"发给模型的"一行写出段数，让用户能对比整篇与按主题的差别。
- **隐私**：向量、翻译记忆、术语候选全部本机；只有最终发给文本模型的文字受外发授权约束；翻译记忆只在同一 Runtime 用户内；对外服务的客户端不读库、不读记忆（架构设计 §5.9、§12.8）。

## 4. 待评审事项

1. **出处的展示形式**：时间码链接、脚注编号还是段尾小字，需原型与用户确认；拷走 Markdown 时的默认（保留或去掉）待定。
2. **按主题选材的默认**：写博客是否默认「按主题」而非「整篇」；长视频阈值（例如超过 30 分钟才默认按主题）待数据。
3. **对称 profile 是否与检索共用空间**：由 G0 评测决定；若不共用，索引体积翻倍，需评估是否只对译文与近期视频建对称索引。
