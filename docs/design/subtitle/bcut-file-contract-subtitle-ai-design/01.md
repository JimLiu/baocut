# 1. 目标与动机

> 出自 [BaoCut 文件契约字幕 AI 管线设计（File-Contract Pipeline, v0.3）](../bcut-file-contract-subtitle-ai-design.md)

现状的逐页 JSON 契约有四类结构性成本：

1. **Token 与页面预算浪费**。入方向：polish 请求把词渲染成 `{"words":{"<词索引>":"<词>"}}` 的稀疏 map，键与引号开销约与正文相当（出方向自 M28 起已是 `paragraphs/sentences` 文本，浪费主要在入方向）；translate 的页信封每行携带 `{id, source, maxChars}`（融合模式再加 `sourceMarked/sourceWords/needsSplit/sourceBreakHints`）。历史融合路径曾把翻译页预算压到 1000 词；融合退役后先放大到 3200 词，现行起始压测值进一步统一为 8000 词。
2. **模型不擅长**。LLM 对"编辑一篇文档""翻译一个 HTML 页面"远比"产出结构严格的 JSON"稳定；JSON 模式下的结构性失败（缺 id、错层级、转义损坏）占了重试预算的大头。
3. **上下文割裂**。小页翻译让模型看不到段落语境，术语与文风在页与页之间漂移（翻译优化战役中 worker 风格方差 9× 的根因之一）。
4. **不可直接审阅**。JSON 载荷对人和 Agent 都不可读；文件契约下每个中间产物都能直接打开看、直接改、直接 diff——diff 能力本身就是版本化（§4）的前提。

同时，本方案**不是推倒重来**：agent 应答循环（`tasks/<taskId>/`）本来就是文件驱动的，本方案是把"文件里装 JSON"改成"文件里装文档"，并把这套文件语义统一延伸到 Cloud Model 路径。
