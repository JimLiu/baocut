# 9. 执行层：Agent 与 Cloud Model 的统一文档接口

> 出自 [BaoCut 文件契约字幕 AI 管线设计（File-Contract Pipeline, v0.3）](../bcut-file-contract-subtitle-ai-design.md)

## 9.1 core 抽象（零 I/O，路径不进 core）

```rust
pub struct DocumentArtifact { pub name: String, pub format: DocumentFormat, pub content: String, pub sha256: String }
pub struct DocumentRequest {
    pub kind: &'static str,              // "polish" | "translate" | "align" | …
    pub contract: String,                // 契约说明（system）
    pub input: DocumentArtifact,         // 待编辑的页
    pub references: Vec<DocumentArtifact>, // context/glossary 等只读引用（与 input 分离）
    pub output_format: DocumentFormat,
    pub attempt: u32,
    pub problems: Vec<Problem>,          // 结构化：{ code, scope, detail }
    pub temperature: f32,
}
pub trait LlmDocument { /* complete / complete_batch_with，与现行 LlmJson 同骨架 */ }
```

- `bcut-flow-core` 保持零 I/O：文件路径只存在于 CLI host；core 收到带名称与 hash 的内存 artifact。（现行 `LlmRequest` 全 String 无路径，不能倒退。）
- `input`/`references` 分离是 provider 内联布局、prompt caching、"references 只读"三件事的共同前提。
- 模型选择是 host 策略，不进 core 请求结构。
- `problems` 元素结构化（`code` 见 §10，`scope` 标注修复范围），供重试波次决定成本。

**M1–M4 实现裁决：只落地了数据结构，没有落地传输通道。** `DocumentArtifact` / `DocumentRequest` / `DocumentFormat` 在 `filepipe/common.rs` 已定义并导出，但**全仓无 `DocumentRequest` 构造点**，`LlmDocument` trait **不存在**——所有文件契约阶段仍走 `LlmJson`（`llm.rs:69`），载荷是 `LlmRequest` 的裸 `user: String`，格式由 host 侧的 kind→扩展名映射表决定。后果有二：`references` 是死通道（§5.3/§9.3）；`sha256` 字段全程为空，§9.5 的内容寻址缓存因此也无从谈起。补齐这条通道是 JSON 契约弃用的前置项（§17）。

## 9.2 Agent 路径

`tasks/<taskId>/` 协议延伸（claim/submit、租约、hedge、`task watch`、`--next` 均不动），改动点：

- **目录分面**：数据面 `inputs/ references/ outputs/` 与控制面 `requests/ responses/ claims/` 分离；**`responses/<callId>.json` 不再内嵌整篇正文，只引用 output 文件路径与 hash**（内嵌会把整页 HTML 做一次 JSON 转义，正是动机要消除的）。**M1–M4 实现裁决：未实现**——任务目录仍是 `contracts / payloads / requests / responses / claims` 五目录，载荷落 `payloads/<callId>.<ext>`（扩展名已按 kind 分化：translate/align→`.html`、polish→`.txt`、analysis/translate-brief→`.md`），`CallResponse.text` 仍内嵌正文。留在原地的理由：目录改名要同时改 CLI、worker 侧 skill 文档与存量在飞任务，属于跨表面的破坏性变更，不能和契约换轨同批做（§17）。
- **claim 信封新增字段**。**M1–M4 实现裁决：落地了四个，缺两个**——非 json 协议下信封增加 `protocolVersion` / `input` / `inputFormat` / `outputExtension`；**`references[]` 与 `answerTemplate` 未加**。`input` 当前**等于** `payload`（同一个文件），要等上面的数据面拆分落地才会分叉。
- **协议/载体自洽检查（M5 补）**：claim 消费请求前先校验 `protocolVersion` 与载荷扩展名是否互相匹配（声明 `file-v1` 却指着 `.json` 载荷、或反之，一律当场拒绝）。不拦的话 worker 会拿 HTML 去跑 json-v0 的 lint 与解析器，症状要到 lint 预算耗尽才浮出水面。
- **worker 步骤**：claim → 读 contract/input → 复制 input 为临时 output → 只按契约编辑 output → `task submit --file <output> --next`。**M1–M4 实现裁决：本地自检环节未实现**——没有 worker 侧的只读 validator 子命令，校验只发生在 `task submit` 的服务端 lint（`bcut task` 子命令集仍是 claim/submit/status/cancel/resume/watch）。`--file` 提交本身已落地。
- **lint 预算**。**M1–M4 实现裁决：未改，仍是 `(callId, leaseId)` 键**（`claims/<callId>.lint.json` 带 `leaseId`，租约不匹配即归零；已有回归测试固化该语义）。改 per-call 恒定预算要新增一份不随 lease 重置的任务侧累计账本，属于租约体系的语义变更；文件契约本身不制造新的换手压力，先观察真实换手率再动（§17）。
- **租约分档**。**M1–M4 实现裁决：`default_lease_sec` 未重标定**，仍是 payload 字符数分档 900/1800/3600s（最后一次改动早于 M0）。文件契约下 HTML 载荷比等价 JSON **更大**而非更小（标签开销），落进同一档或更高档，现有阈值方向上是安全的；重标定需要新的 worker 尾延迟测量数据，缺数据不改（§17）。`request_item_count` **已换轨**：文件契约下改为解析文档并数节点（translate 数 `sentence_ids()`、align 数 `tbody data-sid`），但目前只用于观测，不参与调度。

## 9.3 Provider 路径

- **内联布局**（多文件进一个 user message）：

```text
<BEGIN INPUT name="translate.src.html" media-type="text/html">
…
<END INPUT>
```

**M1–M4 实现裁决：只有 INPUT 信封，没有 REFERENCE 段**——`references` 通道尚未打通（§9.1），`request_user_content` 只包一个 `<BEGIN INPUT>…<END INPUT>`；`name` 取 `<kind>.src.<ext>` 而非页文件名（core 不知道页文件名）；重试上下文追加在信封**之外**，避免污染"信封内即待编辑文档"这条唯一约定。

- 只接受一个完整文件作为答案；单外层 fence 按声明格式零成本剥除；多 fence、前后解释、截断 → 进 §10 格式修复。**不使用 provider Files API**（生命周期/权限/费用/能力跨厂商不一致）。
- **`max_tokens` 按输入页估算的目标输出长度 + 安全余量定标**，不再沿用只适合短 JSON 的固定值——否则文件契约的长输出必然截断，且截断表现为"尾部句缺 id"，会被误判为漏译而烧掉整轮定向重试（配合 `document-truncated` 归因）。**已实现**：`max_output_chars(input) / 2` 折算成 token 后夹取到 `[4096, 16384]`，三家（OpenAI / Anthropic / Gemini）各自落点；Gemini 另给 `thinkingBudget = 8192`。同一个 `max_output_chars`（4× 输入，下限 4096 字符）也是 §16 输出硬顶与 `document-oversize` 的判据，**入方向定标与出方向拒绝共用一把尺子**。
- **JSON 模式按厂商逐一摘除**：OpenAI 形去 `response_format`、Gemini 去 `responseMimeType`、Anthropic 本无 JSON 模式无需改；~~chapters 仍走 NDJSON+JSON 模式，不迁移~~（2026-08 已迁：`chapters` / `chapters-outline` 走 file-v1 HTML，同样不发 JSON 模式并按输入定标 `max_tokens`）。**已实现**，形式是**短路而非状态位**：`if compat.response_format && !file_contract`——文件契约下不发 JSON 模式字段，但**不改动** `CompatFlags` 的持久状态。弃用执行后该短路仍在：未迁移的 json-v0 单轮 kind（segment/cleanup/broll 等）继续用 JSON 模式，能力探测结果不被文件契约的调用污染。
- **400 降级已从单一布尔扩成三维 `CompatFlags`**（`response_format` / `limit`(MaxTokens|MaxCompletionTokens|Reduced) / `default_temperature`），按 400 响应体的字段名子串匹配定位维度，每次 400 只降一维、只重发一次，状态编码进跨泳道共享的 `AtomicU8`。动机正是上一条的 `max_tokens` 抬升：把固定值换成动态值以后，"输出上限字段名/取值不被接受"成了新的常见 400，需要能单独降级而不牵连其他两维。
- 泳道数、429 处理、TailTracker 对冲沿用。响应文本先落盘 `pages/pNNN.out.*` 再进解析器。

## 9.4 模型路由

per-kind 覆盖：config `llm.stages.<kind>` / CLI `--llm-for <kind>=<mode>`。典型配置：`segment-only` 与小页修复波走小模型，analysis/align 走大模型。默认全部继承 `--llm`。默认温度：analysis 0.2 / polish 0.2 / translate 0.3 / align 0.2（与现行一致）。

**M1–M4 实现裁决：per-kind 路由未实现**——`llm.stages.*` 与 `--llm-for` 全仓零命中，所有阶段继承同一个 `--llm`。温度分档照旧生效。见 §17。

## 9.5 复用缓存（新增机制，非沿用）

现行"复用"是线性扫描 + system/user 字符串全等比对（`reuse_prior_response` 扫 `tasks/*/requests/`，provider 侧扫 `logs/llm/*.jsonl`），文件契约下整页比对成本显著上升，且**校验器升级后旧答案会被误复用**。设想中的替代是内容寻址缓存，键 =

```
protocolVersion + kind + contract sha256 + input sha256 + ordered reference sha256s
+ 源/目标语言 + 显式 instructions + renderer/parser version + 影响内容的模型参数
```

renderer/parser version 必须进键——避免新验证器静默接受宽松时代的旧答案（质量回退不可见）。

**M1–M4 实现裁决：未实现，复用仍是 v0.2 描述的"现行"形态**——`reuse_prior_response` 线性扫 `tasks/*/requests/*.json` 做 payload+contract 全字符串相等，`reuse_logged_response` 扫 `logs/llm/<kind>.jsonl` 做 provider/model/attempt/system/user 相等；全仓无 sha256/blake3 摘要。前置依赖是 §9.1 的 `DocumentArtifact.sha256` 通道（当前恒为空串），补齐前无法换轨。见 §17。

## 9.6 协议版本与灰度共存

- claim 信封与 manifest 均带 `protocolVersion`（`json-v0` / `file-v1`）。**历史 task 的 `json-v0` 始终由旧 runner 解释，绝不拿新 parser 猜旧响应**；切换开关打开时已 claim 未 submit 的 call 按其信封声明的协议走完。（manifest 侧的实现口径见 §4.2：json-v0 不写 manifest。）
- ~~灰度开关：`--contract file|json`~~ **2026-08 弃用执行**：`--contract` 参数已整体移除，五个迁移 kind 恒走 file-v1，align 与 translate 天然同链（同一条链不会一半文件契约一半 JSON）。第一条的历史 task 语义保留：本版本对 json-v0 迁移 kind 的提交不做 lint、原样放行，协议判定只认请求信封的 `protocolVersion`、绝不嗅探载荷。
