# 10. LLM 调用层

> 出自 [bcut 转录后处理 AI 管线技术方案（润色 / 分段 / 分章节 / 翻译 / 字幕对齐）](../bcut-ai-pipeline-design.md)

## 10.1 结构化输出：json_object + 引擎侧语义校验

**不用 json_schema strict mode**——它在 OpenAI / Volcano Ark / Gemini-OpenAI 兼容层
之间不可移植。约束靠三层叠加：

1. `response_format: {"type":"json_object"}`（只保证合法 JSON；prompt 内逐字描述
   shape，同时满足 OpenAI 对 json_object 模式「必须提及 JSON」的要求）；
2. **fence-strip 解析**：取响应中最外层 `{…}`，容忍 markdown 围栏与前后闲话；
   数字字段用宽松解码（同时接受 `12` / `12.0` / `"12"`）；
3. **引擎侧确定性语义校验**（覆盖性、id 对账、归一化相等、相似度）——真正的约束层，
   失败走统一重试。

兼容分支：HTTP 400 且报错提及 `response_format` ⇒ 去掉该字段重发一次
（部分轻量模型不支持，fence-strip 仍能从散文中恢复 JSON）。

## 10.2 错误分类与重试

```rust
pub enum LlmError {
    Http { status: u16, message: String },   // 0/408/429/5xx 可重试；401/403/404 终止
    Malformed(String),                        // 可重试
    Terminal(String),                         // provider 终止性错误，直接离开管线
}
```

- 分层重试：传输/JSON 层按上表；**语义错误（引擎抛出）默认可重试**——
  「映射失败 = attempt 失败」由此实现；重试 ×3、2s 退避，取消立即中止；
  其中 `status=0` 表示 DNS、连接、TLS、连接重置或超时等尚未收到 HTTP 状态的
  传输失败，也进入同一有界重试；

**语义拒绝的三级分类（2026-08 重设计）**。每个 kind 都定义「单元」
（analysis = 表格行、polish = 页内句、translate = 句 id、chapters = 章节行，
其余波次生来就是单元级），Problem 按影响范围分三级：

| 级别 | 含义 | 处置 |
| --- | --- | --- |
| **page-fatal**（结构性） | 文档整体不可解析：无栅栏且推不出核心区、无任何可回收单元、体积超硬顶、核心区 atom-LCS 覆盖率 < 0.7 | 唯一允许整页重试的一级 |
| **unit**（单元级） | 某单元缺失、重复、漂移、校验失败 | 该单元判败，其余单元照常接受并落库；败单元进补做队列 |
| **advisory**（提示级） | 只读区漂移、frozen 句被改/被移、多余节点、超出行数、表面级改写 | 只记 Warning，代码确定性纠正或忽略，不影响接受 |

三条落地原则：

- **代码先修**：任何能用代码消解的问题不得触发 LLM 重试——去重合并、列数修复、
  缺失栅栏由邻栅栏推断、冲突标点归一、类别归 `other`、Lock/Origin 降级、越界行
  截断。体积护栏因此改为**硬顶**语义：`max_output_chars` = 8× 输入（下限 4096），
  超硬顶才 page-fatal，否则照常解析并交给单元规则；
- **拒绝即缩窄（shrink on retry）**：单元级失败不重发整页，按该 kind 既有的补做
  载体重新分页（只含失败单元 + 必要只读上下文），每轮带 `[code] detail` 意见，
  补做轮 ≤2（`RetryPolicy::UNIT_ROUNDS`）；page-fatal 的整页尝试为 2 次
  （`RetryPolicy::MAX_PAGE_ATTEMPTS`，第 2 次带意见），之后**对半分页**（各按自身
  分页器把该页的词区间/句集合切成两半）各 1 次，仍失败的半页才走既有兜底。总调用
  上限与旧的「整页 ×3」同量级，兜底粒度减半；
- **耗尽只作用于失败单元/半页**：保留原词、原样或确定性切分，计数上报，不整页兜底、
  不中止命令。`Terminal` / `Cancelled` 照旧立即上抛。

批量原语相应新增报告式变体 `complete_batch_retry_report`：轮次耗尽时把**每个**失败
页与原因交还调用方（旧的 `complete_batch_retry_with` 只报第一条，退化为它的薄封装）。
- **429 由 provider 执行器就地消化，不消耗上述重试预算**：托管配额窗口是分钟级，
  2s 退避必然再撞一次。撞限额时先换 `BCUT_API_KEY_<PROVIDER>_FALLBACK`（若已配置）
  立刻重试，再按服务端 `Retry-After` 头 / 报文里的 `retryDelay` 建议等待重试，
  最多两轮；建议等待超过 75s（多见于日配额耗尽）直接上抛，不把泳道钉死；
- 重试可携带结构化 `retryReason`，注入下一次调用的 prompt；
- **批内尾延迟对冲**：provider 批默认 8 条泳道（配置键 `llm.maxConcurrent`，
  环境变量 `BCUT_PROVIDER_MAX_LANES` 整体覆盖，`0` 为不限）。托管模型单次耗时方差极大——实测 align 同一轮同尺寸请求，多数
  50–82s 返回而个别要 246s，后续修复轮有 barrier，全部泳道只能空等。派发完毕
  的空闲泳道因此会复制仍在飞的长尾调用，取先返回者，败者丢弃。它不是容错
  （被对冲的调用本身成功），而是方差治理，用的是本就空转的泳道。自限三条：
  完成样本 ≥3 才判断、阈值取同批中位数 ×2 且不低于 45s、每个请求至多对冲一次。
  agent 执行器同样对冲，但样本与在飞时长都只算 **worker 时间**（认领→提交，
  排队不计入；无认领记录的调用退回创建时间），末尾唯一在飞的调用系数降为 1——
  否则 12 路 sonnet 会话 4 轮排队会把阈值抬到 26 分钟，形同关闭；
- **Gemini 的 `effort=auto` 仍要封思考预算**：不下发 `thinkingConfig` 不等于
  「不思考」，而是不封顶的动态预算，正是上面那条 33s 与 246s 并存的长尾根因
  （长尾那次的负载还是该轮最小的）。所以 auto 落到 8192，显式 `--llm-effort
  low/medium/high` 仍分别对应 512 / 8192 / 24576。预算是上限不是配额，模型按需
  思考；实测思考令牌需求 2.5k–9.3k。只对 2.5 及以后的型号下发——2.0/1.5 收到
  `thinkingConfig` 会直接 400，认不出版本号一律不下发；
- **DeepSeek V4 的文件任务在 `effort=auto` 下关闭 thinking**：V4 的 OpenAI
  ChatCompletions 缺省启用 thinking，且 `max_tokens` 同时计算推理与最终正文；
  润色/翻译/对齐等整页回写若让推理先耗尽上限，会得到 HTTP 200 + 空 `content`。
  auto 因此发送 `thinking:{type:"disabled"}`；显式 `--llm-effort` 仍启用原生思考。
  空正文错误只记录 `finish_reason`、推理字符数与推理 token 数，不记录 CoT 文本；
- 每次调用（成功与失败）都记文件日志：kind / project / model / system / user /
  response / error / 耗时 / `hedge`——事后审计、重放、A/B 不区分执行器。
  `hedge=true` 的记录是对冲副本，与原调用同 prompt 同 attempt，**不代表任何
  一次失败**，统计重试率时必须排除。

## 10.3 双执行模式（对接 CLI 设计 §8）

`bcut-flow-core` 的引擎只依赖 `LlmJson` trait；CLI 提供两个执行器：

- **provider 执行器**（`--llm provider:<id>`）：ureq 直连 OpenAI 兼容 / Anthropic /
  Gemini（Anthropic 分支注意：thinking 模式要求 `temperature=1` 且
  `max_tokens > thinking budget`）；密钥来自 `BCUT_API_KEY_<PROVIDER>`;
- **agent 执行器**（默认）：阶段发出「调用」= 契约文件 + 载荷文件落 `tasks/`，
  Agent 经 `task claim / submit --next` 认领作答；答案过 lint（= 同一套引擎侧
  语义校验）才落库，`rejected` 带逐条 problems 同租约重试（≤3 次）。
  **提示词与答案永远走文件路径，不进对话上下文。**

两种模式产物 schema 与调用记录完全一致。

**统一词数分页**：analysis、segment、chapters、translate 与 align 都复用
`atomize::word_count`；Latin 一词计 1、CJK 一字计 1，标点随内容原子不另计。
translate 页数为 `ceil(源文词数 / (预算 + 10% slack))`；**默认的 `rows` 模式**下
两执行器共用更小的 800 词档（`/880`，理由与档位详见 §8.6.1），`--align-fusion
on|off` 时才回退到常规档（agent / provider 目前都是 2000，即 `/2200`），随后
按连续顺序均衡页界（§5.3）。
align 在相同词数页数之上，再取 `ceil(待对齐项/40)` 与
`ceil(复杂度总成本/16000)` 的最大值，并按复杂度均衡连续页；并发槽档仍不改变页形；
align 阶段的分页档位不随 `--align-fusion` 取值改变。
`BCUT_LLM_PAGE_WORDS` 只覆盖词数约束（含 rows 的 800 词档），不关闭安全护栏。
定点修复与首轮对齐共享同一套三约束分页；worker 数只影响已经形成的页怎样并发消费。

**融合草稿通道**（`--align-fusion rows|on|off`，默认 `rows`）：见 §8.6 / §8.6.1；
`rows` 只在 `--align-mode many-to-one` 下生效，不改变本节的重试
与响应格式（`file-v1` HTML 不变），只改翻译提示的融合契约段、载体属性，以及
（仅 `rows`）上面这条翻译页预算。`on` 是转正前的旧最小语义块契约，转正后作为
可选回退保留。

**align-only（精修）轮的 brief 复用**：`--align-only` 不改译文真相，brief 在这条
路径上只被消费（受保护术语 + 双语锚点）。精修轮拿不到翻译轮的 analysis /
instructions / tone，按生成输入判定必然失配，会白跑一次 translate-brief 并整表
覆盖 `ai/brief-<lang>.json`（用户 `locked` 的术语被一并冲掉）。因此该路径的复用
条件放宽为「文档词指纹 + 目标语言一致」；翻译轮的判定语义不变。

**brief glossary 的斜杠规则**：斜杠只有在 target **凭空发明**时才算并列备选并被
拒绝；源词自带斜杠的条目（`/compact` 这类 CLI 标志、路径式标识符）必须逐字保留，
校验放行、translate 阶段的逐行规则与 glossary 注入也同样放行。旧规则一刀切拒绝
所有斜杠，与「标识符逐字保留」的提示直接矛盾——模型没有合法输出，整轮 brief 被
判废重跑。该校验同时是 agent 提交期 lint 的实现（§10.3 同一份代码两个执行器复用），
坏 glossary 因此在同一租约内修复，而不是掉出去变成一次全新调用。
