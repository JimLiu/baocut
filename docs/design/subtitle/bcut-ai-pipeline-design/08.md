# 8. 阶段四：翻译（translate）

> 出自 [bcut 转录后处理 AI 管线技术方案（润色 / 分段 / 分章节 / 翻译 / 字幕对齐）](../bcut-ai-pipeline-design.md)

## 8.1 粒度：持久单位 = Sentence；调用顺序 = 最终时间线

三层粒度各司其职：

| 粒度 | 角色 | 键 |
| --- | --- | --- |
| **Sentence** | 完整自然译句、脏检测与持久化单位 | `s-<首词id>`；时间线路由键为 `(srcId, sentenceId)` |
| **页面** | LLM 调用与 checkpoint 单位 | 从最终时间线中的可见 Sentence 顺序确定性分页 |
| **transAlign piece** | 展示与导出切分覆盖层 | `<sentenceId>#<N>`；不拥有独立译文真相 |

v0.3 的句派生以 Cue 末句号为首选边界；无句末标点时只把 ≥1.8s 的强停顿视为
语义句界，0.6–1.2s 的自然思考停顿仍只影响 Cue 展示与 LLM 软标记。另以说话人
切换 / 80 词作为无标点长流兜底。

没有 `timeline.json` 时，路由退化为主源的句序。存在时间线时，投影器依 audience
第一次出现的顺序收集跨源 Sentence，素材复用去重，同一源句在不同 clip/cut 中出现的
可见词取有序并集。给 LLM 的 route id 是不透明键；每条同时携带自己的 `sourceLang`，
所以一页可安全包含不同源语言。上下文来自全局前后页源文，而不是某一个源文件的原始顺序。

## 8.2 契约：紧凑 JSON echo

```jsonc
// 请求页（user payload）
{ "lang": "zh", "context": "Preceding source: …\nFollowing source: …",
  "lines": [ { "id": "r000001", "sourceLang": "en",
               "source": "Ninety days, eight times the growth.",
               "maxChars": 18, "rt": ["BaoCut"] } ] }
// 响应——只回译文，不回显源文（响应 token 减半）
{ "translations": { "r000001": "90 天，翻了 8 倍" } }
```

system prompt 要点：

- 专业字幕译者身份 + Document summary（brief）+ 风格指南 + **glossary**
  （`[LOCKED — use target verbatim]` / `[preferred]` 两档，来自 §5.2 术语表）+ 命名实体；
- **先理解整句，再按目标语言自然语序忠实翻译**——「后续对齐阶段负责把自然句映射回
  时间轴」，明确告诉模型不要为对齐牺牲语序；
- `maxChars` 是按 CPS（阅读速度）与该组显示时长算出的字符预算；
- 每行恰好一个译文（禁止斜杠/括号列备选；但术语自带斜杠——例如 `/compact`
  这类 CLI 命令——必须逐字保留，见 §10.4「brief glossary 的斜杠规则」）；route id 视为不透明字符串，每个 id 恰好出现一次，不得合并/拆分/
  丢弃/重排；CJK 空格规则；简繁按目标码处理。

**校验**：双向 id 对账，三种失败都使 attempt 失败重试——
`unknown id` / `empty translation` / `missing id`。落库后另行统计术语违例与
CPS 违例进 check 报告（advisory，不阻塞）。

CJK 目标译句通过校验后、写入 `trans` 前经过同一套幂等 AutoCorrect。该步骤
必须先于展示切分；若先生成 `transAlign.pieces` 再只格式化整句，会破坏
`concat(pieces) == trans` 的拼接不变量。`align-only` 入口也会在派生 pieces
前补做一次格式化，以兼容旧项目中的未格式化译文。

## 8.3 并发

页与页之间**无串行依赖**：滚动上下文不用「上一页译文」，改用静态的**邻页源文**
（Preceding/Following source）。引擎先构建全部页请求，再经 `complete_batch_with`
批量派发；agent 执行器会一次挂出队列，由最多 3 个不同 worker 并行 claim
（`BCUT_LLM_MAX_WORKERS` 覆盖，`0` = 不限、按 pendingCount 全开；未覆盖且已交付调用
的 worker 时长中位数 ≥ 90 s 时自动放大为 `ceil(pendingCount/2)`、夹在 3..16），provider 执行器
按泳道并发直连（优先级 `--llm-concurrency <N>` > `BCUT_PROVIDER_MAX_LANES` >
配置键 `llm.maxConcurrent` > 默认 4，`0` = 不限；命令行开关只作用于本次运行，
泳道数在执行器构造时解析一次）。每页一旦完成校验便立即回调、checkpoint 和刷新
Studio，失败页携带各自 `retryReason` 独立进入下一轮，不等待同批其他页面。
glossary 匹配在重试循环外计算（昂贵，不能因 JSON 畸形而重算）。
定向重翻的页面会把未选中句作为只读冻结语境；模型改动任一冻结句时整页拒收、绝不
覆盖旧译文。同一页大量冻结句被同时改写时，尝试工件仍保留逐句诊断，但注入下一轮的
`retryReason` 按相同 error code + detail 聚合成计数摘要，避免重复错误挤掉真正的修复指令。
每页结果先按 route id 对账，再散写到对应 `transcripts/<srcId>.json` 或主
`transcript.json`；保存前先校验全部源文档，再逐文件原子替换并刷新一次 Studio 投影。
多文件 checkpoint 不是文件系统级事务；若进程在文件之间崩溃，已经写入的句靠匹配的
`transSrc` stamp 被续跑识别，未写入的句继续处理，因此重入会幂等收敛。

## 8.4 断点续跑：句 id 是持久单位

进度文件存 `{routeId → 译文}` 映射而非页号。续跑时按当前最终时间线重算有效 route
集合，分页参数或 clip 排序变化不会作废已经具有相同可见词指纹的译句。结构上已经不存在
的 Sentence 会从所属源的 `trans` / `transSrc` / `transAlign` 同步清理；仍合法但暂未被
编排进时间线的源译文保留，避免仅因移出/移回时间线而丢失资产。

## 8.5 增量重翻（`--stale-only`）

组级脏检测（§3.3 `transSrc`）+ 段落级重跑：

```
staleSentences = { 句 | 译文缺失，或 transSrc stamp 缺失/不等于当前可见词指纹 }
stalePages     = 含任一 stale 句的最终时间线页面
```

- rebind 保证「小范围润色 → 只有被碰的句 stale」；cut/restore 只让可见词集合变化的句 stale；重转录换发 id 后全部重建；
- **已有译文但没有 stamp 视为 stale**，旧数据必须经当前可见词语义重新确认，不能永远冒充新鲜；
- 翻译输入只含 stale Sentence，但 brief/前后页上下文仍来自整个最终时间线；显示时长/CPS 预算也按 audience 实际可见时窗计算；
- 每个结果只覆盖所属源的句级 `trans` 与 `transSrc`，并删除该句旧 `transAlign`；随后按确切可见词 id 子序列重对齐；
- `--review` 候选按源保存同一正文基线 SHA。`review accept` 先验证所有源未变化，再写任何一个源，避免半提交。

参数：页预算按执行器分档（`paging::PageExecutor`）——agent 2000 源文词、
provider 2000 源文词（两档分开声明、目前同值；`word_count` 口径 + §5.3 slack；`BCUT_LLM_PAGE_WORDS`
可整体覆盖两档用于调优对拍），`temperature 0.3`，重试 3 × 2s。translate 连续页只按
源文词数均衡；句数、序列化字符数和 worker 槽位不改变翻译页数，句子是分页原子、
绝不跨页劈开。align 另有逐项复杂度护栏，见 §9.2。分档动机：单页应答时长近似随
页词数线性，agent worker 一页 5000 词的
translate 约 5 分钟、align 约 11 分钟（Codex 线程 01a003ff 实测），且一篇 3571 词
的谈话在 5000 档只有 1 页，多 worker 槽全部闲置、无法并行；2000 + 10% slack 的
最大页 2200 让 ~3500 词的谈话分成 2 页、~10000 词分成 5 页，worker 才有活可抢。
provider 泳道是本进程直连、无认领/提交往返，但单页时长仍随输出 token 线性、
而泳道（默认 8）通常吃不满：DeepSeek v4-flash 实测（brief 已缓存）3571 词谈话
4000 档 1 页 147/208s vs 2000 档 2 页 108/95s，9784 词谈话 4000 档 3 页 244s vs
2000 档 5 页 140s，残余 violations 也更少——所以 provider 档也定 2000，只多付
一次 brief 与页首 system prompt；两档仍分开声明，日后可独立再调。
agent 模式批量派发并由多 worker 消费，provider 模式按泳道并发直连——两者都是
批量并发，只是并发上限来自不同环境变量。
持久产物：每个源 transcript 的 `trans[lang]` / `transSrc[lang]` / `transAlign[lang]`；
时间线 route 与页面状态属于可重建进度，不另立句译文文件。

## 8.6 切分融合（fused alignment）：翻译调用顺带产出块对齐草稿

动机（fWZ 基准，2026-08-02）：一次典型短视频跑 7 次 LLM 调用，其中 align 占 4 次、
每次答案仅 ~1.2k 字符——而译文本来就是同一模型在 translate 调用里刚产出的。对齐所需
的信息在翻译时就可以给到模型。

机制（`manyToOne` 时默认启用，`TranslateOptions.align: Some(TransParams)`；协议见
[对齐块设计 §6.1](../bcut-alignment-block-subtitle-split-design.md)）：

- **载荷**：仅对确定性判据已经要求拆分的可编辑 `<p>` 附加
  `data-align-words="[1]I [2]didn't [3]go …"`（句内锚定词，一词一序号，与
  `TransAlign.words` 同口径；CJK 源按 `words[]` 原子计）与 `data-align-needed`
  （源侧超单行显示宽度，或整句语音时窗超停留护栏 ~7s）。短句不重复携带融合属性；
  若其译文意外超出 fit，仍由 dedicated `align-edges` 兜底。载荷不含源 Cue
  id/边界、不含停顿提示、不含切点建议——模型不再切源、不再切译、不再解决交叉。
  system prompt 追加融合契约段（`<span data-src>` 微格式）；翻译契约同时保留
  顺句驱动偏好：同样自然的语序里优先贴近源语小句顺序（同传式顺译），从源头减少
  展示对齐的语序交叉。
- **应答**：句子正文仍是一条完整译文；模型只在 `<p>` 内部把译文包成
  `<span data-src="../3 4 5">我们昨天讨论的</span><span data-src="../1 2">计划</span>…`
  ——最小自然语义块 + 每块对应的源词序号（可乱序、可不连续、可为空；每个序号
  一句内至多归属一块）。span 对译文透明（`element.text()` 仍是整句），span 外的
  正文按空归属块计。译文真相仍取自 `<p>` 正文（先写整句、再谈对齐——融合绝不
  允许为对齐扭曲译句）。
- **答案侧属性一律推荐省略**：`<p>` 只需保留 `id`——`data-align-words` /
  `data-align-groups` / `data-align-needed` / `data-budget` / `data-rt` /
  `data-source-id` / `data-sid` / `data-translation` 都是**输入专用**指令，
  `parse_translate_page` / `lint_agent_answer_file` 的每一处校验（对齐草稿、
  `data-rt` 必现术语、`data-editable=false` 冻结句判定与既有译文）都只读**输入页**
  （`TranslatePage` / 渲染出的载荷原文），从不读答案里的同名属性——这正是"答案
  能安全丢光属性"的原因，不是宽松校验，是解析器压根不看那一份。保留属性不算
  错（容忍旧行为），但 system prompt 明确要求省略：理想的句子元素就是
  `<p id="s-g1.0">译文</p>`；冻结句同样只需原样吐出既有译文文本，不必带回
  `data-editable`/`data-translation`。实测一次 59 句 translate 回答从 25277
  字符降到 5871 字符（provider 输出，`on` 模式）。`<article>` 与每个
  `<section id>` 结构仍必须原样保留——定位句子靠的是 id 落在哪个 section，
  不是属性。
- **验收**：translate 侧只做结构预检（序号合法且不重复、块文本拼接归一化后等于
  译文）；通过后草稿原样（`FusionDraft { chunks }`）交给 align 引擎，引擎把块展开
  成软对齐边（权重 0.75）、与 `AnchorAligner` 硬边合并，走与 dedicated
  `align-edges` **完全相同**的确定性块合并 → 双语 DP（`align_block::plan_sentence`）：
  `Aligned` 零调用落库（`AlignOutcome.prealigned_sentences`）；某块超 hard ⇒ 进
  `align-rewrite` 改写轮；证据不足（`SentenceLevel`）**不**直接接受，回落 dedicated
  轮再拿一次块标注。因此该通道只省调用、不降标准；span 解析失败只丢草稿，绝不
  拒绝整页翻译。
- **不适用**：independent/oneToOne 模式、`--align-only`、refine-align 与 routed
  （最终时间线）翻译不融合，走原路径。表格载体（`--align-carrier table`）下融合
  草稿同样先走块核，`NeedsRewrite`/`SentenceLevel` 的句进表格轮。
- **载荷末尾提醒**：本页只要有任何融合句（`on` 或 `rows`），渲染在
  `</article>` 之后追加一行纯文本 `Reminder: …`（`on`/`rows` 各自文案，提醒
  "答案只留 id"以及"每个带融合属性的句子都要标注，不能标几句就退回纯译文"）。
  这不是协议内容：`parse_translate_source` 定位到 `<article>` 即止，根级尾随
  文本一律忽略。动机是长文档下 system prompt 里的契约段会被"稀释"——实测
  deepseek 一页 59 句只有前 3 句标注、其余全退回纯译文；把最关键的一条要求
  放在模型最后读到的位置是侵入最小的补救。`off` 模式没有融合句，不加提醒。

预期效果：草稿验收率高时 translate+align 从 1+N 次调用坍缩为 1 次；验收率低也不会比
原来多调用；省略只读属性后答案本身也显著变短（见上）。

**开关（`--align-fusion rows|on|off`，默认 `rows`）**：`rows`（默认，见 §8.6.1）
把契约定成显示行分区，`TranslateOptions.align_rows: true`；第五轮对拍达标后
（Trilemma overFit 15%→10%、墙钟 ~60s→16s，Pi Agent 40s vs `on` 86–130s，且
三项宽度/读速指标全面优于 `on`）从实验模式转正为默认。`on` 是转正前的旧
最小语义块契约，仍走同一套 `TranslateOptions.align: Some(_)`（只是
`align_rows: false`），转正后作为可选回退保留。`off` 时 `TranslateOptions.align`
置 `None`，载荷不带 `data-align-*`、system prompt 不挂融合契约段，本轮不产出也不
采信草稿；解析侧不变，回答里即使仍带 `<span data-src>` 也只当译文文本，不拒页
（provider 的 `parse_translate_page` 与 agent 提交期的 `lint_agent_answer_file`
共用这一行为，各有一条回归）。开关只在
`bcut translate` 上（`bcut auto` 内部同步默认 `rows`，不单独暴露该参数）；
`refine-align` 不重跑翻译，固定按 `on` 的旧契约核验既有草稿，不随这次默认
切换、也不暴露该开关。

## 8.6.1 行分区模式（`--align-fusion rows`，默认）

动机：`on` 模式的融合草稿是"最小语义块"，块到显示行之间仍要靠 align 引擎的双语
DP 再切一轮；既然译文和分行本就是同一份认知负担，不如让模型在 translate 调用里
直接把整句"翻译 + 拆成显示行"一次给出——省掉的不是证据，是再问一轮。

- **载体**：`rows` 沿用 `on` 的 `data-align-words` / `data-align-needed`，额外给
  可编辑 `<p>` 追加 `data-align-groups`，确定性源侧分组 + 每组时长，格式
  `firstOrdinal-lastOrdinal@startSec-endSec`，多组用 `;` 分隔，例如
  `1-4@0.0-1.4;5-9@1.4-3.2`：序号 1-based 闭区间，秒数相对句首、固定一位小数
  （内部按 0.1 秒整数存放，渲染/解析/相等三者同源，见
  `filepipe/translate_html.rs::{render_align_groups, parse_align_groups}`）。
  `data-align-groups` **只在 rows 模式渲染**；`on` 模式的载体形状不变。
- **答案同样只需 id**：`data-align-words`/`data-align-groups`/`data-align-needed`
  等全部是输入专用（见 §8.6 的通用说明），rows 契约额外强调"逐句都要标"——
  载荷末尾的提醒文案是 `EVERY sentence that carried data-align-groups — all of
  them, not just the first few — must come back cut into <span data-src>
  display rows`，因为 rows 比 `on` 更容易在长页后段整段退回纯译文（省属性腾出
  的上下文正是用来多标几句）。
- **分组规则**（`engines/align.rs::fusion_groups`，零 LLM、零随机）：种子边界
  优先复用源侧已有的字幕 Cue 行首词；再补两条本地规则——前一词以从句标点
  （`,;:—–，；：、…`）收尾、或词间静音 ≥ 0.35s。小于 3 词且短于 0.8s 的组并入
  相邻组（优先并入左邻，句首组并入右邻）；大于 5 秒或大于 14 词的组在其最大
  内部停顿处递归再切（两侧各留 ≥ 2 词）。
- **应答契约的四条硬约束**：每个 `<span data-src="../a-b">` 是**一条连续递增的单一
  区间**；相邻行首尾相接，全部行合起来恰好覆盖 `1..N`（与源词顺序同步——不允许
  为语序自然而打乱行序，语序对不上时把相关组合并成一行，整句实在排不进源序就
  退化成覆盖 `1-N` 的单一 span）；**行只能是一个组或若干相邻组的并**，不得切在
  组内部；每行 ≤ `fit`、绝不超过 `hard`，且读速（display units / 行覆盖的组时长
  之和）不超过 6 单位/秒。
- **覆盖面判据**：`needs_split || source_words >= 8`（`FUSED_ROWS_MIN_WORDS`）——
  比 `on` 模式的"源侧已需拆分"放宽，短句只要词数够就搭上免 align 的直通路径。
- **验收**：`format_fusion_draft` 在 AutoCorrect 落库后用入库译文的源词数重验
  `is_row_partition`；`accept_fused_drafts` 命中行分区草稿时改走
  `align_block::plan_sentence_rows`（对齐块设计 §6.1）——行边界直接冻结成块边界，
  行内超 `hard` 才在行内候选切点上再跑双语 DP，绝不跨行合并。写入的
  `TransAlign.aligner` 是新增标签 `llm-rows+anchor/1`，`correspondence` 仍是
  `Block`。**块粒度因此从"语义块"变成"显示行"**：下游字段形状（`blocks[]` /
  `pieces[]`）与 I3/I4 块层不变量都不变，只是块数变少、块更粗。
- **短行合并**：按行分组之后、写入条目之前有一道确定性后处理
  `align_block::merge_short_rows`。动机是模型实测基本按源侧分组一对一切行
  （每句行数明显多于常规融合的语义块），契约里"偏向合并"的措辞对它几乎无效，
  宽度/读速/时长都是可算的量，改由引擎收口不必再多花一次调用去劝模型。判据
  对同句相邻两片，任一片"太快"（读速 > 6 单位/秒）或"太小"（时长 < 1.0s 或
  宽度 < 6 单位）即触发，但**合并守卫分级**：由"太快"触发的合并允许合并后
  宽度到 `hard`（zh 20）——读速没有更便宜的补救手段，只能靠拉长时窗；只由
  "太小"触发的仍守 `fit`（zh 16）。两级都还要求合并后时长 ≤ 7s。这是有意的
  "宽度换读速"取舍，与 `on` 模式双语 DP（`pair_cost` 里超 `fit` 只是罚分、
  只有超 `hard` 才是硬约束）同一口径——第四轮对拍里 rows 的 overFit 已压到
  1–2%，cps>6 仍有 12–13%（`on` 中位 7.9%），让宽度给读速正是缺的那一步。
  两侧都能合时取合并后读速更低的一侧（平局取左，保证与遍历顺序无关）；迭代
  到没有合法合并为止（每次合并减少一片，必然收敛）。**只合并片
  （`groups`），不动块（`blocks`）**——块仍逐行记录模型给出的源词↔译文对应，
  下游双语高亮不因合并而变粗；被行内双语 DP 因超 `hard` 切出的碎片不会被这
  一步粘回去（两级守卫都 ≤ `hard`，而那些碎片正是因为合起来超 `hard` 才被
  切开的）。合并掉的行数计入
  `AlignOutcome.rows_merged`，`--json` 汇总为 `rowsMerged`，advisory 明细带
  `(N short row(s) merged)`；不落盘进 transcript，`aligner` 仍是
  `llm-rows+anchor/1`。
- **整页缺行软重发**：一页里"载体请求了行"（`data-align-groups` 非空）的句子
  ≥3 句，且其中拿到合格行分区（`draft.rows`）的不足 30% 时，判定整页放弃了
  行标注——实测模型偶尔会交回结构完整、只留 `id` 的干净答案，却一个
  `<span data-src>` 都不给，不是坏草稿而是整页漏做，重发一次通常就能拿到。
  引擎原样重发该页（同一份 system/user），`retry_reason` 换成强调版本
  （点名"上一次一个 display row 都没有"）。这是**软**重试：每页最多重发 1 次，
  不占用页级错误重试预算（`RetryPolicy::SPLIT_THEN` 那条独立计数）、不拒页；
  第二次仍缺行或传输失败就放弃、保留第一次的译文与草稿；第二次可用则译文与
  行草稿都以第二次为准（对同一批句 id 是覆盖写）。provider/agent 两种执行器
  走同一份判据；`routed`（最终时间线）翻译不适用（该路径本就不跑融合草稿）。
  次数计入 `--json` 的 `rowsPageRetries`。
- **回落**（以下任一不成立就静默回落到 `on` 模式的常规路径，坏草稿永不进
  `problems[]`、永不拒译文）：分区本身不合格（`is_row_partition` 为假：序号有
  缺口、不递增、覆盖不到 N）；AutoCorrect 后复验失败；块字符区间定位失败
  （`chunk_char_ranges` 返回空）；行边界被硬锚横跨、无法成为块边界
  （`plan_sentence_rows` 找不到对应块起点）；行超 `hard` 且行内双语 DP 无解。
  行边界没能落在 `data-align-groups` 的组边界上（`on_groups` 为假）**不算失败**，
  草稿照常接受，只计入 `alignFusionRowsOffGroup` 观测分组提示的命中率。
- **不落盘**：`data-align-groups` 只是翻译请求载荷里的提示属性，随该轮
  `ai/translate/<lang>/vNNN` 页级审计工件一并留痕（与其它 prompt 内容同等对待）；
  解析出的 `FusionGroup` 不写入 transcript 的任何字段，也不进入 `TransAlign`——
  它只在本次调用内部驱动 `plan_sentence_rows` 的行内再切判定，用完即弃。
- **翻译页预算降档**：rows 把每源词的调用成本抬高约 1.6–2×——覆盖面放宽到
  ≥8 词、每个覆盖句多带一条 `data-align-groups` 输入（30 句样本实测用户载荷
  8928 → 10206 字符），答案侧又要逐句给 `<span>` 行而非整句一行文本。更关键的
  是合规率随页长下降：deepseek-v4-flash 在一页 59 句时只有前 3 句给了行
  span，其余 56 句整体退回纯译文；同一模型在较短页上稳定给出 38/50。因此
  `agent`/`provider` 两种执行器在 rows 下共用更小的
  [`budgets::TRANSLATE_ROWS_WORDS`] = **800** 词档（`+10%` slack → 单页上限
  880 词，`ceil(总词数/880)`），而不是 `on`/`off` 的 2000（`/2200`）——
  一场 30 分钟谈话（约 3500 词）因此切成 4 页并行，单页句数落到 30 上下。
  该档取值收紧过一轮：先按 `2000/1.67 ≈ 1200` 落档，第四轮对拍显示 1200 词、
  59 句一页仍会整页 0 span；配合上面的整页缺行软重发一起把这个敞口从不可
  恢复变成可恢复，但页本身也需要更小——800 才落进实测稳定给行的区间。
  `BCUT_LLM_PAGE_WORDS` 覆盖语义不变：设置了就整体覆盖，rows 也不例外；
  align 阶段的分页档位不受影响（详见 §10.4）。
