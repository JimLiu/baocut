# 11. 编排、进度与 CLI 命令面

> 出自 [bcut 转录后处理 AI 管线技术方案（润色 / 分段 / 分章节 / 翻译 / 字幕对齐）](../bcut-ai-pipeline-design.md)

## 11.1 阶段依赖与自动编排

```
asr ──▶ polish ──▶ segment ──▶ chapters
              └──▶ translate(lang) ──▶ display-split(lang)
```

- `bcut auto <media> [--lang zh]`：转录 →（默认）润色（顺带首次分段）→
  有 `--lang` 则翻译+对齐 → **收尾一轮定向重对齐**；
- 收尾精修是检出与修复的闭环：`check` 的对齐类告警只进 `warnings`（不影响
  `ready`），若管线到 translate 为止就结束，这些"能自动修"的缺陷永远停在报告里
  等人工。auto 在翻译后就地跑一次 `refine-align` 的单轮流程（check → 收热点 →
  `translate --align-only --sentences …` → 复核），每语言至多一轮、至多 40 句；该
  auto 子调用不再重新获得 align 全局 repair 预算，也没有额外续轮，复核后无论
  结果都终止。结果落信封 `data.refine[]`
  （`lang`/`rounds`/`refined`/`remaining`/`deferred`），残留交显式
  `bcut refine-align`。`--no-refine` 关闭该收尾。这一轮失败不改变 auto 的
  `status`：翻译与对齐已落盘，只在 stderr 与 `data.refine[].error` 里说明；
- 各阶段开跑前查依赖戳：translate 前确保有分段（`ensure_segmentation`），但
  **人工版式编辑优先**——`asrLayout` 戳显示有手工干预时传空钉、不覆盖；
- transcript 有人工文本编辑（`asr` 戳不符）时 `--polish` 默认翻转为不润色
  （直译现状），显式 `--polish` 可强制；
- `bcut check` 汇报各阶段 stale 状态与 `next` 建议命令（`stale` 错误类清晰可分支）。

## 11.2 Studio 投影与阶段提交

CLI 用 `studio/data.json` 承载字幕正文投影，用 `studio/progress.json` 承载高频
阶段状态。提交顺序是强约束：

1. 阶段产物原子写入所属源 transcript；单源是 `transcript.json`，时间线翻译可在一页中更新多个 `transcripts/<srcId>.json`；
2. `studio_projection::refresh` 原子重建 `studio/data.json`、`rev + 1`，写入
   `contentFingerprint`；项目缺 `studio/` 或 `studio/data.json` 时（`bcut auto`
   直接对未 `project create` 的目录落盘）先自愈补齐骨架与默认数据再刷新——投影
   不是可选步骤，缺 Studio 不再降级成静默跳过；
3. 以同一指纹更新 `progress.json`，才把当前阶段标为完成或进入下一阶段。

运行中 `progress.json` 还可携带 `callsDone` / `callsTotal` / `callsActive`
（provider 泳道自报的瞬时在飞数，阶段切换时清空）、`callsRetried`、`activity`、
`inFlight`、`flow`、`lang`、`taskId` 与 `error`。这些都是向后兼容的可选字段；
批量 translate/brief extract 仍在单页结果就绪时按上述顺序提交，不把整批完成当作
正文刷新门。`flow`/`lang` 由翻译 flow 在进入长静默段前写入（`begin_with_context`）；
agent 路径换新 task 目录派发时（对齐阶段就是新目录），只要处在翻译/对齐上下文就沿用
这份归属——file-v1 的 payload 是 HTML/Markdown，读不出语言不等于没有目标语；只有
非翻译 flow 的新 task 才清掉上一跑残留的 `lang`。

**波次可观测性**（`activity` / `inFlight` / `callsRetried` / 估算 `pct`）。polish
链路不是一波调用：逐页润色（每页最多 3 次尝试）→ 低相似度句复核 → 页缝合并判定
（≤2 轮）→ 超长段落补切（≤3 轮）→ 长句标点补修（≤3 轮），每一波都新增调用。只报
累计 `callsDone/callsTotal` 时，用户看到的是分母莫名变大加一堆 `retry 2/3`，无从判断
现在在做什么、为什么重试。因此 provider 执行器（`ProviderLlm` 的内存台账）额外自报：

- `activity`：当前波次短语，`{波次}[ · 第 {n} 轮 | · 第 {n} 次尝试] · {本波 done}/{本波 total}`。
  波次短语按 kind 取：`analysis` 分析上下文、`speaker-repair` 说话人归属修复、
  `speaker-names` 推断说话人实名、
  `polish` 逐页润色、`polish-retry`
  低相似度句复核、`seam-repair` 页缝合并判定、`segment-repair` 超长段落补切、
  `punct-repair` 长句标点补修、`segment`/`segment-index` 语义分段、`chapters` 生成章节、
  `translate` 整句翻译、`brief`/`translate-brief` 提取术语与风格、`align*`
  拆分并对齐双语字幕，其余沿用阶段 action。**本波** = 一次批派发，重试轮是新批，
  与跨波累计的 `callsDone/callsTotal` 不是同一口径。`detail` 相应扩成
  `"{action} · {activity} · 已完成 {done}/{total} 次模型调用"`（第一段仍是 action，
  客户端的相位关键词匹配不受影响；波次短语本身等于 action 时不重复）。
  agent 路径按 task 目录的请求/应答数写同形态的 `activity`。
- `inFlight`：`[{id,kind,attempt,retryReason?,startedAt}]`，最早开始在前。调用日志
  `logs/llm/<kind>.jsonl` 只在调用**结束**时落盘，正在等返回的请求此前完全不可见；
  在飞台账补的就是这段空白。登记与移除由 RAII guard 保证，成功、失败、取消与 panic
  展开都会清账；`callsActive` 直接取台账长度，两者同源。尾延迟对冲副本也登记
  （它确实是一个在飞请求），但累计的 `callsDone`/`callsRetried` 按下标只记一次。
  agent 路径不报 `inFlight`。
- `callsRetried`：已完成调用中 `attempt > 1` 的条数（累计口径，对冲副本不计）。
- 估算 `pct`：polish 链路自身不写 `pct`，客户端一旦看到有调用完成就把进度视为确定，
  却只拿得到 0%。因此在 `linesTotal` 为空时按波次写单调不减的估算值：`analysis`
  2→6、`speaker-repair` 6→8、`polish` 8→75、`polish-retry` 75→82、`seam-repair` 82→88、
  `segment-repair` 88→95、`punct-repair` 95→99、`speaker-names` 99→100，其余 kind
  5→95，波内按本批 `done/total`
  线性插值。
  这是**估算**，flow 自己写的真实 `pct`（translate/align 逐句 checkpoint）优先，
  阶段提交照旧写 100。agent 路径（`--llm agent`）同一张区间表、同一条门：派发与
  `task submit` 时按 task 目录里**本 kind** 的请求/应答数插值（同一 task 目录会先后
  装下简报、整句翻译与 `align-rewrite`，按目录总数算会串味）；submit 只在投影仍归属
  本 task/阶段时把估算带进注册表。`pct` 是**阶段内**口径，翻译阶段进对齐时归零重走；
  要整跑口径的客户端（App 翻译运行态头的四段阶梯与翻译任务卡 `translate_badge::translate_run_pct`、Web 只读进度 `jobDisplayPct`）自己按阶段折算。

命令以终止错误收场时（`events::error` 统一收口），只要 progress 仍是 active 就写入
`error` 并把 `callsActive` 归零、`inFlight` 清成 `[]`：客户端因此能在 Running 对话框
里看到失败原因，而不是停在一个永远等不到结束的在飞请求上。已经 ready 或与本次失败
无关的项目不受影响。

翻译每页先校验所有源，再按源原子 checkpoint；因此网页逐页出现译文，进程崩溃导致的
跨源半页由下一次幂等续跑收敛。润色、对齐、转录、
章节、说话人重命名和页面编辑回写复用同一刷新函数。正文投影失败时保留已经写入
的 transcript 成果，但 progress 不得前进。页面只有在 progress 与 data 的
`contentFingerprint` 一致时显示完成勾选；不一致显示“正在同步字幕内容”。

`bcut studio sync <project>` 提供显式重建入口；Python `studio_sync.py` 只是兼容壳。

## 11.3 命令面（与 CLI 设计文档对齐，此处只列 AI 阶段增量）

```bash
bcut auto <media|url|project> [--download-dir DIR] [--lang L]...
          [--polish/--no-polish] [--no-refine] [--llm MODE]
bcut polish <project> [--repair --paragraphs p1,p2]   # 全量 / 定点重润色
bcut segment <project>                                 # 仅分段（罕用，通常随 polish）
bcut chapters <project> [--target N] [--title-style S]
bcut translate <project> --lang L [--stale-only] [--align-only [--sentences …]] [--fit N]
bcut review list <project>
bcut review accept|reject <project> polish|translate|chapters
bcut check <project> [--for srt|mp4|…] [--lang L] [--strict]
```

`polish`、`chapters`、`translate` 都支持 `--review`：引擎在内存候选上完成全部校验，
只写 `ai/reviews/<kind>.json`（含正文基线 SHA、候选 transcript 和摘要），不覆盖
`transcript.json`。`review accept` 在项目锁内复核基线后才提交正文并刷新 Studio；
正文已被 App、Studio 或 Agent 改动时返回 `stale`。`review reject` 只把候选标成
`rejected`，正文保持不变。

时间线项目的 `--sentences` 使用 `srcId:s-…`（也接受 slash 形式）的路由键；只有在全项目
唯一时才接受裸 `s-…`，歧义会稳定返回 `ambiguous`。跨源 translate review 保存每个源的
基线与候选，accept 在写入前一次性验证全部基线。

定点重润色（`--paragraphs <p-…>`）：请求的段落区间先按位置排序、相邻/重叠的
合并成一个 scope 再分页（20 个连续段落是 1 页而不是 20 个单段小页），无
carry-over；`ai/polish.json` **合并写**——处理集之内的句记录/建议以本轮为准，
之外的（含仍是兜底的句）原样保留，`fallbackSentences` 是合并后的全篇口径，
`scopedRun{paragraphs, retainedSentences, runFallbackSentences}` 记本轮明细；
只有与 `stages.polish` 同指纹的旧产物参与合并，否则整份覆盖。没有这条语义，
`polish-fallback` 的 fix 只重润一部分段落就会把其余兜底记录抹掉、blocker 假阴性。

## 11.4 写作三工具（`summary` / `blog` / `titles`）

```bash
bcut ai summary <project> [--instructions "…"] [--lang L] [--force]
bcut ai blog    <project> [--instructions "…"] [--lang L] [--force]
bcut ai titles  <project> [--instructions "…"] [--lang L] [--force]
```

这三个是**读文稿、写文本**的工具，不是管线阶段：它们不写 `transcript.json`、
不落 `stages.*`、不进 §3.3 的过期规则表，因此也没有 `--review` 候选稿通道和
`bcut review accept` 入口。前置只有一条——项目里得有非空的 `transcript.json`。

**输入形状**：文稿按 Sentence 派生（`derive_cues` → `derive_sentences`）渲染成
`[n] 原文` 的编号行。模型只被允许引用**句号 `n`**，不许自己写时间；`summary` 的
`t` 由引擎按 `Sentence::start(doc)` 回填。这条不是为了省 token，而是让「时间码
落在文稿范围内」成为结构性事实而不是校验项：越界句号判 `Malformed` 走重试，
**不夹取**——夹取会把幻觉悄悄变成一个看起来合理的时间点。

**分页**：与 chapters 同一档（8000 词，`BCUT_LLM_PAGE_WORDS` 覆盖）。单页直接
一次调用出终稿；多页先 Map（每页抽要点，页 id `mNNN`，走 `complete_batch_retry_with`，
agent 多 worker / provider 多泳道两条路径都并发）再 Reduce（页 id `final`）在
要点摘录上写终稿。摘录行的形状与文稿行一致（`[n] …`），所以终稿提示两条路径共用一份。

**产物**（`ArtifactWriter` 的版本目录语义）：

```
ai/<stage>/
  vNNN/result.json     扁平一层：bcutWriting/kind/version/createdAt/lang/instructions/
                       model/inputFingerprint + 按工具并入的载荷字段
  vNNN/pages/*.md      file-v1 页级尝试归档
  vNNN/manifest.json
  latest.json          {bcutWriting, kind, version, dir, result, createdAt, lang,
                       instructions, inputFingerprint}（只是指针，不复制载荷）
```

载荷字段按工具分形：`summary` = `"points":[{"t":<秒>,"text":"…"}]`；
`blog` = `"title"` + `"markdown"`；`titles` = `"candidates":[三个]`
（多了截断、少了重试——「恰好 3 个」是契约而不是建议）。刻意**不**再套一层
`result` 对象：产物本身就是结果，多一层只会让读取方多写一个 `["result"]`。

**复用与追问微调**：同文稿指纹、同 `--lang`、上一版也没带指令，且未带
`--instructions` / `--force` 时直接复用上一版（`reused: true`，零模型调用，
信封形状与新跑一致：`{kind, reused, version, dir, path, result}`）。带 `--instructions` 即视为追问微调：
永不复用，并把上一版产物经 `latest.json` 读出来作为上下文注入**用户消息尾部**
（顺序是「媒体背景 → 上一版产物 → 自定义指令」，指令在最后，优先级最高；
放用户消息而不是 system 是为了不破坏 prompt 缓存）。每次运行都产生新的 `vNNN`，
所以微调链条是可回溯的，而不是就地覆盖。

**进度**：写 `studio/progress.json` 与 jobs 事件，`jobStage` 取各自的 kind 名
（`summary` / `blog` / `titles`），`detail` 是 App 的 MODEL ACTIVITY 文案；收尾
落回 `active: false` / `phase: "ready"`，三阶段行按 transcript 推导，**不写任何
阶段完成戳**（走 `complete_stage` 会把「润色完成」写成既成事实）。已知限制：
`bcut_jobs::studio::Stage` 只有润色/翻译/拆分对齐三个相位，写作只能借
`Stage::Polish` 的 `phase`（粒度进度的归属门是 `phase == stage.phase()`），
因此运行期间三阶段行会把「润色」显示成 active，收尾时恢复。
