# docs/design/screen-recording/ — 屏幕录制与可编辑的录制素材

**方案稿（2026-11-15）：格式已定并写进规范，格式版本 4、联动组的登记与取景的引用已经实现；录制后端、联动组的成组编辑、取景的渲染，以及本稿 §11–§13 的入口、命令行与智能体工具都还没有实现。** 让 BaoCut 能录屏，并且录下来的东西进现有的编辑器继续剪：屏幕、摄像头、麦克风、系统音频各是时间线上的普通片段，鼠标轨迹驱动可以再编辑的放大与跟随。录制后端自己实现，不用 [Cap](https://github.com/CapSoftware/Cap) 的代码（2026-11-15 定，[§8](#8-许可与-cap)）；设计时对照过 Cap 的数据（核对的版本是 `bd28aaf`，[§4](#4-参考cap-的数据怎样对应)）。素材管理、时间线、效果与成片渲染都是 BaoCut 自己的。

相关：视频格式规范 §1.4（版本）、§3.18（联动组与屏幕取景）、§4.7–§4.10（录制清单、指针轨、屏幕取景文档、键盘轨）、§3.16、§6.7、§7.8；架构设计 §5、§9；[LUT 效果设计](../color-lut/README.md) §9（版本号的升法）。

## 1. 结论

| 问题 | 方案 | 详见 |
| --- | --- | --- |
| 录下来的东西是什么 | 四路媒体是普通的视频、音频素材与实例；不新增实例种类与素材种类 | 规范 §3.18 |
| 各路流怎么对时 | 一份录制清单（文档 `recording`）定义录制时间：不含暂停，每路流记自己的起点与有内容的区间 | 规范 §4.7 |
| 鼠标数据存在哪 | 指针轨：与录制后端无关的 JSON 素材，整数刻度、归一化坐标 | 规范 §4.8 |
| 键盘数据存在哪 | 键盘轨：另一份 JSON 素材，可以单独不录、单独删掉；缺省不录，要录时缺省只录快捷键 | 规范 §4.10 |
| 缩放与光标的编辑存在哪 | 屏幕取景文档（`screen-view`），时刻写在内容的时钟上；视频实例用 `screenView` 引用 | 规范 §4.9、§3.18 |
| 剪辑怎么不失步 | 登记的联动组：移动、拆分、修剪、删段、变速按组进行；旧的 `linkGroupId` 不登记就不联动 | 规范 §3.18 |
| 只拆分时画面变不变 | 不变：取景只是内容时间的函数，不读播放历史与序列位置 | 规范 §3.18 |
| 格式版本 | 版本 4：写出去的一律是 4，版本 3 的视频照常打开、第一次被改时升上来 | 规范 §1.4 |
| 屏幕放大时摄像头 | 不动：位置与大小都不变 | 规范 §3.18 |
| 录制后端 | 自己实现的 Recording Worker 进程，直接用系统的采集接口；边界是「控制协议 + 录制清单」 | [§7](#7-进程与职责)、[§8](#8-许可与-cap) |
| 先做什么 | 先做最小的录制 Worker 产出真实的录制，再把成组剪辑与取景渲染做对，最后补体验 | [§9](#9-分期与验收) |

## 3. 数据怎么分层

| 层 | 存什么 | 在格式里是什么 | 谁能改 |
| --- | --- | --- | --- |
| 录下来的事实 | 媒体、鼠标事件、光标图片、分段与对时 | 素材 + 录制清单 | 写好之后不改 |
| 编辑意图 | 片段的剪辑与布局、缩放区间、光标样式 | 实例、联动组、屏幕取景文档 | 用户与智能体，经事务 |
| 派生结果 | 取景曲线、光标曲线、帧计划、缓存 | 不进格式 | 按输入与算法版本重算 |

两条容易漏的规则都写进了规范：

- **各路流不保证同时开始。** 摄像头比屏幕晚 400 毫秒，就晚 400 毫秒出现，不把它的第一帧对到屏幕的第一帧。断流的区间画面露出下层、声音是静音，不停在最后一帧。
- **有轨迹不等于光标能换。** 光标录进了画面（`baked`）时轨迹只用来取景；界面要关掉隐藏、放大、替换光标这些做不到的选项。

## 4. 参考：Cap 的数据怎样对应

BaoCut 不用 Cap 的代码，也不把导入 Cap 工程当成一个阶段（[§8](#8-许可与-cap)）。下表留作参考：定格式时逐项对照过 Cap Studio 模式的工程（`recording-meta.json` 的 `MultipleSegments`），它说明这套格式装得下一个成熟录屏工具录下的全部事实，也是自己写录制后端时核对「有没有漏记」的清单。以后要是做「导入 Cap 工程」这个可选功能，换算照这张表。

| Cap（`crates/project`） | BaoCut | 换算 |
| --- | --- | --- |
| `segments[i]` | 清单的一段 `segments[i]` | 段的长度取这一段屏幕流的有效长度；各段首尾相接 |
| `display`、`camera`（`VideoMeta`） | `screen`、`camera` 流，视频素材 | `start` = 段的 `t0` +（这路的 `start_time` − 这一段最晚的 `start_time`） |
| `mic`、`system_audio`（`AudioMeta`） | `microphone`、`system-audio` 流，音频素材 | 同上 |
| `cursor`（每段一个 JSON：`moves`、`clicks`） | `pointer` 流，指针轨素材 | `time_ms`（浮点毫秒，从这一段的管线起点算，流的 `start_time` 也从这个起点算）换成整数刻度，所以 `start` = 段的 `t0` − 这一段最晚的 `start_time`。Cap 自己的渲染也是这样对的：查光标用的时间是段内时间加上最晚的 `start_time`（`crates/rendering/src/segment_timing.rs` 的 `segment_frame_times`）。还没有拿真实录制实测；每条事件上的 `cursor_id` 换成 `cursors` 的切换表；`clicks` 的 `cursor_num` 是按键编号 |
| `cursors`（`CursorMeta`：图片、`hotspot`、`shape`） | 清单的 `pointer.cursors`，图片素材 | `hotspot` 在 Cap 里已经是图片宽高的比例，照搬 |
| 移动事件的 `x`、`y` | 指针轨的坐标 | 已经是相对捕获区域的归一化坐标，窗口录制时跟着窗口走；在区域之外的值越出 [0, 1]，照搬不夹 |
| `status`（`InProgress`、`NeedsRemux`、`Failed`、`Complete`） | 不进格式 | 只有 `Complete` 的工程可以导入 |
| `keyboard`（`presses`：`key`、`key_code`、`time_ms`、`down`） | `keyboard` 流，键盘轨素材 | 键名换成 UI Events 的 `code` 与 `key`（规范 §4.10）；时间的换算同 `cursor` |
| `ProjectConfiguration` 的 `zoomSegments`（`start`、`end`、`amount`、`mode`） | 屏幕取景文档的 `zooms` | 可选：`auto` → `focus: pointer`，`manual {x, y}` → `focus: point`；时间从 Cap 的编辑时间换回录制时间 |
| `ProjectConfiguration` 的 `camera`（位置、大小、形状、镜像） | 摄像头实例的 `place`、`mask`、`flipX` | 可选：只换成初始布局 |

录制产物进视频在一笔事务里完成（自己的录制后端同样）：登记素材、写清单、写一份屏幕取景文档、按 `coverage` 放实例并登记联动组。事务失败时没被引用的文件由现有的清理回收；重试用同一个 `commandId` 找回回执，不重复插入。

## 5. 时间线上的样子

一次录制默认显示成一个可以展开的组：

| 行 | 是什么 | 能做什么 |
| --- | --- | --- |
| 录制 01 | 联动组 | 整组移动、拆分、修剪、变速 |
| 屏幕 | 视频实例，`role: 'screen'` | 剪辑、裁剪、布局 |
| 屏幕 · 缩放 | 屏幕取景文档的 `zooms` | 拖边界、改倍率、改焦点 |
| 屏幕 · 鼠标 | 指针轨的点击标记与文档的 `pointer` | 改样式、平滑、点击提示 |
| 摄像头 | 视频实例，`role: 'camera'` | 位置、大小、圆角、镜像、显隐 |
| 麦克风 | 音频实例，`role: 'microphone'` | 音量、转录、混音 |
| 系统音频 | 音频实例，`role: 'system-audio'` | 音量、静音 |

「缩放」与「鼠标」是屏幕实例的附属行，显示文档的内容，不是新的轨道种类。摄像头的布局预设（右下角圆形、左下角圆角矩形、左右分屏、摄像头全屏、某一段隐藏）都落在现有的 `place`、`mask`、`enabled` 上。界面改动属于「复杂」一档，先做原型。

**录完之后怎么编辑。** 停止后直接进现有的编辑器，不另开一个录制专用的编辑界面。每项编辑都落在已有的字段上，格式表达不了的不做成功能（[§14](#14-待评审事项)）：

| 想做的事 | 怎么做 | 落在哪里 |
| --- | --- | --- |
| 剪掉说错的、停顿的 | 文稿里删句子、时间线上拆分与修剪、剪口播的固定流程；都按组进行，屏幕、摄像头与声音一起动 | 联动组的时间编辑（规范 §3.18），剪口（§6.7） |
| 调某一次放大 | 「屏幕 · 缩放」行上拖区间的两端、拖动整段；检查器里改倍率、过渡长短、跟随鼠标或固定看一点；固定看一点时在舞台上拖取景框 | 取景文档的 `zooms[].t0 / t1 / scale / focus / rampIn / rampOut`；改过的自动区间记 `edited` |
| 加一次放大、删一次放大 | 缩放行的空白处拖出一段；选中后按删除 | `zooms` 加一项（`origin: 'manual'`）或去一项 |
| 重新自动缩放 | 检查器「屏幕取景」一节的「重新生成」；只换没改过的自动区间 | `zooms` 里 `origin: 'auto'` 而且没有 `edited` 的项（[§6](#6-自动缩放)） |
| 镜头跟得紧一点或松一点 | 检查器的两个滑块：安全区、平滑 | `follow.safeArea`、`follow.smoothing` |
| 光标的大小、平滑、静止隐去、点击提示、不显示 | 检查器「光标」一组；光标录进了画面（`baked`）时整组置灰并说明原因 | 取景文档的 `pointer` |
| 摄像头放哪、什么形状 | 舞台上直接拖与缩放；检查器里的布局预设（角落圆形、圆角矩形、左右分屏、摄像头全屏） | 摄像头实例的 `place`、`mask`、圆角、镜像 |
| 某一段不要摄像头，或换一种布局 | 在那一段的两端拆分整组，再改中间那一段的摄像头实例 | 拆分出的实例各自的 `enabled`、`place`、`mask` |
| 屏幕不铺满，留边、圆角、阴影 | 检查器的「演示样式」预设：全屏，或缩小留边 | 屏幕实例的 `place`、圆角与 `fx.shadow`（规范 §3.9），底色是 `canvas.background`（§3.2，只有纯色）；要图片背景就在下层放一个图片实例 |
| 声音 | 麦克风与系统音频各自的音量、淡化、静音；降噪、响度沿用现有的音频功能 | 两个音频实例的混音字段（§3.9） |
| 字幕 | 对麦克风转录，再做字幕层；与普通视频相同 | 转写文档与字幕层 |
| 做竖屏版 | 现有的短视频取景（`focalPoint`、`panels`）；有 `panels` 的实例不能同时有屏幕取景，改竖屏时界面提示二选一 | 规范 §3.18 的约束 |
| 整组拆开各剪各的 | 组的菜单「解组」 | `unlinkItems` |

选中屏幕实例时，检查器多出「屏幕取景」一节（缩放区间的列表、跟随、光标、重新生成），其余各节不变。Web 端可以做上表里全部的编辑，只是不能录。

## 6. 自动缩放

分三步，都不需要大模型：

1. **什么时候放大。** 读有效录制区间里的按下事件，在每次点击前后留出一段（起步的数值可以用点击前约 0.3 秒、点击后约 2.5 秒，实测后再调），挨得近的并成一段，丢掉太短的。结果写成 `origin: 'auto'` 的缩放区间。
2. **看哪里。** 指针在可见区域中间的安全区里移动时镜头不动，越出去才跟；可见区域不露出画面之外；用户给了固定焦点就用它。
3. **按时刻取值。** 曲线由文档、清单、指针轨与算法版本确定地算出来，任意时刻可以直接取值，不依赖播放顺序。

重新生成只替换没被改过的自动区间。智能体在这些区间上再调整（「这一段保持全景」「这两次点击合成一次」）。

## 7. 进程与职责

- **Recording Worker**（新进程，与 `engine-host` 并列，自己实现）：枚举屏幕、窗口、摄像头与声音设备，处理系统权限，倒计时、开始、暂停、恢复、停止，采集与编码各路流，记鼠标与键盘事件，收尾与恢复，产出一个可以导入的录制包。控制消息沿用 Worker 的 JSON 行协议；摄像头预览走单独的低分辨率通道。
  - 采集直接用系统接口：macOS 是 ScreenCaptureKit（屏幕、窗口、系统音频）与 AVFoundation（摄像头、麦克风），Windows 是 Windows.Graphics.Capture、WASAPI（含回环）与 Media Foundation。编码沿用 BaoCut 已有的硬件编码路径。平台专属代码条件化（开发流程 §4）。
  - 各路流打同一个单调时钟的时间戳，清单的 `start` 与 `coverage` 由它算出；不为了凑齐丢帧或补帧。
  - 鼠标：缺省让系统不把光标画进画面（两个平台的采集接口都有这个开关），另记位置、按键与光标图片，清单的 `pointer.mode` 是 `separate`；拿不到不带光标的画面时是 `baked`。
  - 键盘：缺省不录。用户打开时缺省只录快捷键（清单的 `keyboard.scope: 'shortcuts'`），「全部按键」要单独选，界面说明它会录下输入的文字；系统的安全输入（密码框）期间拿不到按键，也不补。macOS 上监听键盘要「输入监控」权限，与录屏权限分开申请。
- **Runtime**：持有录制会话与状态，管 Worker 的启动、停止与恢复，核对录制产物，经现有的 `edits.apply` 提交导入。停止的确认只表示命令收到了，素材可以编辑之前都不算成功：录制中、停止中、收尾中、可导入、导入中、已进时间线是六个不同的状态。开始之前另有三个：等待开始（面板开着，还没有采集）、准备中（启动设备、核对权限）、倒计时；录制中可以进出「已暂停」。任何一步失败进「失败」，用户主动丢弃进「已丢弃」，两者都把已经写下的临时文件留到用户确认删除或恢复之后（[§11](#11-入口与录制过程)「收尾与恢复」）。
- **VideoEngine**：仍是唯一的写入端。登记素材与文档、放实例、登记联动组、执行成组的编辑、维护撤销与导出冻结。
- **录的是哪台机器的桌面**要明确：桌面端提供录制入口；Web 端继续编辑已经导入的录制，远程的 Web 会话不能把服务器的桌面当成用户的桌面。首版只做 macOS 与 Windows。

## 8. 许可与 Cap

**已定（2026-11-15）：录制后端尽可能不用 Cap，自己实现。**

- Cap 的根许可证：`cap-camera*`、`scap-*` 两个 crate 家族是 MIT，其余（包括 `cap-recording`、`cap-project`、`cap-rendering`、`cap-cursor-*`）是 AGPLv3。BaoCut 用自己的 Community License，与 AGPL 不能默认兼容。
- 所以：不依赖、不移植、不改写 Cap 的 AGPL 代码。实现录制后端时照系统接口的文档与本稿的格式写，不对着 Cap 的源码写。本稿与规范里从 Cap 得到的只有事实层面的对照（它录了哪些数据、怎样对时），格式是 BaoCut 自己定义的。
- MIT 的那部分（`scap-*`、`cap-camera*`）也不作为缺省依赖：它们的依赖链要逐个审（例如 Windows 的 `scap-direct3d` 依赖不在 MIT 例外里的 `cap-d3d-adapter`）。某个平台的采集确实绕不开时，单独评估、单独决定。
- 「导入 Cap 工程」不在分期里。它只读 Cap 写出的数据文件，不涉及 Cap 的代码，以后想做可以做（[§4](#4-参考cap-的数据怎样对应)）。

入口与命令随阶段开放：阶段 1 有 Home 与编辑器两处入口、录制面板的最小形态（一块屏幕、麦克风、鼠标）、`record` 与 `recordings` 整组命令，其余选项在面板里置灰、在命令行里拒绝并说明还不支持；Space 的入口、摄像头、系统声音、窗口与区域、键盘、全局快捷键、菜单栏图标与控制条的完整形态在阶段 4；智能体改缩放与布局在阶段 5。

阶段 1 提前到联动组与取景之前，是因为没有 Cap 导入器之后，真实的录制只能从自己的 Worker 来；它先做到最小，够后面两个阶段拿真数据验证就行。

必须覆盖的用例：摄像头晚于屏幕启动；暂停后恢复；摄像头中途断开；删掉中间一段；只拆分（画面逐帧相同）；两倍速；同一次录制用两次（效果互不影响）；Retina 与 Windows 的不同缩放比例下光标对得上点击处；窗口移动与区域录制；随机拖动播放头；改导出帧率；导入中进程退出（没有悬空引用、没有重复插入）；撤销、重做与重新打开；便携包换一台机器仍能编辑。

## 10. 已定的裁决

2026-11-15 定下四项：

1. **格式版本。** 新视频一律是 4，旧视频保持兼容：版本 3 照常打开，被这一版第一次修改时升到 4（规范 §1.4）。后果是旧视频被新版本改过之后，旧版本的 BaoCut 不能再打开它。
2. **录制后端。** 尽可能不用 Cap，自己实现（[§8](#8-许可与-cap)）。
3. **屏幕放大时摄像头不缩放。** 摄像头是独立的实例，位置与大小都不变；格式里不加联动（规范 §3.18）。
4. **键盘事件要收。** 加了 `keyboard` 流与键盘轨（规范 §4.7、§4.10）。按键提示怎样显示在画面上还没有定义，放在阶段 5。

还没有定的都在规范 §10 的状态行里：求值算法 1 的曲线与数值、按键提示的显示、键盘轨从历史里彻底清除的办法、成组编辑的细节。

## 11. 入口与录制过程

录制是「不经过智能体、直接产出一个视频」的动作，与「新建空白视频」同类；它不是一个新的工作区域，不占 Rail（产品设计 §2.1：单个动作不单独占一格，同类归入已有区域）。只有 BaoCut 桌面端、而且 Runtime 就在这台电脑上时才有入口：Web 端不显示；桌面端连着远程 Runtime 时入口置灰，说明「只能录运行 BaoCut 的这台电脑」。

**入口**

| 位置 | 样子 | 结果落在哪 | 为什么在这里 |
| --- | --- | --- | --- |
| Home 的快速开始旁 | 与「新建空白视频」并排的「录制」 | 当前项目里的一个新视频 | 不依赖当前对象，直接完成核心工作，不经智能体（产品设计 §3.2.1） |
| Space「新建」菜单 | 「录制新视频」 | 当前所在项目里的一个新视频 | 与新建空视频、从文件新建同属「新建」（§4.8） |
| 编辑器素材面板 | 「导入」旁的「录制」 | 当前视频：素材入库，联动组放在播放头处的新轨道上 | 依赖当前视频，属于页面内部（§5.9） |
| 会话里的智能体 | 智能体调 `record`，弹出预先填好的录制面板 | 会话的视频，或一个新视频 | [§13](#13-智能体) |
| 命令行 | `baocut record` | `--video` 指定的视频，或一个新视频 | [§12](#12-命令行) |

不放进工具页：工具页是「给一个输入、得到一个产物」的骨架（输入、模型、选项、保存位置、开始），录制没有输入，产物是进编辑器继续剪的视频，硬套进去只多一个重复的入口。

**录制面板。** 各处入口打开同一个面板（不是新页面）：

1. **录什么**：整块屏幕（多块屏幕时选一块）、一个窗口、一个区域。BaoCut 自己的窗口缺省不录进去（[§14](#14-待评审事项)）。
2. **摄像头**：不用，或选一个设备；有小预览。
3. **麦克风**：不用，或选一个设备；有电平条。
4. **系统声音**：开或关。
5. **鼠标**：另画光标（缺省，之后可以改大小、隐藏）、录进画面、不要光标。选「不要光标」时说明自动缩放也就没有了。
6. **键盘**：不录（缺省）、只录快捷键、全部按键；选「全部按键」时说明会录下输入的文字。
7. **倒计时**：3 秒（缺省）、5 秒、不倒计时。
8. **开始录制**。

- 每一路旁边显示权限状态。没有权限的那一行给出「打开系统设置」并说明要开哪一项；BaoCut 不替用户改系统设置。缺的是必需的一路（屏幕）时开始按钮不可用，缺的是可选的一路时可以去掉它继续。
- 面板记住上次的选择（按这台电脑记，Web 没有这份记录）。设备已经不在时退回「不用」并提示。
- 开始之前检查落点所在磁盘的剩余空间，不足以录十分钟时警告，可以继续。

**录制中**

- BaoCut 的窗口收起；屏幕上只剩一个小控制条：已录时长、暂停与继续、停止、丢弃。控制条不被录进画面。
- 菜单栏（Windows 是托盘）有录制中的图标，点开是同样的四个动作；全局快捷键可以停止、暂停与继续，在设置 › 快捷键里改。
- 系统自己的录屏指示照常显示，BaoCut 不去隐藏它。
- 暂停的时间不进成片。丢弃要确认一次。
- 设备中途断开（摄像头被拔掉、麦克风换了）不中断录制：那一路从此没有内容，控制条提示一次，清单用 `coverage` 照实记下。
- 磁盘快满时自动停止并收尾，已经录下的保留。

**停止之后**

- 控制条变成「正在收尾」，BaoCut 的窗口回来，直接打开编辑器：联动组已经在时间线上，自动缩放已经生成，摄像头缺省在右下角、圆形。此后的编辑见 [§5](#5-时间线上的样子)。
- 收尾与导入是一个后台任务（种类 `recording`），在后台任务页与视频卡上都看得到；收尾慢的时候可以先去做别的。任务完成才算录制成功（[§7](#7-进程与职责)的状态）。
- 录进当前视频时，整次导入是一笔可以撤销的事务：撤销之后素材留在素材库，时间线恢复原样。

**收尾与恢复**

- 录制中的数据先写在 Runtime 的临时目录，导入成功后才成为视频里的素材。
- BaoCut 或电脑在录制中、收尾中退出：下次启动时 Home 提示「有一次没有收完的录制（日期、时长）」，可以恢复（把已经写下的部分收尾并导入）或删除。没有选之前不自动删。
- 导入中退出：按幂等键重做，不重复插入，不留悬空引用。

**设置**

- 设置 › 快捷键：开始录制、停止、暂停与继续。
- 设置 › 通用（或录制一节）：缺省帧率、缺省倒计时、录制时是否收起 BaoCut 的窗口。
- 权限不在设置里管：它们是系统的开关，只在录制面板与诊断里显示状态。

## 12. 命令行

沿用智能体面与命令行的命名（agent-surface 设计 §4.1）：开始录制是一级动词 `record`（一个任务），录制会话的读与控制是名词组 `recordings`。工具与命令同名同参数，`surfaces` 是 `agent` 与 `cli`；不进对外的 MCP 服务：外部客户端不应该能让这台电脑开始录屏。

**录的是哪台机器。** 录的是 Runtime 所在的那台电脑的桌面。`baocut` 连着远程 Runtime 时 `record` 拒绝（`RECORDING_UNAVAILABLE`，说明原因），不去录远端。没有窗口、由命令行自己拉起的 Runtime 能不能录、系统权限算在谁头上，见 [§14](#14-待评审事项)。

| 命令 | 效果 | 做什么 |
| --- | --- | --- |
| `baocut record` | job | 开始一次录制。缺省 `--wait`：阻塞到「已进时间线」或失败，结果里是 `videoId`、`recordingId`（清单的 `documentId`）、`screenViewDocumentId`、`groupId`、`itemIds`、`duration` |
| `baocut recordings sources` | query | 列出能录的屏幕、窗口、摄像头、麦克风，各带 ID、名字、尺寸；另列每项系统权限的状态（`screen`、`camera`、`microphone`、`inputMonitoring`）与这台电脑能不能录、不能时的原因 |
| `baocut recordings status [id]` | query | 一次录制的状态（[§7](#7-进程与职责)）、已录时长、各路流是否在录、落点；不给 ID 是当前这一次 |
| `baocut recordings list` | query | 当前的与没有收完的录制 |
| `baocut recordings pause [id]`、`resume [id]` | mutation | 暂停与继续 |
| `baocut recordings stop [id]` | mutation | 停止并保留。返回只表示命令收到了，带 `jobId`；要等到可以编辑用 `--wait` 或 `baocut jobs wait <jobId>` |
| `baocut recordings discard [id]` | destructive | 丢弃这一次，要 `--yes` |
| `baocut recordings recover <id>` | job | 把没有收完的录制收尾并导入 |

`record` 的参数：

| 参数 | 含义 | 缺省 |
| --- | --- | --- |
| `--display <id>` / `--window <id>` / `--area <x,y,w,h>` | 录什么，三选一；ID 来自 `recordings sources`，区域是所选屏幕上的逻辑点（配 `--display`） | 主屏幕 |
| `--camera <id>` | 加摄像头 | 不录 |
| `--mic <id>`、`--no-mic` | 麦克风 | 系统缺省的麦克风 |
| `--system-audio` | 录系统声音 | 不录 |
| `--cursor separate \| baked \| none` | 鼠标模式（规范 §4.7）；`none` 没有指针轨，也就没有自动缩放 | `separate` |
| `--keys off \| shortcuts \| all` | 键盘（规范 §4.10） | `off` |
| `--fps <n>` | 屏幕的目标帧率 | 设置里的缺省 |
| `--countdown <秒>` | 倒计时；0 是不倒计时 | 3 |
| `--duration <秒>` | 到时自动停止 | 不限 |
| `--video <id>` | 录进这个视频；不给就新建 | 新建 |
| `--name <名字>`、`--project <项目>` | 新视频的名字与项目 | 「录制 日期 时间」、当前项目 |
| `--no-auto-zoom` | 不生成自动缩放 | 生成 |
| `--no-open` | 完成后不在桌面端打开编辑器 | 打开 |

- **等待与停止。** `--wait` 时进度写到 stderr（状态与已录时长，没有总量）。录制中在终端按第一次 Ctrl-C 是**停止并保留**，继续等到收尾完成；第二次才是退出等待（任务照常收尾）。这与别的任务「Ctrl-C 取消」不同，是有意的例外：按 Ctrl-C 的人要的是录到这里，不是把录好的扔掉；要扔掉用 `recordings discard`。落地时要在 agent-surface 设计 §5.4 写明这个例外。
- **`--no-wait`** 开始之后立即返回 `jobId` 与 `recordingId`，之后用 `recordings stop`。同一时刻只能有一次录制，已有一次在录时 `record` 拒绝（`RECORDING_BUSY`）。
- **`--dry-run`** 只做预检：解析来源与设备、核对权限与磁盘，报告会录什么，不开始。
- **权限。** 缺系统权限时失败，错误的 `details.systemAccess` 列出缺哪几项与各自在系统设置里的位置；命令行不弹系统的授权窗口之外的任何东西。`baocut doctor` 多一项「录制」：这台电脑能不能录、各项权限的状态。
- 没有选项的 `baocut record` 等于面板的缺省：主屏幕、缺省麦克风、另画光标、不录键盘、3 秒倒计时。

例子：

```bash
baocut recordings sources --json
baocut record --display 1 --camera cam_2 --name "产品演示"
baocut record --window 4821 --no-mic --duration 30 --video vid_01H…
baocut record --no-wait && baocut recordings stop --wait
```

## 13. 智能体

智能体可以发起录制、读它的结果、在录完之后帮着剪；它不能在用户不知情时开始录，也不替用户操作屏幕。

**怎么唤起。** 智能体调 `record`（与命令行同一个工具），参数是它从用户的话里读出来的（「录我的屏幕加摄像头，讲一下这个功能」→ 屏幕加摄像头加麦克风）。会话里的 `record` 不直接开始采集：

1. 工具立刻返回 `jobId`，录制处在「等待开始」。会话里出现一张录制卡，同时弹出预先填好的录制面板。
2. 用户看一眼要录什么，可以改，按「开始录制」；也可以关掉面板，任务以「已取消」结束。**这一下点击就是批准**：不另外弹审批卡，也因此任何访问模式（包括完全访问）下都要有这一下。
3. 智能体这一轮到此结束，回一句「录完按停止，我接着处理」。它不轮询。
4. 用户停止，任务收尾、导入、完成。Runtime 经完成收件箱（架构设计 §7.2）把结果交回会话，智能体接着做用户原先要的事：转录、按文稿剪掉口误与停顿、调缩放、加字幕、导出。失败时同样交回，智能体说明原因。

选「预填面板、用户按开始」而不是「工具直接开始采集」，是因为批准、确认人在场、确认录的是什么三件事合成一步，而且面板本来就要有；直接开始的做法留给命令行。

**没有人在场时不录。** 定时任务、Bot 会话与别的无人看守的运行里，`record` 直接拒绝（`RECORDING_UNATTENDED`），不转成待办去等人。远程 Runtime、Web 会话同样拒绝，理由写在错误里，智能体转告用户到桌面端来录。

**权限。** 缺系统权限时面板上照常显示（[§11](#11-入口与录制过程)）；智能体没有打开系统设置的工具，只把 `details.systemAccess` 里缺的项目告诉用户。

**工具的风险等级。** `record` 是 `high`；`recordings_pause / resume / stop` 是 `command`；`recordings_discard` 是 `high`（丢掉的是用户的录制）；`recordings_sources / status / list` 是 `read`。窗口的名字可能带出隐私（文档标题、网页标题），`recordings_sources` 的结果只在本机的会话里用，不进对外服务。

**录完之后智能体能做的**，都走现有的工具，与用户在界面上做是同一套命令：

| 用户的话 | 智能体做什么 |
| --- | --- |
| 「把口误和停顿剪掉」 | `transcribe` 麦克风，再用剪口（规范 §6.7）；剪口按联动组落到每一路 |
| 「这一段别放大」「这两次点击合成一次放大」「这里放大到按钮上」 | 读取景文档，改 `zooms` 后写回（`edits_apply` 的 `patchDocument` 或 `putDocument`）；改过的自动区间记 `edited` |
| 「光标大一点」「加点击提示」 | 改取景文档的 `pointer` |
| 「讲到代码的时候把摄像头收起来」 | 按文稿找到区间，在两端拆分整组，改中间一段的摄像头实例 |
| 「做成带圆角留边的样子」 | 改屏幕实例的 `place`、圆角与阴影，改画布底色 |
| 「加字幕、出一条竖屏的」 | 现有的字幕与短视频流程 |

**现在还缺的**（落地时补，不是新格式）：

- 智能体的修改操作目录（`edits_ops`）里还没有 `linkItems`、`unlinkItems` 与 `setStyle.screenView`；成组的时间编辑实现之后一并开放。
- `documents_read` 与 `documents_put` 现在面向文稿类文档，收不收 `screen-view`、读出来的形状要补一份说明；在那之前智能体用 `edits_apply` 改取景文档。
- 指针轨是素材不是文档，智能体要「看鼠标点了哪里」需要一个只读的摘要工具（按时间列出点击与停留），属于阶段 5。
- BaoCut 的 skill 里加一份「录屏与讲解视频」的做法：先确认录什么、录完的缺省处理（转录、去口误、检查自动缩放）、哪些事要问用户。

## 14. 待评审事项

- **命令行的 Ctrl-C。** [§12](#12-命令行) 把录制中的第一次 Ctrl-C 定为「停止并保留」，与通用约定不同。要不要这个例外。
- **没有窗口的 Runtime 能不能录。** 命令行自己拉起的 Runtime 没有界面：系统的录屏、摄像头、麦克风权限算在哪个进程头上，没有控制条与倒计时算不算「用户知情」，都没有核实。未定之前这种情况下 `record` 拒绝，请用户打开 BaoCut 再录。
- **未核实的系统接口。** [§7](#7-进程与职责) 里「采集接口可以不画光标」「监听键盘要单独的输入监控权限」「安全输入期间拿不到按键」，以及本稿「控制条不被录进画面」「BaoCut 的窗口可以从整屏的采集里排除」，都要对着两个平台的文档与实机核实之后才算数。
- **BaoCut 自己的窗口。** 缺省不录进去是为了不把会话内容录下来；但用户有时正是要录 BaoCut（做教程）。是做成面板里的一个开关，还是按「选了 BaoCut 的窗口就录」处理。
- **完全访问模式下的 `record`。** [§13](#13-智能体) 定为仍要用户按一次开始。要不要给「我信任这个会话，直接开始」留口子；本稿的立场是不留。
- **按键提示怎样显示。** 键盘轨已经能存，画到画面上的样式还没有定义，要补格式（规范 §10）。
- **图片与渐变背景。** 留边时的底色现在只有纯色（`canvas.background`）；常见的渐变与壁纸背景要么用下层的图片实例，要么给格式加背景的种类。
- **摄像头的布局随段落切换。** 现在靠拆分整组再逐段改；要不要一个「布局场景」的概念（一次定义、多处套用），放在阶段 5 评估，可能要补格式。
- **并入产品设计。** 本稿确认后，入口写进产品设计 §3.2.1、§4.8、§5.9，加一条需求（录屏并在编辑器里继续剪，关联 S11），命令写进 agent-surface 设计 §4.2、§4.3 与 §5.4；在那之前这三份文档不提录制入口。
