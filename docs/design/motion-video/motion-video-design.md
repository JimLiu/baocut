## 1. 问题与目标

### 1.1 现状

- 代码合成已经能导入、验证、烘焙成 ProRes 替身并放上时间线（代码包规范 §3、§7；`packages/runtime-core/src/compositions/`）。但预览与导出只读替身：`render-graph` 把带 `prerender` 的合成当成一段视频，没有替身的记为 `bundle-without-prerender`。编辑器里没有任何运行代码包的路径，检查器的参数页只读。
- 讲解片与 MV 目前靠视频工程外的脚本串起来（配音 → 对齐 → 打包 → 拼装 → 字幕），每段一个代码包、拼装脚本自己记时间线位置；重录一段改变了时长，下游全部要重放，拼装脚本只能报错。预览靠一张自写的网页（iframe 里的代码包跟着 `<audio>` 走），与编辑器无关。
- 时间线上旁白、配乐、音效没有角色：`Track` 只有 `kind` 与 `name`，角色只是实例上开放词汇的 `role`，放置时没有按角色归轨的规则。
- 章节只有序列上的 `chapter` Marker（视频格式规范 §3.13），记时间与标题，不知道哪一章对应哪个代码包、哪段配音、哪段脚本。

### 1.2 目标

对应用户提出的十点：

| # | 要求 | 本文的回答 |
| --- | --- | --- |
| 1 | 集成到 AI 编辑器 | 章节表进视频，章节页进内容面板，智能体用现有工具目录做（§2、§5、§6） |
| 2 | 分章节，每章独立生成 | 一章一个代码包、一个合成实例，章节表绑定三者；重做一章只替换那一章（§2） |
| 3 | 配音、配乐独立轨，同类不重叠时同轨 | 轨道角色与按角色归轨的算法（§3.2） |
| 4、6 | 播放器直接播 HTML 动画 | 舞台上新的「实时合成层」：沙箱 iframe 跟着共用的播放时钟走，替身是后备（§4） |
| 5 | 每章脚本可看可改 | 新的「章节」页：脚本（Markdown）、参考图、配音、代码包版本与状态（§5.1） |
| 7 | 素材都在页里看得到 | 声音页按角色分组；代码包是素材，能定位到文件夹，不要求看代码（§5.3） |
| 8 | 导出 | 烘焙在后台进行、不占视频锁，导出照旧只读替身；过期规则写明（§7） |
| 9 | 研究 baoyu-design 的做法 | 采纳与不采纳的清单（§8） |
| 10 | 不限制模型 | 要求只有四条（可定位、确定、离线、字体随包），章节与脚手架都是约定（§9） |

## 2. 章节表：一章一行

### 2.1 为什么要一张表

现有的几样东西各管一片：Marker 管时间与标题，语音文档管词与句，`NarrationCueSheet`（视频格式规范 §7.10，仍是计划、未实现）管句子到场景的锚，`SoundCueSheet`（§7.9）管声音事件到 `AudioItem` 的编译，`SceneRecipe` / `BuildLedger`（架构设计 §8.6）管一次构建。没有一处把「这一章的脚本、配音、代码包版本、落在时间线上的实例与标记」绑在一起，所以重做一章时既没有可寻址的目标，也没有过期传播的依据。章节表补这一处；它与 `SoundCueSheet` 同一地位：作者意图与构建记录，编译成普通的实例与标记，自己不是第二条时钟。它也取代 `NarrationCueSheet`：每章的词锚就是 `narration.speechRef` 指向的语音文档，镜头意图写在这一章的脚本里；两张表都记「句子 → 场景」，留一张就够。

### 2.2 形状

新的文档种类 `chapter-sheet`，正文 `schema` 为 `baocut.chapter-sheet/1`，一部视频的一个序列最多一张。字段的归属在视频格式规范 §4.6 与新的 §7.12 补全，这里只给概要：

```ts
interface ChapterSheet {
  sequenceId: Id;
  kind: 'explainer' | 'music-video' | 'custom';   // 决定默认的时长归属（§2.3）
  inputs?: { audioRef?: VersionRef; lyricsRef?: VersionRef; scriptRef?: VersionRef };  // 用户给的歌、歌词或讲稿
  chapters: Array<{
    id: Id;                                 // 稿里的章节号（s01、s04b…）就是它；重做不换 ID
    title: string;
    script?: { markdown: string; imageRefs?: VersionRef[] };   // 这一章的脚本正文与参考图，图与文分开存
    narration?: { assetRef: VersionRef; speechRef?: VersionRef };   // 讲解片：这一章的配音与对齐结果
    section?: { start: MediaTime; end: MediaTime };               // MV：这一章对应歌曲的哪一段
    bundle?: { assetRef: VersionRef; revision: Revision };        // 当前采用的代码包版本
    duration: { owner: 'narration' | 'section' | 'bundle' | 'user'; frames: number; tail?: number };
    status: 'planned' | 'narrated' | 'built' | 'placed' | 'stale';
    stale?: Array<'script' | 'narration' | 'bundle' | 'placement'>;   // 哪一层过期了
  }>;
  compiled: Record<Id /* chapterId */, { itemId: Id; markerId: Id; audioItemIds: Id[]; viaTransactionId: Id }>;
}
```

- `chapters` 的顺序就是播放顺序。编译后每章对应一个合成实例（`CompositionItem`，代码包规范 §3.1）、一个 `chapter` Marker 与零到多个 `AudioItem`，映射记在 `compiled`，与 `SoundCueSheet.compiled` 同一做法。回执保留 chapter → item 的 lineage。
- 一章可以没有代码包（只有配音，画面由别的实例提供），也可以没有配音（纯画面章节）。章节表不要求每章都是代码合成；原生元素做的章节同样登记，`bundle` 为空。
- 整部片是一个代码包时，章节表只有一行；章节在包里怎么分由作者自己定。
- 一章至少要有画面归属（代码包或原生实例）或配音中的一样；只有音效不成章，音效是所属章的 cue（`cues.json` 或 `SoundCueSheet`）。章长不设下限：短于一句话的转场章照常成章，章节条画不下标题时只画色块、悬停显示。

### 2.3 谁决定一章多长

一章的时长只有一个归属（`duration.owner`），这条规则决定重做一章之后谁跟着动：

| 片种 | 默认归属 | 规则 |
| --- | --- | --- |
| 讲解片 | `narration` | 章长 = 这一章配音的实际时长 + `tail`（默认 0.4 s，按序列帧率向上取整帧，30 fps 是 12 帧；每章可改）。不按章末标点区别：句末的停顿由配音本身决定，留白只管画面收尾与下一章的衔接。重录配音改变了时长，章长跟着变，代码包必须按新长度重建或接受拉伸（§2.4） |
| MV / 歌词视频 | `section` | 章长 = 歌曲段落的长度，段落来自 `assets_analyze` 的 sections 与歌词的分段，用户可改边界。歌不动，章节的边界也不动 |
| 纯画面章节 | `bundle` | 章长 = 代码包的 `intrinsic.durationFrames`。用户在时间线上拉长或缩短时归属改成 `user`，代码包按 `timeMap` 重映射（代码包规范 §3.5）：作者时间 → 落位时间，等同 baoyu-design 的 authored / placed 两套时间（§8） |

讲解片与 MV 里，章节必须首尾相接、不重叠、不留空（除 `tail`）；`custom` 不作此要求。

### 2.4 过期与重编译

编译（`compile`）把章节表投影到时间线：按顺序累加章长得到每章的 `fromFrame`，新建或移动实例与 Marker（`moveItem`，不重新导入），放置声音实例，写一笔事务。重编译只动位置变了的章节；用户在时间线上手动挪过的实例按 `SoundCueSheet` 同样的 pin 规则处理：保留并提示冲突，或由用户显式重置。

过期沿一条链传播，只标记、不自动重做：

```text
script 改了 → narration 过期（讲解片）→ bundle 过期（词时间变了）→ placement 过期（章长变了，下游章节要挪）
section 改了（MV）→ bundle 过期 → placement 过期
bundle 换了版本 → 若 intrinsic 时长 ≠ 章长且 owner 不是 bundle：bundle 记为「长度不符」，由智能体重建或用户接受拉伸
```

旧拼装脚本「起点变了就抛错」的情形，在这里是 `placement` 过期加一次重编译；下游章节整体挪动，不重新烘焙。

## 3. 时间线落位与分轨

### 3.1 画面

一章的合成实例落在同一条画面轨上（默认名「场景」，`kind: 'visual'`），首尾相接。整条轨就是章节表的投影；章节条（时间线顶部的 Marker 带）与这些实例一一对应，拖章节条的边等于改 `duration`（归属改为 `user`）并重编译。字幕、标题、补充画面照常放在它上面的轨。

### 3.2 声音按角色归轨

实例已有开放词汇的 `role`（视频格式规范 §3.3；按约定用 `narration`、`dub`、`music`、`sfx`、`a-roll` 等，配音流程今天就按它建「Dub (<lang>)」轨）。`Track` 增加可选的 `role`，同一词汇，由落在它上面的实例的 `role` 派生、作为放置的键；实例的 `role` 仍是唯一的来源，轨道只记归轨结果（视频格式规范 §3.3 补全）。归轨算法与该节「重叠时放到相邻轨道」的规则并在一处，由引擎 `AddItem` 的默认轨选择与 `assets_import` 的 `place` 实现；章节表编译、`SoundCueSheet` 编译与智能体放素材都走它：

```text
放一个角色为 R、区间为 [a, b) 的声音实例：
  1. 取 kind = audio、role = R 的轨，按 order 从上到下；
  2. 第一条在 [a, b) 上没有实例的轨就落在那里；
  3. 都有重叠：新建一条 role = R 的轨，名字按角色与序号（旁白 2、配乐 2），放在同角色最后一条的下面；
  4. 没有任何 role = R 的轨：新建第一条，旁白与配音轨在音频叠的最上，其后配乐，其后音效，原声在最下。
```

- 旁白一章一个 `AudioItem`，起点与章的 `fromFrame` 对齐（精确采样位置按视频格式规范 §7.11，不量化到帧）。MV 的歌是一个 `AudioItem` 横跨全片，落在配乐轨。音效（`assets_sfx` 或章节的 `cues.json` 编译出来的）落在音效轨，重叠的才另起一条。
- 代码包的 `output.audio` 在讲解片与 MV 里必须是 `none`（代码包规范 §4.8）：声音全部由轨道上的实例提供，合成自带的声音与外部轨不得同时播（视频格式规范 §7.9 的路由规则）。带声音的代码包导入到这两种片里时记为警告，实例的 `audio.enabled` 置假。
- 空的、没有名字的音频轨照旧不画（`timelineRows`）；带角色的轨有名字，建出来就显示。

## 4. 实时播放

### 4.1 新的层

今天舞台只有一张 WASM 画的 `<canvas>`。要在编辑器里播代码包，舞台增加一种「实时合成层」：每个在视的代码合成一个沙箱 `<iframe>`（`sandbox` 不放网络、不放顶层导航；包内文件经媒体通道按来源放行），由预览引擎按共用的播放时钟驱动：

- `baocut/1`：每个视频帧调一次 `renderAt(time, params)`，`time` 是实例的 `timeMap` 映射后的本地时间；`hyperframes/1`：调 `seek`。两种合同沿用 `packages/code-runtime/src/composition-adapter.ts` 注入页面的同一份脚本；离屏宿主用 `executeJavaScript` 直接调它，编辑器里要改成 `postMessage` 桥接（沙箱 iframe 不开 `allow-same-origin` 时父页面调不进去），桥的两端与 sandbox 的取值随 §4.2 一起验证。
- 播放中按显示器刷新驱动但一个视频帧只送一次（与架构设计 §9.4 的现规则一致）；定位时送目标帧并等两次 `requestAnimationFrame` 再认为「到了」。
- 当前章与前后各一章的 iframe 预先载入（`initialize` 跑完、第 0 帧画好），其余按需；一次最多挂 3 个，超出的 `dispose`。
- 层的几何按实例的 `place`、`fit` 与画布比例摆，与替身是同一套（`item_box.rs` 把合成当媒体算，继续用）。

### 4.2 与画布的叠放

第一期实时层只放在**最底**：实时合成层 → 现有画布（透明底）。帧计划（`render-graph`）增加一个「从某个 order 起画、底下留透明」的切点，画布上只画合成以上的层（字幕、标题、补充画面）；这是讲解片与 MV 的全部形状（合成是满幅的底）。选这个形状的理由：舞台今天就是一张绝对定位的 `<canvas>`，底下垫一个同几何的 iframe 只是 DOM 顺序，内核只要少画几层、不填背景，不需要第二张画布。合成夹在两段视频之间、或两个合成同一帧重叠时，退回替身；一般形状的三明治（下层画布 → 实时层 → 上层画布）留到后期，按需要再做。切点的实现要在 `preview.tsx` / `render-graph` 上实测（§13）。

### 4.3 与替身的关系

- 实时层的帧是 Interactive / Draft（架构设计 §9.4），界面不得把它标成 Export-Exact。
- 停住时（暂停、定位落地 200 ms 后）：有替身且替身不过期（§7.2）就画替身那一帧，这才是导出的那一帧；没有替身或替身过期时继续显示实时层，舞台右上角的「画不出来的东西」改成一句「实时预览，导出前要烘焙」。
- 代码包载入失败、`renderAt` 抛错或 3 秒内没就绪：退回替身；替身也没有就是现有的占位（代码包规范 §7.3）。
- 声音始终来自轨道上的实例，由现有的 `<audio>` 元素播；实时层不出声。
- 舞台点选、拖动仍按实例的几何盒算（`stage-pose.ts`），iframe 上盖一层透明的拾取面，指针事件不进包。

### 4.4 导入即可播

`compositions_import` 完成第二笔事务之后实例就能在编辑器里实时播，烘焙改为后台任务（§7.1）。智能体给用户看一章的间隔从「烘焙完」缩短到「导入完」，这是用户第 10 点里「更快给出反馈」的主要来源。

## 5. 编辑器界面

### 5.1 「章节」页

内容面板新增一页 `chapters`（工具栏名「章节」），只在视频有章节表时出现；没有章节表的视频，章节仍只在时间线顶部的章节条与文稿页的章节标题里。页里一章一张卡，按顺序列出：

- 头：章节号与标题、时长、状态词（计划中、已配音、已生成、已上线、过期；过期写明哪一层：脚本、配音、画面、位置）。点卡把播放头放到这一章的开头，播放跟随时当前章高亮，与文稿页的跟随同一机制。
- 脚本：Markdown 正文，可直接编辑；旁边是参考图缩略图（`imageRefs`），点开看大图。保存脚本只写章节表，随即把这一章标为「脚本已改」。图与文分开存、不做富文本编辑器：脚本是给智能体与配音读的纲要，Markdown 够用，参考图单独成素材才能被 `compositions_import` 与图片页复用。
- 配音：音频条目（时长、播放），MV 时换成「歌曲 0:42–1:08」。
- 画面：代码包的名字与版本号、「在文件夹中显示」；没有代码查看与编辑（用户第 7 点不要求，列为将来）。
- 动作：「交给智能体重做这一章」把这一章的 ID、脚本、过期项作为引用标签放进会话输入框（产品设计 §3.2.3 的引用标签）；「只重配音」「只重画面」是同一动作带不同范围。界面自己不生成任何东西。

章节页是内容面板独立的一页，不并入文稿页：文稿页保留今天的职责（词级时间、剪口播、改字），讲解片的配音转写进文稿页照常显示，章节标题来自同一组 Marker。脚本正文（计划说什么）与转写（实际说了什么）是两样东西，编辑动作也不同（改脚本触发重做，改转写只改字），并成一页的模式只会让两套状态挤在一起；章节页在 Web 宿主也显示。

### 5.2 检查器与时间线

- 选中合成实例时检查器的合成页（`inspector-elements.tsx` 的 `CompositionPage`）补上：可调参数按参数 Schema 出控件并真正写 `setCodeParameters`（引擎已有，界面今天只读）；版本号与「换回上一版」；所属章节与「在章节页里打开」。
- 时间线上合成实例的标签写章节号与标题；过期的实例在条上加角标。章节条的边可拖（改 `duration`，§3.1）。
- 轨道头按 `role` 显示角色名（旁白、配乐、音效、原声），后面接序号。

### 5.3 素材

- 声音页（`audio` tab）按角色分组列出：旁白（按章节排）、配乐、音效、用户给的原始音频（`inputs.audioRef`，MV 的歌、讲解片外部录的旁白）。每条能播放、能看在哪些章节用到。
- 代码包是目录素材（代码包规范 §2.5），在素材里以「代码包 · 版本」显示，操作只有「在文件夹中显示」与查看 `verification.json` 的摘要；替身继续标「预渲染替身」并阻止替换（今天的规则）。
- 参考图、封面图在图片页里，带「章节 sNN 的参考图」标签。

## 6. 智能体的工作流与工具

### 6.1 讲解片

```text
讲稿（用户的或智能体写的）→ 按章拆成章节表（planned）
  → 每章配音（speak）并对齐（align 按讲稿取词时间）→ narrated
  → 每章按配音的词时间写代码包（code-scenes 的约定：lines.js、cues.json）→ compositions_import --chapter sNN → built / placed
  → 字幕（captions_create 用讲稿原文 + 对齐时间）→ 整片实时预览 → 用户在章节页给反馈 → 只重做被点名的章
```

代码包的编写约定沿用 `video-production/references/code-scenes.md`（整帧分段、确定性、字体随包、第一帧即封面），只把「一段」改称「一章」，并把拼装的职责交给章节表的编译。

### 6.2 MV / 歌词视频

```text
歌（MP3）+ 歌词 → assets_import（配乐轨，inputs.audioRef）
  → align 按歌词原文取词时间（§6.3）→ assets_analyze 取节拍、段落
  → 按段落建章节表（section 归属）→ 每章一个代码包，lines.js 取该段的词时间，cues.json 取节拍
  → compositions_import --chapter → 实时预览 → 反馈 → 重做某段
```

歌是唯一的声音；代码包静音。歌词视频与 MV 的区别只在画面风格，流程相同。

**有原文时先对齐，再退到转写**。强制对齐（`align`）拿着用户的原文只求时间，与现行「转写取时间、文字以原文为准」没有冲突：后者是没有对齐工具时的替代做法，靠识别出的字去对原文、对不上的行不估时间。两条路并存只为两种情形：原文与实际唱、说的不一致（即兴、副歌重复次数不同、歌词版本不对）时，对齐会硬把原文压上去、给出低置信的时间，转写对位反而能暴露差异；以及当前的转写模型没有 `align` 能力（本机 Qwen3 forced aligner 有，云端转写没有）。规则：给了原文就先 `align`；`coverage` 低于阈值或 `lowConfidence` 过多时改走转写对位，并把对不上的行报给用户。

### 6.3 工具的增减

尽量不加新动词，改在现有工具上加参数：

| 工具 | 变化 |
| --- | --- |
| `documents_put` / `documents_read` | 接受 `chapter-sheet` 种类；写章节表就是建章节 |
| `chapters_compile`（新） | 把章节表编译到时间线（§2.4），返回每章的 `compiled` 与过期项；`--dry` 只报不改 |
| `compositions_import` | 新参数 `chapter: <chapterId>`：代入该章的位置与时长，首次放实例、之后等同 `replace` 那一章的实例，并更新章节表的 `bundle`。与 `place` / `replace` 互斥。导入后立刻返回，烘焙转后台（§7.1） |
| `assets_import` / `assets_sfx` | `place.role`：按 §3.2 归轨；`place.chapter`：起点取该章开头 |
| `compositions_preview` | 增加 `chapter`，按章节取帧；默认取这一章的首帧、尾帧与边界前后 0.15 s（§8 的边界拼图） |
| `videos_inspect` | 结果里带章节表摘要与过期项，智能体一眼看到要重做哪几章 |
| `align`（新） | 把用户的讲稿或歌词按音频强制对齐，写成 `stages.aligned.mode: 'script'` 的语音文档。运行时已有这项能力（Qwen3 forced aligner），只缺工具与 CLI；没有 `align` 能力的模型时工具返回 `CAPABILITY_NOT_CONFIGURED`，智能体按 §6.2 的规则退到转写对位 |

skill 侧：`video-production` 的代码场景一节改写为按章节表工作；`SKILL.md` 路由表的 MV 一行指向同一流程。

## 7. 烘焙与导出

### 7.1 后台烘焙

- `compositions_import` 的两笔事务只登记代码包与放实例；烘焙成为一项 Job（新的 Job 种类 `bake`），完成后以一笔事务写入替身素材并把实例的 `prerender` 指过去。Job 在跑时不持有视频的写锁：用户与智能体可以继续改别的章节；写入替身那一笔按正常的版本冲突重试。这解决旧工程「拼装时不要同时改这部视频」的限制。
- 多章同时导入时烘焙串行排队（指令烘焙本身已多线程光栅，并行只会争 CPU）。
- 烘焙只在桌面端可用（需要 Electron 离屏宿主）；Web 宿主导入只到「可实时播」，导出时提示到桌面端烘焙（§10）。

### 7.2 替身何时过期

补全代码包规范 §9 的这一项：替身的 `BakeRecord.sourceBundleRef`（bundleId / revision）与实例当前的 `source.assetRef` 不一致，或替身的 fps 与序列不同，替身即过期。过期的替身预览不用（§4.3），导出预检记为 `prerender-stale`：默认失败并列出要重烘的章节；用户显式允许时按旧替身导出并在报告里写明。

### 7.3 导出

导出路径不变：读替身、走同一份帧计划。章节表与实时层都不参与导出，所以导出的像素与今天完全相同。导出报告按章列出用的替身版本与烘焙方式（指令 / 像素）。

## 8. 从 baoyu-design 借鉴什么

baoyu-design 的 animated-video 把一部动画写成一个 React 树，整体是作者时间 `T` 的纯函数；页面里一段 JSON 字面量 `OM_SCENES` 列出全部场景（名字、时长、说明、`nat` 作者锚点），宿主能读它、改它、写回去；时间拉伸把同一段作者切片重放到新长度上；验证靠边界前后 ±0.15 s 的拼图；参数在 `TWEAK_DEFAULTS` 面板里。

采纳：

- **场景表是唯一的结构来源**，宿主能寻址、能写回 → 章节表与 `compiled`（§2）。
- **作者时间与落位时间分开**，宿主拉伸不改源码 → 纯画面章节的 `timeMap`（§2.3）；有配音或歌的章节时长另有归属，不采用拉伸。
- **边界拼图验证** → `compositions_preview --chapter` 的默认取帧（§6.3）。
- **参数面板** → 代码包规范 §3.2 的参数 Schema 在检查器里真正可调（§5.2）。
- **单一纯函数 `render(T)`** → 这正是 `baocut/1` 的 `renderAt`，不另立合同。

不采纳：

- 只认 React 的运行时与组件库；BaoCut 的合同不绑框架（代码包规范 §1.2）。
- 整部片一个页面：章节化之后每章一个包，重做一章不动其他章；整片一包仍然允许（§9）。
- 宿主改 `OM_SCENES` 后由模型改源码来对齐时长：这里由章节表与 `timeMap` 承担，源码只在画面要变时才改。

- 为 baoyu-design 的定位事件（`data-om-seek-to-time-frame`）另加一种合同：只为兼容一个生成器没有必要，它的页面要进 BaoCut 时在包里加一个几行的 `baocut/1` 适配壳即可。

## 9. 要求与约定的边界

对代码包的**要求**只有代码包规范已有的四条：能按时间定位（`renderAt` / `seek`）、同一时间同一画面（代码包规范 §4.2 确定性）、离线（代码包规范 §2.4、§2.6）、字体随包。满足这四条的任何 HTML（Canvas 2D、WebGL、Three.js、p5、DOM 动画、HyperFrames）都能导入、实时播、烘焙。

以下全是**约定**，模型可以不遵守、用户可以不要：

- 一章一个代码包。整部片一个包、一章几个包叠着放，都成立；章节表只记映射。
- `lines.js` / `cues.json` / `post-fx.js` 的文件布局与 motion-graphics 的脚手架：skill 里的做法，便于走指令烘焙，不是合同。
- 指令烘焙的条件（单张 Canvas 2D、不读回像素……，代码包规范 §7.2）：不满足就走像素烘焙，慢但同样导出。
- 第三方图形库（Three.js、p5、D3 等）：合同不限制库，库文件随包带着即可（网络 deny，代码包规范 §2.4、§4.3、§4.4）。`.glb` / `.gltf` / `.hdr` / `.ktx2` 等 3D 资源加入扩展名白名单（§12）。WebGL、SVG 与 DOM 画面在 iframe 里实时播没有差别，烘焙走像素烘焙；p5 的 2D 模式底下是一张 Canvas 2D，录制器不支持的调用会让它回退到像素烘焙。
- 竖版、画幅、章节时长、留白：都来自内容与用户。

这份设计给模型的是更快的反馈回路：导入即播、章节页点名重做、边界拼图。生成空间与今天相同。新增能力（比如一个新的图形库）不需要改任何实例类型（架构设计 §8.1）。
