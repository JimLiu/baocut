## 1. 口径

### 1.1 条目是定义，不是结果

本文的每一条验收都是**待实施的验收合同**。条目写在这里，不表示它已经被执行，更不表示已经通过。

- 执行状态由测试记录维护，不写在本文里。
- 表格存在不等于测试通过。公式复算、文档检查或静态核对，不能代替对产品实现的测试。
- 某项能力尚未开放时，对应的条目标为「不适用（能力关闭）」，并确认该能力在界面与智能体两侧确实被禁用。不能把没有执行的条目记为已通过。

### 界面图标检查

按[产品设计 §2.1](../product/product-design.md#图标尺寸与语义)，在浏览器 100% 缩放和 Electron 桌面窗口分别检查：

- Rail 的 workflow 画布为 20 × 20 CSS px；Home／Space／设置页面侧栏为 16 × 16，Home 新建会话使用 AddCircle。
- Rail 以外的 workflow 图标一律 16 × 16：页面主要操作、Home 输入框与快捷开始、菜单项、模型页签、列表文件类型、收藏、行尾操作、会话状态和工作区标签类型图标；工具卡、服务卡等图标块内的标识图形为 20 × 20。
- 标题栏外壳图标（侧栏开关、标签页按钮、完整视图、会话摘要、隐藏标签页 / 进入分屏视图）与侧栏浮层的「固定侧边栏」：glyph 渲染盒为 20 × 20，居中于 32 × 32 的方块按钮，与会话菜单 ··· 同高；已打开标签页列表的行尾按钮为 24 × 24。这是 Rail 以外唯一的 20 × 20 渲染盒，其余 workflow 图标仍为 16 × 16。
- Space 查看框、菜单、弹层等 portal 内容同样为 16 × 16；同一组图标不因文字大小出现 14、18、21px 等其他尺寸。
- 只测 workflow 图标画布与外壳图标渲染盒；组件 UI 图形、插画和素材预览按各自规格检查。图形安全留白不计作尺寸不一致。
- 原有按钮点击区域、键盘焦点、tooltip 和导航行为不变；浅色、深色均可辨认。

### 1.4 一条验收怎样才算通过

- 「必须观察到」的每一项结果都被观察到，并且有记录可查（回执、事件、文件、截图或录音的引用）。
- 没有出现 §3.2 列出的阻断级问题。
- 记录中写明执行环境：操作系统与设备、Runtime 与引擎的版本、相关 Adapter 与模型的版本、使用的夹具。
- 涉及人工判断的条目（听感、语义、叙事）有审阅人与问题分级，不用自动评分代替。

## 2. 测试策略与评估方法

### 2.1 固定的任务集

建立一组固定的、可以重复的任务，覆盖：

- 本地的原生编辑；
- 双语字幕；
- 录屏；
- 配音驱动的动画；
- 代码合成；
- 错误恢复。

每个任务包含：素材、目标、硬约束、允许修改的范围、用户反馈的轮次，以及预期可以观察到的结果。

### 2.2 三种验收方式

| 方式 | 检查什么 | 不能替代什么 |
| --- | --- | --- |
| 自动检查 | 视频的差异、时间关系、回执与事件、文件的格式与完整性 | 语义与听感 |
| 人工查看与试听 | 重要片段的画面、字幕、声音与叙事 | 可以自动判定的结构正确性 |
| 真实用户完成连续任务 | 是否能理解、能接管、能继续修改 | 自动回归 |

内容的语义、叙事效果与自然度，不能只用自动评分代替。

### 2.3 测试层次

| 层 | 对象 | 重点 |
| --- | --- | --- |
| 引擎单元与性质测试 | 时间运算、量化、映射、事务、依赖失效 | 精确的有理数预期值；随机生成的编辑序列保持不变量 |
| 合同测试 | 命令、回执、事件、错误码、Adapter、Driver、Provider | 形状与语义符合规范；版本不兼容时明确拒绝 |
| 集成测试 | Runtime、引擎宿主、任务调度、存储 | 幂等、恢复、停止屏障、授权 |
| 故障注入 | 崩溃点、断线、磁盘不足、响应丢失、租约过期 | 每个失联点的恢复行为符合恢复矩阵（架构设计 §7.5） |
| 渲染一致性 | 预览与导出、不同后端 | 语义与时间映射一致；像素差异有声明的容差 |
| 端到端 | 十二个工作流与两个三轮演示（产品设计 §9） | 真实的预览、可编辑的结构、要求的成片 |
| 界面 | Home、Space、编辑器 | 状态表达、键盘可达、布局保持、发送前同步 |

### 2.4 夹具

- 夹具使用原创的、明确授权的或程序化合成的素材。不分发来源或许可不明的素材。
- 至少包括：30 分钟的口播；带多层转场的短片；10 秒的 Three.js 合成；1 分钟的 sequential p5.js 合成；带音频的 Remotion 合成；混合视频；长片的翻译配音；多语言批量导出；可变帧率的手机素材；30000/1001 fps 的长片。
- 只对发布范围内的能力执行发布门槛。其余的夹具保留，用于扩展。

### 2.5 涉及模型的测试

- 自动回归可以使用固定的模型产物，或模拟的模型服务。
- 这样的测试只证明流程与合同，**不能被说成真实模型的效果已经通过**。
- 真实模型的效果用人工审阅记录与问题分级来裁定，并记录模型的版本。

### 2.6 基准的记录

每次性能或时间相关的基准，必须分别记录：

- 设备、操作系统、GPU 与驱动；
- Runtime、引擎、Adapter 与浏览器的版本；
- 媒体与视频的规模、缓存的冷热状态、输出的质量档；
- `editFps`、`outputFps`、源素材的 timebase、代码包的 fps；
- 输入的精度、`timeContractVersion`、采样与舍入的政策；
- 逻辑范围与编码之后的尾端。

源码注释里的帧率，或作者的估计，都不是实测基准。

### 2.7 用户研究

用户研究先建立基线，再设定正式的完成率目标。不虚构当前的转化率或行业对比。成功指标的口径见产品设计 §11.4 与 §11.5。

## 3. 发布门槛

### 3.1 门槛

发布一个阶段，必须同时满足：

1. 开放范围内的全部 G 条目通过；
2. 该阶段要求的 P0 条目通过（§3.3）；
3. 没有 §3.2 列出的阻断级问题；
4. 性能目标在发布测试矩阵上有实测记录（§4）；
5. 没有开放的能力确实处于关闭状态，界面与智能体都不宣称能够执行。

### 3.2 阻断级问题

出现以下任何一项，不得发布：

- 未经授权的数据外发；
- 已确认的视频内容丢失；
- 锁定或保护的内容被误改；
- 状态未知时自动重复付费；
- 结果被应用到错误的目标；
- 没有文件却报告导出成功；
- 把候选说成已应用，或把未发布的导出说成成片；
- 不可信的代码越过隔离读取文件或访问网络。

### 3.3 各阶段的出口

| 阶段 | 出口条件 | 主要条目 |
| --- | --- | --- |
| R0 体验与合同基线 | 快照与事件无缺口；命令重试与崩溃时的提交安全 | A01–A05、C01–C03、C05、C06、TM01–TM07 |
| R1 可委托的编辑 | 改字、加元素、撤销、预览、导出可用；不改错对象 | AT-04、AT-11、AT-18、AT-24、AT-25、UI-01–UI-06、T05–T08、T30–T32、M01、M02、M06 |
| R2 P0 双闭环 | 两个闭环各连续三轮；全部已开放的 G 条目 | 全部 P0 的 AT 与 UI；T、A、C、M、TM 中属于已开放能力的条目 |
| R3 完整版 | 原版本不被误伤；源码可以维护；输入过期与费用对账完整 | 全部 P1 的 AT；T17–T20、T26、T27、T38 |
| R4 加固与规模 | 有实测报告；未验证的快速路径保持关闭 | §4 的全部指标；M07、M08、M11、M12、M20 |

R0 与 R1 的前半按四个起步版本交付，各自的出口：

| 版本 | 出口条件 | 主要条目 |
| --- | --- | --- |
| 0.1 最基本的智能体 | 一个回合经 Driver 完整往返；中断与审批经 Harness；会话可以重开；事件流无缺口 | AT-20、AT-34、A05、A07、A10、C06 |
| 0.2 外壳 | 入口切换、项目与会话列表可用；界面重载或断线不取消运行中的回合 | UI-01、UI-02 中不涉及视频的部分；A04 |
| 0.3 播放器 | 画面、声音与字幕同步；不修改任何文件 | T30 |
| 0.4 编辑器 | 与 R0 相同 | A01、A03、C01–C03、C05、T05、T06、TM01–TM07；UI-04 中打开视频的部分 |

各阶段与起步版本的内容见产品设计 §11.1。P0 的出口在 R2。

### 3.4 性能与语义质量

- 性能目标在发布测试矩阵中明确测量。无法达标的复杂代码场景必须缩小支持范围，或使用有标记的代理预览。不用平均数掩盖不可用的设备。
- 语义质量用人工审阅记录与问题分级裁定。建议值不包装成保证。

## 4. 性能目标

这些是**待基准校准的目标**，不是已测结果。

| 指标 | 目标 | 必须记录 |
| --- | --- | --- |
| 接收操作并显示它绑定的范围 | 本地 P95 ≤ 500 ms | 操作类型、视频规模、界面与 Runtime 的版本 |
| 停止新的调用与自动提交 | 本地 P95 ≤ 1 s | 停止屏障的确认点、提交的线性化点、未能取消的外部 Job |
| 常见的原生内容热缓存定位 | P95 ≤ 150 ms | 帧率与分辨率、设备、缓存状态、输入帧与显示帧 |
| 纯原生字幕的视频 | 代码浏览器 Worker 的启动数为 0 | 实际的执行路径 |
| 只改原生字幕之后的二次导出 | 没有变更传递依赖时，代码内部的求帧调用数为 0 | 缓存键、背景依赖、命中与失效的原因 |
| 长片的内存 | 随流式窗口受控，不随片长线性增长 | 峰值 RSS、可观测的显存、buffer 池、背压 |
| 大时间线与长文稿的滚动、缩放 | 已挂载的节点数与更新量受可见窗口的预算控制 | 规模档位、可见窗口、P95 帧耗时 |

说明：

- 「停止」的目标指的是停止新的调用与自动应用，不是供应商已经停止计费（架构设计 §7.4）。
- 规模档位、可见窗口与 P95 门槛在固定的设备上冻结之后才成为发布门槛。
- 服务恢复、会话恢复、任务恢复分别测量。

**M12 基线（2026-10-06）**：「大时间线与长文稿的滚动、缩放」在一台开发机上的首次实测，用来定规模档位与可见窗口。单台机器不是冻结的设备矩阵，这些数字不是门槛。同样规模的合成夹具与同一量法可用 `npm run bench:panels` 复测（[开发流程 §2](../development-workflow.md#2-验证)）。

**成片导出基线（2026-10-12）**：`node tools/export-bench.ts`（[开发流程 §2](../development-workflow.md#2-验证)）在一台开发机上的结果，用来比对之后的改动，不是门槛。

- 环境：Apple M4（4 个性能核、6 个能效核）、16 GB、macOS 27.0；release 构建的 Worker（含下面两处修复、整帧填充与拷贝的削减和调度优先级），AVFoundation 解码与编码；1 分钟负载 3–6。
- 合成夹具（缺省：60 秒、双语、`studio-color`，24 句），各 3 次的中位数：`cover` 217.5 fps、`contain` 218.3 fps（4.6 ms/帧）。
- 一个真实工程（1920×1080、30 fps、900 帧，双语逐词字幕；`--input`），交替各 3 次的中位数：两处修复（`d5f98799` 去掉整幅的发光扫描、`9925ed96` 逐词变色不再把帧号放进缓存键）之前 75.5 fps；`9925ed96` 215.0 fps；再加上整帧填充与拷贝的削减和调度优先级 216.4 fps，字幕层光栅 151 次。空闲时 `9925ed96` 之后的改动被硬件编解码的吞吐挡住，看不出差别；1 分钟负载约 10 时，削减整帧填充、拷贝与扫描（架构设计 §9.11 输出帧的那条）前后是 167 与 211 fps（两边都关着调度优先级，交替 5 次的中位数）。
- 字幕效果层复用（架构设计 §9.12）：另一个真实工程（1920×1080、30 fps、4575 帧，阴影＋描边的逐词变色，字幕层光栅 853 次），空闲时两边都顶在 219 fps 左右；Worker 进程每帧的 CPU 时间（用户＋系统）交替 5 次的中位数 4.79 → 4.12 ms（1 分钟负载 4.5–5.6），每一对都省。主线程采样里字幕光栅的占比 38.5% → 21.8%，其中画效果层笔划的 18.5% → 1.6%。每帧都在变的效果层（弹跳＋发光＋入场，600 帧光栅 574 次）没有变慢（9.59 对 9.40 ms/帧）。
- 字幕重画的门禁是确定性的，不靠计时：`subtitle-render` 的 `caption_layers_are_redrawn_only_when_the_picture_changes`（架构设计 §9.12）。

**导出的调度优先级（2026-10-12）**：[架构设计 §9.11](../architecture/architecture-design.md#911-冻结导出与发布)「调度优先级」在一台开发机、一个工程上的实测，不是门槛。

- 环境：Apple M4（4 个性能核、6 个能效核）、16 GB、macOS 27.0；release 构建的 Worker（含整帧填充与拷贝的削减），同一个二进制按 `BAOCUT_EXPORT_PRIORITY=0` 开关对比；一个真实工程，1920×1080、30 fps、900 帧，烧双语逐词字幕，AVFoundation 解码与编码；命令行直接跑 `export-worker render`，帧率是 `frames / renderSeconds`。
- 量法：开、关交替跑，每轮轮换先后，取中位数；忙进程是每次运行新起的 `yes > /dev/null`（默认 QoS）。机器上同时有别的会话的进程，负载照实记。

| 抢 CPU 的 | 开（帧/秒，中位数） | 关 | 每一对 |
| --- | --- | --- | --- |
| 别的会话的进程（1 分钟负载 14–21），5 轮 | 200 | 160 | 开着都快 |
| 6 个忙进程（负载 5–7），4 轮 | 214 | 195 | 开着都快 |
| 12 个忙进程，多过核数（负载 12–25），4 轮，另 2 对逐线程采样 | 102 | 159 | 开着都慢 |

此前在负载上百（别的会话大量编译）时，用减少拷贝之前的构建测过 6 组，5 组开着快。12 个忙进程时，开着的 Worker 自己的线程用的 CPU 反而少（合成线程约 55%，关着时 68–82%），每帧的 CPU 时间相同，也就是在等。等的是编码管线：合成线程约七成时间等编码队列空出缓冲，编码线程九成以上在等写入器就绪，AVFoundation 内部的线程本身用的 CPU 很少，慢在被挤掉之后排队。上表是视频轨还按离线源声明时测的，见下一段。

**视频轨声明为实时源（2026-10-12）**：同一台机器、同一个工程，同一个二进制按诊断开关对比写入器视频轨的 `expectsMediaDataInRealTime`（关＝离线源，开＝实时源），都开着调度优先级。

| 条件 | 实时源（帧/秒） | 离线源 | 说明 |
| --- | --- | --- | --- |
| 不加忙进程（1 分钟负载 15–18），3 轮 | 208 | 206 | 都顶在硬件编码的吞吐上 |
| 12 个忙进程（负载 18–27），4 轮 | 183（138–202） | 59（48–89） | 每一对实时源都快；编码线程每次运行等就绪的次数 61–865 对 9 千–2.2 万 |
| 带声音（30 秒 WAV 混音），12 个忙进程，各 1 次 | 206 | 37 | |

- 画质与码流：两种都是 High、有 B 帧、900 帧里 16 个关键帧，码率都是 8.86 Mbps；对近无损的参考（`BAOCUT_EXPORT_NATIVE=0` 加 `crf: 1`）的 PSNR 都是 49.90 dB、SSIM 都是 0.99556，12 个忙进程时实时源 49.92 dB。
- 封装：moov 都在前；按文件顺序扫包，音视频的最大偏斜实时源 0.47 秒、离线源 2.14 秒；音视频时长与帧数相同。
- 内存：进程峰值（phys_footprint）337 MB 对 315 MB。
- 完整工程（4575 帧，正式构建）：不加忙进程 207–213 fps（3 次）；12 个忙进程时实时源 93 与 147 fps（2 次，其中 147 那次挂着逐线程采样，两次都另有别的会话在大量占用 CPU），改动前的构建 53 fps（1 次）。离线源的构建不加忙进程时偶尔整次落到 54–83 fps，那时别的进程（spindump、另一个应用的渲染进程）正大量占用 CPU。
- 完整工程、20 个忙进程（多过核数近一倍，负载 22–31），实时源的正式构建 4 次：中位数 212 fps（197–216），每帧 CPU 5.7 ms，仍顶在硬件编码的吞吐上。
- 试过没有采用：读帧线程读前 8 帧（1080p）对 2 帧，20 个忙进程交替 10 轮（900 帧 6 轮、完整工程 4 轮）分不出差别（中位数 208 对 206、215 对 212），每个解码器多占约 48 MB，不改。

## 5. 实验失败时的规定行为

以下各项能力需要实验验证。产品行为已经固定；实验只决定能力是否开放。**验证没有通过时，按右列执行，不由实现者临时决定。**

| 待验证项 | 没有通过时的规定行为 |
| --- | --- |
| Rust 与 WASM 的字幕布局一致性 | Export-Exact 走同一个实现；Interactive 预览标示差异 |
| 动态字幕场景 | 样式/参数严格校验，词时间不伪造；分页、逐词弹入、连续波浪、随机 seek 与实例隔离验证；native/WASM 黄金帧逐字节相同，旧字幕夹具保持不变 |
| 各操作系统上浏览器的 alpha 与视频呈现同步 | 禁用出问题的快速捕获路径，使用验证过的基线路径 |
| Remotion 的 props、音频、透明与区间导出 | 按能力矩阵关闭不支持的合成，不包装成通用支持 |
| 跨进程的 GPU surface 共享 | 使用受控的 CPU buffer 或中间文件，不承诺零拷贝 |
| sequential 检查点的可恢复性 | 从起点重放，或使用已验证的片段缓存 |
| Provider 的取消与幂等 | 尽力而为的状态加对账，不冒充恰好一次 |
| 多语言时长自动适配的听感 | 标为 `needs-fit` 并交人工审阅，不强行导出 |
| 不同 GPU 上的像素一致性 | 固定执行环境，或声明容差；不跨环境复用严格缓存 |

| TM11 | 连续的原生曲线在 1 秒内从 0 到 100，30 → 60 fps | 第 1 个输出帧在 t = 1/60 秒，x = 5/3；不先吸附到视频帧 | §2.11；架构设计 §9.10 |
| TM12 | 30 fps 的父层、24 fps 的嵌套序列、60 fps 的输出 | 连续的对象传递精确的时间；离散取帧只发生在源的边界上 | §2.5；架构设计 §8.5 |
| TM13 | 帧驱动的代码包；sequential 的 `fixedStep` | 帧率按作者的合同；步率不随导出帧率改变；返回实际的采样 | 代码包规范 §5.3、§5.4 |
| TM14 | 可变帧率的展示时刻 0 / 40 / 100 / 130 毫秒，请求 75 毫秒 | 选择 [40, 100) 的样本；不按平均帧率或 DTS 选帧 | §2.6 |
| TM15 | 30000/1001 fps 下一百万个输出帧的微秒时间戳 | 每一帧都从绝对值计算；末端等于直接换算；误差不逐帧积累 | §2.13 |
| TM16 | 精确的 10 秒以 30000/1001 fps 导出 | `cover-range` 得到 300 帧、10.010 秒；`exact-grid` 被拒绝；没有暗中的音频拉伸 | §2.11 |
| TM17 | 把序列从 30 fps 改为 60 fps，`preserve=time` | 帧坐标按比例变换；真实时长与音频位置不变；单笔事务提交 | §2.12 |
| TM18 | 30 → 25 fps；锁定的轨道；零长度；`preserve=frames` 未支持 | 给出影响与量化的报告；不满足硬约束或能力时拒绝；不部分修改帧率 | §2.12；命令与协议规范 §6.5 |
| TM19 | `frameIndex` 相同、输出帧率不同的求帧、缓存与证据 | 请求的身份不同；局部样本只在全部依赖相同时复用 | §2.13；架构设计 §8.4 |
| TM20 | 预检之后修改帧率；导出冻结之后修改帧率 | 新的提交返回版本冲突；已启动的导出保留旧快照；重试返回原回执 | 命令与协议规范 §6.3；架构设计 §9.11 |

独立的脚本可以验证其中一部分有理数的预期值。但这张表里涉及应用、音频、Adapter、缓存、并发与界面的行为，必须由真实的实现测试。

### 6.8 版本记录验收 V01–V12

视频的工作区快照与版本记录（视频格式规范 §9，架构设计 §5.12）。

| ID | 场景 | 必须满足 |
| --- | --- | --- |
| V01 | 同一状态写两次快照；改一个实例的一个字段 | 两次逐字节相同，第二次不重写文件；改一个字段的 diff 只改一行，文档没变不重写 |
| V02 | 一串编辑之后回到第 k 版，或回到最旧版本之前 | 得到的快照与当时写出的逐字节相同；作为一笔可撤销的修改提交并单独成一个 `restore` 版本，撤销后回到之前；已经是那个样子时不提交 |
| V03 | 篡改、删掉或写坏一个中间的版本文件，再回到它之前 | 以 `VERSION_CHAIN_BROKEN` 拒绝并报告断开的序号，视频不变；更新的版本照常回得去 |
| V04 | 没有超过 5 分钟停顿的一串手工与智能体修改；关闭后 5 分钟内重新打开继续改 | 只有一个版本，动作清单按执行者与标签列全；满 30 分钟、保存、回到版本或按回合切分的新回合才开新版本 |
| V05 | 版本数超过 `versions.keep`，或 `history/` 超过 64 MiB | 删最旧的未命名版本，保存的版本与最新一版保留，链保持连续，剩下的每一版都回得去 |
| V06 | 保存版本，再删掉它 | 保存的版本带名字与检查点，不被清理；删掉时两侧的 diff 合并、检查点一起删；不是保存的版本不能删 |
| V07 | 被保留的版本引用的收进来的素材，在关闭视频的 blob GC 之后 | 仍在；回到那个版本时素材完整 |
| V08 | 删掉 `video.db` 后打开项目或打开视频 | 按快照重建，`videoId` 不变，重建后立即写出的快照与读入的逐字节相同；有版本文件时版本记录照常可用并多一个 `rebuild` 版本，没有时从重建开始 |
| V09 | 快照被 BaoCut 之外改了 | 不覆盖，状态是 `conflict` 并列出文件；编辑与关闭照常；保存与回到版本以 `SNAPSHOT_CONFLICT` 拒绝 |
| V10 | 关闭视频后立刻重新打开 | 等关闭写完快照、放下写锁再打开，重新打开的视频照常可改，修改照常进版本 |
| V11 | 不属于项目的视频 | 不写快照、没有版本；保存与回到版本以 `VERSIONS_NEED_PROJECT` 拒绝 |
| V12 | 没有 git | 版本记录的全部功能可用 |

二期（外部改动的导入、git 桥）的验收要点在[版本记录设计 §9](../design/version-history/version-history-design.md#9-分期与验收要点)，实施时移到这里。

自动化检查：

- 引擎（`crates/video-engine/tests/version_history.rs`）：V01（基线与一行的 diff）、V02（回到版本、回到最旧版本之前、撤销、重试与相同状态）、V03（篡改中间版本）、V04（安静期、时长与回合的边界）、V05（按数量清理后链连续）、V06、V07、V08（重建逐字节相同、`rebuild` 版本）、V09 的引擎部分；另有版本文件能被 `patch -R` 逐版退回。
- Engine Host（`crates/engine-host/src/host.rs` 的 `versions_round_trip_through_snapshot_restore_save_delete_and_rebuild`）：内部命令的往返。
- Runtime（`packages/runtime-core/src/videos/videos.test.ts`，真实的 Engine Host）：去抖写快照、保存与回到版本、关闭前写；V08 的打开时重建；V09；按回合切分与会话记录；V10；V11。智能体工具（`agent-tools/object-tools.test.ts`）：保存、列出、读 diff、回到版本与没有的版本给出下一步。
- 还没有自动化：V02 的随机编辑序列、V05 的大小上限、V04 里两部视频之间来回切换、V12 在没有 git 的机器上的端到端检查。
