# 发布更新日志

每个新版本或新 build 都根据实际包含的 commits／PR 生成更新日志。发布前完成整理；发布完成后写入 GitHub Release 并读回核对。只改 skill、配置或凭据时不生成实际版本日志、不发布。仅补发同一版本的平台产物时复用该版本日志，补充平台信息。

## 确定范围并收集完整来源

1. 固定本次完整 `source_commit`，以同一 App 发布渠道上一次已公开发布的桌面版本为基线，记录其 tag 与完整 SHA。不要用仓库全局 Latest（可能仍指向历史 skill）、未发布的候选 tag、日期窗口或最近若干条 commit 代替基线。核对基线是目标 SHA 的祖先；有分叉或无法唯一确定基线时先解决范围，不能猜测。首次桌面发布应明确首发边界；没有其他约定时整理目标 SHA 可达的完整历史。
2. 保存完整原始 commit 清单到仓库外的任务临时目录，同时记录基线、目标 SHA 与总数。普通版本使用 `base_commit..source_commit`，首发使用 `source_commit`；变量必须是上一步核实的值。例如：

   ```bash
   git rev-list --count "$base_commit..$source_commit"
   git log --reverse --topo-order --format='%H%x09%s' "$base_commit..$source_commit"
   ```

   不使用 `--max-count`、`--first-parent` 或路径过滤缩小原始清单；merge commit 与其子提交在后续归组，不在收集时丢掉。浅克隆、缺失 tag 或历史时先补齐再计数。
3. 按完整 SHA 查找关联 PR，收集编号、标题、正文、合并 SHA 与链接；标题不足以判断时查看 diff。GitHub API／CLI 的列表必须翻完所有分页，核对已收集数量，不能把默认第一页当作全量。PR 必须能对应本次 commit 范围，不能只按合并日期、最近 PR 或标题搜索确定归属。多个 commits 属于同一 PR 时归为一个来源组，仍保留全部 SHA 映射。
4. 直接提交、squash／rebase 后的提交或查不到关联 PR 的提交都以 git 来源补齐，不能漏掉。PR 获取失败时记录缺失信息，用 commit 正文与 diff 整理并披露来源限制；完整 commit 清单仍是覆盖核对依据。不能声称没有读取的 PR 或缺失历史已经完整检查。

## 分批总结与汇总

- 先建立来源台账：每个完整 SHA 恰好归入一个来源组，记录关联 PR、变更要点、批次与最终去向。merge、重复来源和 revert 都保留归属；不能靠记忆或自由摘要追踪覆盖。
- 内容能在上下文内完整审阅时直接整理；提交／PR 多或正文与 diff 较大时，按时间或模块分批，通常每批约 30–50 个来源组，按内容体量缩小。保存编号批次、每批来源 ID 清单与摘要到临时目录，逐批完成；不要只抽样、截断前后若干条，或把未读内容交给最终摘要猜测。
- 每批摘要记录用户可见功能、修复、兼容性与迁移要求、平台限制、相关工程变更及对应 SHA／PR。内部改动也必须审阅并登记，可标为「内部改动，无用户可见变化」；没有证据的影响不要推测。跨批关联的修复、重复改动或 revert 先保留来源，汇总时对照最终代码确认实际出货效果。
- 全部批次完成后再合并同类项：同一功能合成一个条目并合并来源；已撤销且未出货的变化不写成新功能。保留不同修复、限制和迁移事项，不因只突出亮点而遗漏。公开正文面向用户描述结果，PR 链接或 commit 链接提供依据，避免逐条复制 commit 标题。
- 汇总后核对：所有批次来源的并集等于原始清单，既无遗漏也无范围外来源；归组后的完整 SHA 数量等于原始总数。每个来源组都有最终条目或明确的省略理由（如纯内部改动、重复或已撤销）。任何未归类来源都要补齐后再发布，不能宣称「完整整理」。

commit 的 type 与统一 scope 按[开发流程 §1.1](../../../../docs/development-workflow.md#11-提交分类)辅助归类：`feat`、`fix`、`perf` 通常对应功能、修复、性能，同 scope 的内容按主题汇总并保留各项独立修复。其他类型按实际用户影响判断。旧提交没有前缀或分类不准确时，读取正文与 diff 补充判断；`docs`、`chore` 等类型也必须进入覆盖台账，不能直接过滤。

分支／worktree 合入前按[开发流程 §1.2](../../../../docs/development-workflow.md#12-合并前提交整理)形成事项提交。发布时审阅整理后的 commit 正文、PR 与最终 diff，不能只读 squash 标题而遗漏内部各项变化；不要为了日志归类再改写已合入 `main` 的历史。覆盖计数以最终冻结 SHA 的实际 commit 范围为准。

完整整理要求审阅并交代所有来源，不要求把每条内部提交放进公开正文。更新日志默认用英文（包括标题与正文），用户明确指定其他语言时按要求处理；不因对话语言或历史日志语言改变默认值。

## 发布与读回验证

1. 发布前保存汇总正文（如临时目录里的 `release-notes.md`）及覆盖台账，记录基线 tag、目标 SHA、commit／PR 数、批次数与核对结果。候选构建只交付本地日志。冻结 SHA 若改变，重新收集范围并核对新增来源，不能沿用旧日志直接发布。
2. 手动创建 Release 时，通过正文文件写入日志并保留平台、签名、公证、依赖与验证边界。Actions 当前主要生成平台说明；它不代替本流程的变更整理。等本次所有发布任务和平台正文追加都完成后，重新读取实际 Release body，把准备好的更新日志与已有平台说明整合，保存到新的正文文件，然后更新：

   ```bash
   gh release edit "$release_tag" --repo "$release_repo" --notes-file "$notes_file"
   gh release view "$release_tag" --repo "$release_repo" --json body,url,tagName
   ```

   变量指向核实过的仓库、tag 和已整合的正文文件。不要在平台发布任务仍写正文时抢先覆盖，不改变 Latest、tag、assets 或 feeds。正文中已有本版本更新日志时更新该部分，保留其他段落，避免重试追加重复内容。
3. 读回核对版本与范围、各类变更、来源链接、平台说明均保留且无重复。若发布任务重跑又修改正文，再核对并按需补回；未写入或读回不一致时，发布任务尚未完整完成。
4. 最终报告提供 Release 链接、比较范围、覆盖数量与批次核对结果，并说明实际来源缺失或跳过项。不要把自动平台说明或 GitHub 自动生成的 PR 列表当作已整理完成的更新日志。
