1. 项目概览

了解 BaoCut 是什么、解决什么问题，以及它的技术选型理念。

BaoCut 是一个「以可编辑视频为中心」的 AI 视频智能体。
它的核心哲学是：视频是真理之源（The video is the source of truth）。 所有转录、翻译、字幕、配音、章节、动效都落在可编辑时间线上， 用户可以随时接管并精确修改任何一行、任何一帧，而不是拿到一个一次性 MP4 后重头再来。

🎯 一句话定位

用户用自然语言下达任务 → 智能体转录、翻译、配音、剪辑、生成动效 → 所有结果进入共享的可编辑时间线 → 用户随时接管精修 → 导出成片。

🛤️ 四条入口，同一个 Runtime

🖥️ 四端统一
  • 桌面应用（Electron） — 主力工作界面：Home 创作模板、Space 浏览、全功能时间线编辑器
  • CLI（baocut） — 脚本/终端调用；可管道化，退出码语义化
  • MCP 服务 + BaoCut Skill — 外部智能体（Claude Code、Codex、Cursor…）通过同一套工具目录驱动
  • Web 客户端 — 一次性链接在浏览器打开某个视频的编辑器，方便远程智能体展示工作
核心理念：所有入口走同一套协议、编辑同一部视频、经过同一个 Node Runtime。 没有第二份业务逻辑，没有第二个写入方。

🔐 状态所有权：每份状态只有一个权威

原则：Node 不凭缓存副本独立增加视频版本；Rust 不把模型任务状态复制成第二份账本。 任务产物入库与视频应用之间用幂等回执对账，不要求跨数据库的分布式事务。

3. 进程树与生命周期

从 Electron 启动到 Runtime 优雅退出，理解每个进程的职责与停止顺序。

BaoCut 采用多进程架构：界面轻薄、业务集中、计算隔离。 每个视频持有一把操作系统文件锁，保证在跨窗口、跨 Home 的场景下也只有一个写入者。

🌳 进程树

Electron Main                          ← 窗口 / 菜单 / 更新 / 监管
├─ Renderer(s) : React + WASM 预测预览  ← 每窗口一个
└─ BaoCut Supervisor（可脱离界面运行）  ← 启动/重启/停止 Worker
   └─ Runtime Worker（Node）            ← 三个业务模块：Harness · Video · Models
      ├─ Engine Host（Rust）            ← 视频单写方，每个视频独立加锁
      ├─ Agent 进程                     ← 按会话：Claude Code / Codex / Pi / OpenCode …
      ├─ Render / Media Workers         ← 按任务池复用
      ├─ Model Workers                  ← 每个常驻模型包一个进程，按需启动
      └─ Browser / Remotion Workers     ← 代码动效帧烘焙，按隔离域复用

⏱️ 生命周期关键事件（点击展开细节）

1

🚀 启动发现

Electron 检查发现文件（instanceId / home / endpoint / runtimeVersion），识别已有 Runtime 或创建新 Supervisor。

启动阶段：acquiring-lock → starting → ready / degraded / failed。 进程存在 ≠ 可以接收业务，必须进入 ready 才发业务请求。 一个 BAOCUT_HOME 对应一个 Supervisor，多个窗口复用同一 Runtime。
2

🛡️ Supervisor 监管

拉起 Runtime Worker、发布 ready、处理崩溃重启与退避。

运行期崩溃可以有界重启；启动失败则报告错误，不无限拉起。 替代者取得写入权之前必须验证旧 Worker + Engine Host 已确认失去写入与执行能力。 PID、启动身份和代（generation）三者一起验证。
3

🔒 Engine Host 所有权屏障

每个视频持有 OS 文件锁；每次打开获得 ownerGeneration。

Runtime 与 Engine Host 之间使用私有 IPC / 受限套接字，不开公共产品端口。 Runtime 失联时，Engine Host 停止接受新修改并进入受限关闭。 替代宿主不得仅因租约超时抢写同一文件：必须先证明旧进程已退出或撤销其写能力。
4

⌨️ CLI 拉起的 Runtime

CLI 找不到运行中的 Runtime 时，默认后台拉起一个空闲自动退出的实例。

带参数：--launched-by cli --idle-exit。 空闲满 runtime.idleExitMinutes（默认 10 分钟）自动停止。 条件：无活动连接 · 无排队/运行任务 · 无开着的对外服务。 runtime.stop 只停 CLI 自己拉起的那一个：非本人 → RUNTIME_NOT_OWNED；还有人用 → RUNTIME_IN_USE。
5

🛑 正常停止顺序（可中断的有序关闭）

严格按顺序执行，避免留下「待对账」或「半应用」的视频状态。

  1. 停止接纳新业务，把 Task / Run 标为 stopping
  2. 结算仍在提交边界内的视频事务（不丢已在管线内的写入）
  3. 请求取消 / 中断本地 Job 与 Agent Turn
  4. 持久化任务、候选、审批、外部任务 ID（用于下次启动对账）
  5. 关闭执行器（ModelWorker、Engine Host、CodeRuntime…）
  6. Worker 退出，Supervisor 释放实例锁
超过优雅退出期限 → 升级为进程树强杀，但保留「未确认取消 / 待对账」记录。
6

📦 应用更新

Electron Main 负责：检查 → 下载 → 校验签名与 SHA256 → 等应用退出 → 替换文件。

  • 一个版本一套二进制：engine-host、model-worker、Runtime 同版发布
  • 安装前必须先过「停止屏障」（按步骤 5 执行正常停止）
  • 退出即安装，从不自动重启：下次用户手动打开就是新版本
  • 版本不一致时不混跑：外壳只读取、提示重启服务，不发业务命令
  • 支持按 rolloutHours + releasedAt 做灰度分批推送
易错点：
  • 关闭视图 / 断开连接 ≠ 取消任务。退出应用时才会让用户选择。
  • Agent Turn 结束 ≠ 撤销已应用的修改。已提交的事务独立存在。
  • Runtime 关闭 ≠ 远端云任务必然取消。界面必须明确显示仍可能在计费的任务。

转录结果（baocut.asr-result/v1）存入 Artifact Store，Application 提交给 Engine Host → VideoEngine 事务校验 → 原子写入 VideoStore（Revision +1，事件落盘）。

🌐 翻译 + 双语字幕层

Models 能力路由到文本 Provider，译文按句级 alignment 与原文对齐， 经 captions_create 计算切条 → 再进 VideoEngine 建两层字幕实例。

7

✂️ 口播剪辑（去口头禅/长停顿）

智能体根据转写 + 填充词检测，生成编辑操作 → edits.apply → VideoEngine 做时间语义校验（精确有理数、帧量化）、版本冲突检测 → 提交。

8

🎬 用户审阅 + 调整时长 → 精确到 60s

用户拖拽时间线（Renderer 内纯本地操作 + WASM 交互预测）；确认提交时走同一命令网关，进入同一个事务与撤销栈。

9

📤 Export Worker 成片导出

export Job 启动 Export Worker：RenderGraph 排帧 → render-raster 光栅化 → ffmpeg 编码 MP4（烧录字幕）→ 发布 Artifact → 用户下载。

🔑 记住这三个保证
  • 单写：所有视频版本变化 唯一 来自 VideoEngine 的事务提交。
  • 幂等：每个 Application 都有独立幂等键，失败重试不会双写。
  • 阶段独立：Job 完成 ≠ 视频已改；Artifact 就绪 ≠ 已交付；交付阶段由 TaskContract 的 requiredStage 明确判定。

5. 仓库目录地图

理解 BaoCut 为何这样布局，而不是常见的 frontend/backend 分离。

按职责划分，不按语言或前后端划分。 两个 workspace 并存、各管各的依赖： npm workspaces（apps/* + packages/*）与 Cargo workspace（crates/* + bindings/*）。

💡 放置哲学：
  • App 要薄：apps/ 里的代码只做装配，业务逻辑进 packages/ 或 crates/。
  • 按领域拆：不用 utils、common、helpers；文件用领域名（seek.ts、video-store.ts）。
  • 依赖不成环：TS 不直接 import Rust 内部，只经 bindings/（WASM）或 Worker 的 stdio JSON。
  • 只经公开入口引用：包外部只允许 @baocut/<名> 或 exports 声明过的子路径。
  • 生成物不进 git：构建产物进 .gitignore，由 tools/ 生成。

6. 关键架构决策（D01 – D17）

BaoCut 架构中最有重量的 17 个决定。点击卡片查看它为何这么做、约束了什么。

这些决定是「红线」。违反它们的 PR 或实现通常需要单独的设计讨论， 而不是在局部代码里悄悄绕开。
📌 记住最重要的三条（D01 · D02 · D12）：
  1. D01 单入口 + 单写：Node 的 VideoService 是唯一对外入口；Rust 的 VideoEngine 是唯一写入权威。
  2. D02 Engine Host 私有：它是 VideoService 私有的宿主，不是界面要直连的第二个后端。
  3. D12 「完成」由交付阶段判定： 预览任务交 candidate；应用任务必须有回执；成片任务必须有校验后发布的文件。 不得把「Job 成功返回」直接等同于「用户任务已完成」。

🗺️ 架构心智模型 · 一页总结

  1. 一个 Runtime 承接所有入口。桌面 / CLI / MCP / Web 都经 Node Runtime 的 WS 网关。
  2. 一个 Rust 引擎单写所有视频。事务、版本、撤销、事件 outbox 都在 VideoEngine。
  3. Node 做编排，Rust 做状态与计算。两者绝不双写，交接通过「幂等回执 + Artifact Store」对账。
  4. Task → Run → Turn / Job → Application → Transaction。每一层单独建模、独立 ID、独立状态。
  5. 每份状态唯一权威：视频→Rust；会话/任务→Runtime Store；计算→Job Ledger；bytes→不可变 Artifact Store。
  6. 仓库按职责，不按语言。npm workspaces（apps+packages）与 Cargo workspaces（crates+bindings）并立。
  7. 四端同构但 App 轻薄：apps/ 只做装配与生命周期，逻辑都下放到 packages/ 与 crates/。
  8. 关闭视图 ≠ 取消任务。退出时才让用户选后台继续或停止；版本不一致时绝不混发业务命令。
